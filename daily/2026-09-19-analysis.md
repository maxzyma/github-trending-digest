**主线二：竞争从"给 agent 塞什么能力"上移到"怎么约束 agent 的工作流程"。** `Fission-AI/OpenSpec`（NEW，#8）带着 69,373 ⭐ 直接进来，它做的事和技能包正相反：不给 agent 加能力，而是在 agent 动手写代码之前先逼出四份人可审的 Markdown（proposal / specs / design / tasks），审完才允许 `/opsx:apply` 落地。9-16 的 HN 主帖拿到 196 分 / 98 评论。同组的另外三项也在这条线上——`open-code-review`（#3）管的是产出后的门禁，`gitdiagram`（#16）管的是读别人代码时的全局观，`claude-code`（#2）是流程的承载体本身。读者这里可以抓的判断是：技能包这一层的入场门槛低到十几个文件就能上榜，所以竞争正在往上游挪；决定 agent 输出质量的不再只是"它能调什么工具"，而是"它被允许在什么时候动手"。

值得对照的是同赛道的批评。HN 那帖里最集中的反驳不是"不好用"，而是"规格必然和代码漂移，写规格等于多维护一份会过期的文档"；X 上 Povilas Korop 的批评更具体——整个 spec-driven 品类的演示都是一次成型的玩具项目，规格由同一个人现编现审，和真实项目里反复拉扯完全不同。这条线还没有可信的 benchmark。

**主线三：三个老项目回流，而且三者的热度都能追到具体事件——这在近期榜单里不常见。** `rustfs/rustfs`（RE，#13，+267）在 9-16 发了 1.0.0 GA（S3 兼容对象存储，Rust 重写 MinIO 那一类），随后两天连推 1.0.1-preview.3/.5/.6；`ankitects/anki`（NEW，#9，+174）9-14 发 26.09，带两个安全修复（编辑器里查看笔记可读取本地文件、"打开图片"不校验扩展名导致牌组能执行危险文件），并移除了 `anki.importing` / `anki.exporting` 两个 legacy 模块；`asciimoo/hister`（RE，#17，+889，单日涨了总量的 22%）的驱动是 9-17 的 HN 帖，695 分 / 190 评论——比它 8-18 那次 497 分的帖子还高一档。这三项的共同点是可核验：不用推断传播路径，版本号和帖子分数就在那里。

**主线四：榜单解读提醒 — 今天 5 个新面孔的社区底子差异很大，不能按同一把尺子看。** `OpenSpec` 是 245:1 的 stars/subscribers，但有 HN 98 条评论、4,750 个 fork、npm 真实下载量和 issue 里带版本号的流程死锁报障（#1697：重命名一个 scenario 就被判成"丢了 scenario"从而阻断 archive），属于热度跑在采用前面、但不是空心。`gitdiagram` 是 279:1，今天上榜几乎确定来自 9-18 的后端整体重写（FastAPI + Postgres + EC2 全砍，改成 Next.js on Vercel + R2 + Upstash），但近期外部讨论是双空——HN 最高分那帖是 2024-12 的旧帖，X/Reddit 都没有新贴，归因是 commit 历史推断而非直接证据。`tradingview-mcp` 是今天最需要小心的一项：fork:star 比高达 42%，但抽样显示 14% 的 fork 之后有自己的提交，说明 fork 来自真实打补丁的用户；真正的问题不是热度虚不虚，而是它已经停更 7 周、195 个 PR 无人合、CI 自 7-24 起从未跑过，同时 TradingView 官方 MCP Server 已进 public beta。另外 `supabase`（#14，110,162 ⭐）这种超大仓的 146:1 ratio 是结构性的，不能拿来判 vanity。

### [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) — NEW ⭐ 69,373（+296）| TypeScript | 信源：强

**它是什么**: 一个让 AI 编码助手"先写清楚要干什么、你审过之后再动手"的命令行工具。你说一句"给项目加暗色模式"，它不会让 AI 直接改代码，而是先产出四份 Markdown——提案、规格、设计、任务清单；你读完改完确认，再让它按任务清单落地，最后把这次变更归档。整个东西是一个 npm 包（`@fission-ai/openspec`），装在你自己的仓库里，Claude Code、Copilot、Gemini CLI 都能用。

**解决什么问题**: AI 写代码最常见的失败不是写不出来，而是"写出来的东西跟我想的不一样"，而你要等它写完几百行才发现。这类工具把需求先固化成人能读能改的文档，并且规定产物有依赖顺序——设计没定就生成不了任务清单，agent 跳不过思考阶段。和 GitHub Spec Kit、Amazon Kiro 属同类，OpenSpec 的定位是更轻、更适合已有存量代码的项目。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 个人项目把原来手工的"写 spec.md → 反复改 → 让 AI 实现"循环系统化，把变更切成小 PR 提交。
- 场景 2: 多人团队用它统一跨人跨项目的产出规范。issue #725（12 条评论）要的是跨仓/微服务的规格管理，#697 要能自定义 `openspec/` 目录路径，#682 要归档钩子——这些需求只有真把它接进团队流程的人才会提。
- 场景 3: issue #783（16 条评论）提出让不同产物之间互相评审质量，说明已经有人在用它跑多轮迭代而非一次成型。

**社区怎么评价**:
- 正面: HN 主帖（196 分 / 98 评论，9-16）里最认可的是"ceremony 最少的一个"——token 消耗低于 SpecKit，团队能靠它标准化产出。日本开发者社区在 X 上尤其活跃，有企业技术博客逐段拆解它的工作流。
- 负面: 同一帖里的主要反驳是方法论层面的——规格必然与代码漂移、生成的文档"满是 AI 味"、"代码本身就是规格"。X 上 Povilas Korop 的批评最具体：spec-driven 品类的演示全是一次成型的玩具项目，规格由同一人现编现审，与真实项目里和决策者反复拉扯完全不同；他认为 OpenSpec 和 TaskMaster 是这类里最接近可用的，但仍要学一套结构和命令，收益有限。实操摩擦也有具体样本：issue #1697 报告重命名一个 scenario 会被 `MODIFIED` 判定成"丢了 scenario"从而阻断归档，1.8 / 1.9 均复现；#1273 指出 stores 没有 lockfile 或 commit pin，团队之间同步不了确定版本。
- 健康度: 69,373 ⭐ / 283 subscribers（245:1）/ 4,750 forks / 235 个 open issue（其中 123 issue + 112 PR）。维护很活跃，近 8 周每周 12–39 commits，9-17 刚发 v1.13.1。但贡献高度集中：两名主要贡献者占人类提交约 87%。建仓 2025-08-05，仓龄 13 个月。
- Reddit 侧是取证缺口而非"无讨论"：`site:reddit.com` 只返回 Substack / InfoQ 的二手文章，原生讨论未取到。

**风险与争议**:
- **bus_factor**: 两人占 87% 提交，作者即项目；235 个 open issue/PR 在排队。
- **stability**: 工作流刚整体重写（旧 `/openspec` 命令族换成新的 `/opsx` artifact-guided 流程），README 自己还带 TODO 占位符；#1697 这类流程死锁说明校验规则仍在磨合。
- **vanity**: 245:1 的 ratio 加 13 个月仓龄，热度确实跑在采用前面。但 HN 98 条评论、npm 下载量和 issue 里带版本号的深度需求表明有真实用户基底，不是空心盘——这里的判断是"热度超前"，不是"热度造假"。
- **dependency**: 产物质量完全取决于底层模型行为；"规格漂移"这个最核心的批评，工具本身并没有解决。

**技术备注**: TypeScript CLI，MIT，pnpm workspace + 多包结构，仓内自带 `skills/`、`schemas/` 和 `openspec/` 三套目录（工具用自己的流程管理自己）。命令入口是 `/opsx:apply` / `/opsx:archive` 这类 slash command，靠 `AGENTS.md` 对接各家 agent。

### [tradesdontlie/tradingview-mcp](https://github.com/tradesdontlie/tradingview-mcp) — NEW ⭐ 6,478（+79）| JavaScript | 信源：强

**它是什么**: 把 AI 助手接到你本机**已经装好、已经登录**的 TradingView 桌面版上，让它替你看图、改 Pine Script、画关键位、建价格提醒、跑历史回放。它不连 TradingView 的服务器、不抓数据、不下真单——走的是 Chromium 类应用自带的调试接口（CDP），而且那个调试端口默认关闭，必须你自己加 `--remote-debugging-port=9222` 才生效。前提是你有 TradingView 的付费订阅。

**解决什么问题**: 图表分析和 Pine 脚本调试原本全靠手点：改一行指标、切图、看结果、再改。接上 agent 之后可以用自然语言迭代指标、批量读多个标的的指标值、把关键位一次画完。作者把仓库定位成研究项目而非交易机器人——README 里明确列的问题是"LLM agent 怎么和专业交易界面协作"。

**谁在用、怎么用**（来自 Issues/第三方）:
- 场景 1: 个人交易者用自然语言迭代 Pine 指标。issue #396 里多位用户跨配置互相复现问题，精确到 TradingView 3.3.0.7992、MSIX 包名、Win10 19045——这是真在自己机器上跑的人。
- 场景 2: Windows MSIX 安装形态的启动问题多到社区自己出了修复仓（#470 里指向 `emremigh/tradingview-mcp-windows-msix-fix`）。
- 场景 3: 有第三方教程站（humbledtrader.com）写了完整接入步骤做导流，说明有非作者渠道的使用人群。

**社区怎么评价**:
- 正面: 跨用户互相复现 + 社区自发出修复仓，这两件事很难伪造。Forex Factory 上有一条"对开发者和交易者确实有潜力"的讨论。
- 负面: 负面反馈高度集中在同一类——**报成功、实际静默失败，而且部分失败不可逆**。#475 指出 `pine_new` / `pine_open` 会静默覆盖已保存的脚本；#497 指出 `indicator_set_inputs` 会弄坏用户自己的 Pine 指标；#527 指出字符串 `"false"` 被判成 true，结果删光了全部 alert；#484 replay 模式退不出；#489 布局不切换却返回成功；#477 / #476 点击与 async 求值失效；#452 调试模式启动慢 36 倍。
- 健康度: 6,478 ⭐ / 90 subscribers（72:1，反而是今天新面孔里最健康的比值）/ 2,717 forks / 256 个 open issue，**其中 195 个是 open PR**。作者 82 次提交、第二名 3 次。最后一次提交 2026-07-28，而那次只是加了个榜单 badge——实质开发止于 07-21。issue #474 的实测更直接：外部 PR 的 CI 自 2026-07-24 起从未跑过，92 个 workflow run 卡在待审批。
- 关于 42% 的 fork:star 比：抽样 1,945 个 fork 中有 278 个（14%）在 fork 之后有自己的提交，也就是用户在为自己那个 TradingView 版本打补丁——这不是刷任务的形态。fork 爆量出现在建仓后一周内（2026-03-31~04-04，845+），来源是作者自己的 X 账号发布冲量。不过 issue 与 PR 作者中大面积出现 `-dot` / `-tech` / `-oss` / `-bot` / `-hash` / `-ux` / `-alt` 这类用户名后缀，疑似批量注册账号，这一层保留怀疑。

**风险与争议**:
- **stability**: 多个工具"成功返回但实际没动作"，且存在不可逆破坏——覆盖已保存脚本、删光全部 alert（#475 / #497 / #527）。
- **bus_factor**: 单人维护 + 停更 7 周 + 195 个 PR 无人合 + CI 瘫痪；这是目前最硬的信号。
- **dependency**: 走的是 TradingView 未公开的内部 Electron 结构，README 自己就警告每次 TradingView 更新都可能整体打断，建议锁版本。更关键的是 TradingView 官方 MCP Server 已进 public beta——平台方正在把这个项目的存在理由收回去。
- **compliance**: README 自认可能与 TradingView 使用条款冲突，责任归用户。仓内 LICENSE 是 MIT 正文后追加了一段商标声明（明确不授予 TradingView Inc. 与 Anthropic, PBC 的商标权），因此 GitHub 的许可证探测返回 NOASSERTION——商用前需自查。

**技术备注**: JavaScript / Node 18+，通过 CDP 连本机 TradingView Desktop；仓内带 5 个 skill（chart-analysis / multi-symbol-scan / pine-develop / replay-practice / strategy-report）和 1 个 agent 定义，走的是"MCP server + skill 包"双形态。已有独立替代实现（`atilaahmettaner/tradingview-mcp`）。

- 场景 2: 给项目文档配架构图、代码评审前建立全局观。

**社区怎么评价**:
- 正面: 传播侧口碑扎实，HN 222 分、ProductHunt 5.0 分。工具站型项目的用户大多只用网站不看仓库，这也解释了它的高 ratio。

## 如何理解今天的热度信号

今天最容易误读的是 ratio。榜上有三个高 stars/subscribers 比的项目，但性质完全不同：`supabase` 的 146:1 是超大仓的结构性常态（watch 噪音大，用户不订阅）；`gitdiagram` 的 279:1 是工具站型项目的常态（用户用网站，不集成代码）；`OpenSpec` 的 245:1 才真的说明热度跑在采用前面（13 个月仓龄 + 235 个积压 issue/PR）。同一个数字在三种项目上要读出三种结论。

其次是"停更"与"热度"的错位。`tradingview-mcp` 今天只涨 79 ⭐，在榜上几乎垫底，但它是今天最需要提醒的一项——不是因为热度虚，而是因为它的 issue 区有多条不可逆破坏的实测报告（覆盖脚本、删光 alert），同时停更 7 周、195 个 PR 无人合、CI 瘫痪，而平台方的官方 MCP 已进 public beta。热度低不等于风险低。

反过来，今天三个回流项目提供了一个对照样本：`rustfs` 的 1.0.0 GA、`anki` 的 26.09 安全版本、`hister` 的 HN 695 分，三者的热度都能追到一个可核验的具体事件。当一个项目的星增能对上版本号或帖子分数时，解读成本要低得多；对不上的那些（`supabase`、`supermemory`），把它读成"排序边界效应"比读成"趋势信号"更安全。
