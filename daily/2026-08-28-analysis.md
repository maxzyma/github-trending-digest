### [bilawalsidhu/gods-eye-view](https://github.com/bilawalsidhu/gods-eye-view) — NEW ⭐ 8,240（+1,984）| JavaScript | 信源：中

**它是什么**: 一个在浏览器里打开就能用的"间谍卫星模拟器"，但屏幕上的东西是真的。它把一个照片级真实的 3D 地球放在网页里，然后把公开可获取的实时信号叠上去：民航飞机的位置、货轮的航迹、卫星的轨道、地震、火点、路况摄像头。你还能用语音直接问它"这里现在在发生什么"。作者是前 Google AR / 3D 地图产品经理，此前以 YouTube 上的"God's Eye View"系列视频出名（播放量 500 万+），这个仓库就是把那套视频里的可视化开源出来。

**解决什么问题**: 开源情报（OSINT）的原始信号其实一直是公开的——ADS-B 飞机应答机、AIS 船舶信标、TLE 轨道根数、地震台网、公共摄像头。问题在于它们分散在几十个网站，看一件事要开一堆浏览器标签页。这个项目把这些信号合并到同一个 3D 地球上，让"看世界正在发生什么"从翻网站变成转地球。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 事件复盘。作者自述用它做过某次军事打击的 24 小时四维回放，把当时的航迹和卫星过顶叠在一起看。
- 场景 2: 数据源接入。issue #1 里一家公共摄像头 feed 的提供方主动找上门，给了免费 key 并附了可用的 adapter；issue #71 中欧洲用户自建了绕过 Google 3D Tiles 区域限制的方案。
- 场景 3: 大量用户停留在"装起来看一眼"阶段——issue #86、#76 是 npm 安装报错，#74 / #69 是不会配 API key 和 `.env`，#59 是 Google 3D 图层不可用。

**社区怎么评价**:
- 正面: 视觉冲击力被广泛认可；1,840 forks 对 8,240 stars（22% fork 率，榜单里属高值）说明确有相当比例的人真的把它拉下来跑了。
- 负面: 工程质量被点名。issue #87 指出 `vite.config.js` 一个文件 7,383 行，同时承担 API server、代理和安全边界（本地 clone 实测确认为 7,383 行，`src/ui.js` 10,293 行），并称 `npm audit` 报 9 个 high 级漏洞；issue #84 直接以「AI Slop」为题，被作者以"人身攻击"关闭。
- 健康度: 8,240 stars / 219 subscribers（37.6:1）；81 open issues、27 个 PR 全部未合并；contributors 只有作者 1 人；仓库 6 月 22 日建为占位，8 月 24 日才真正开源。license 元数据是 `NOASSERTION`，README 声明 MIT。

**风险与争议**:
- **bus_factor**: 单人维护，27 个 PR 无一合并；`jsawyerdev` 一人提交的 26 条安全 issue（#16–#41）全部零回复、全部未关闭。
- **stability**: 安装失败类 issue 密集，作者自述依赖链存在 9 个 high 级漏洞。
- **dependency**: 核心 3D 底图依赖 Google Maps Platform 计费 key（需绑卡，免费额度约 1,000 session/月），无 key 则最主要的照片级地球图层不可用。

- **privacy**: 服务默认可绑 `0.0.0.0`，那样会把本机 API key 广播给同网段。
- **vanity**: 传播路径几乎完全来自作者自媒体（X 全平台 210 万+ 粉丝、YouTube 500 万播放）；HN 两次投递（8/26、8/27）分别只有 2 分和 3 分、**零评论**，缺少独立开发者的技术评价。

### [JetBrains/go-modern-guidelines](https://github.com/JetBrains/go-modern-guidelines) — NEW ⭐ 2,130（+300）| Go | 信源：强

**它是什么**: 一份专门给 AI 编码助手看的"现代 Go 写法手册"，由 JetBrains 的 GoLand 团队维护。它要解决的是一个很具体的毛病：让 AI 写 Go，它会写出五年前风格的代码——手写 if-else 比大小而不用 `max(a, b)`，手写循环找元素而不用 `slices.Contains`，一连串 nil 判断而不用 `cmp.Or`。这个项目把"该用哪个新写法"整理成机器可读的规则喂给 agent。

**解决什么问题**: README 把病因说得很清楚，两条：① **训练数据滞后**——模型没见过训练截止之后新增的语言特性，比如 Go 1.26 的 `errors.AsType[T]`；② **频率偏置**——即使模型知道新写法，训练语料里 `for i := 0; i < n; i++` 远多于 `for i := range n`，它就倾向输出旧的。以前大家靠在 `CLAUDE.md` / `AGENTS.md` 里手写一段 Go 风格约定来对付，问题是这段约定既不区分项目实际用的 Go 版本，也不会随语言演进更新。

**它实际是什么形态**（本地 clone 核实）: 不是文档集，是「Go CLI + 一个 skill」的组合。规则事实源是 `internal/guidelines/guidelines.json`，实测 **54 条**结构化条目，每条含 `id` / `since_version` / `guideline` / `details` / `examples`，覆盖 Go 1.0 到 1.27，包含 `modernize` analyzer 的全部目标项。`plugin/skills/use-modern-go/SKILL.md` 只有 66 行，靠 CLI 的两个子命令做渐进披露：`list` 在编辑前列出简要规则，`explain` 按需展开示例——避免一次性把几万字规则灌进上下文。CLI 会先读项目 `go.mod` 的版本，只吐出该版本可用的规则。分发上仓内同时放了 Junie / Claude Code / Codex / Cursor 四份 `marketplace.json`，Junie 新版本已内置默认开启。

**谁在用、怎么用**:
- 场景 1: Go 项目日常 agent 编码时自动注入版本感知的现代惯用法，替代手写在 `AGENTS.md` 里的 Go 风格段落。
- 场景 2: 与 `go fix` / `modernize` 互补——后者改存量代码，前者管新写的代码。HN 讨论（[47098398](https://news.ycombinator.com/item?id=47098398)，14 分 4 评论）里就有人指出 `go fix` 已能自动化同类改写，两者定位需要分清。
- 场景 3: issue #3（endigma）提议补 `testing/synctest` 规则，同时建议用 `references/` 目录分层以免主文件撑爆上下文；维护者明确认同"新版本单独分层"这个方向。

**社区怎么评价**:
- 正面: 痛点被普遍认可——"agent 写的 Go 总是过时"是 HN 讨论里的共识；JetBrains 品牌与 Junie 内置分发提供了可信度。
- 负面: issue #14（RO-29，8 月 26 日）在 Go 1.27.0 上实测后列出 8 处缺陷——6 个示例的改写前后行为不等价（涉及 `strings_cut` / `bytes_cut`、`context_after_func`、`maps_clone` 等），1 条 `since_version` 标错（`strings_clone` 标 1.20，实际 1.18），另有 CLI 版本探测在两种情况下判断错误。一个"教 AI 写正确代码"的规则库自身给出行为不等价的示例，是相当直接的质量问题。
- 健康度: 2,130 stars / 19 subscribers（112:1）/ 65 forks；contributors 5 人，实质由 1 人推进；10 个 open issue，最后一次提交 8 月 19 日（`Add guidelines for encoding/json/v2`）。Apache-2.0。

**风险与争议**:
- **正确性**: issue #14 实测出的 8 处缺陷至今未修，对应修复 PR #20–#24 经 API 核实全部 **0 comment、未合并**（#20 提交于 8/26，#21–#24 于 8/27）。规则库的权威性目前打折扣。
- **bus_factor**: 实质单人维护，8 月 19 日后主干无新提交，而外部 PR 正在堆积。
- **dependency**: 运行时依赖本机 Go toolchain，首次使用需 `go install` 拉 CLI，要求 Go 1.25+。
- **vanity**: 2,130 星 / 19 subscribers 的比值主要由 JetBrains 官方博客与品牌背书驱动；搜索 `go-modern-guidelines` 关键词本身在 HN 零命中，Reddit r/golang 无讨论。#20–#24 五个 PR 在 8/26–8/27 两天内由五个不同账号提交、内容都是小修，更像上榜后的 drive-by 贡献潮而非稳定社区。

**技术备注**: Go 1.25+，Apache-2.0；核心是 `guidelines.json` + 一个查询 CLI + 一个 SKILL.md；同时按 Claude Code plugin、Cursor plugin、Codex plugin、Junie extension 四种规范打包。

## 如何理解今天的热度信号

今天有两类需要分开看的"热"：

**第一类是事件驱动的终点热度。** Nitter 的 71 星和 28% 的 fork 增长不是采用信号，是备份信号——项目已经归档，star 记录的是"这件事发生过"。这类热度对读者的价值在于事件本身（平台方对第三方前端的法律态度），而不在于项目可用性。看到类似的"墓碑式上榜"时，先查 `archived` 字段和 README 顶部声明，比看 star 曲线快得多。

**第二类是传播驱动的起点热度，需要看外部贡献能不能进得去。** `gods-eye-view` 和 `go-modern-guidelines` 今天的共同点很有意思：都不缺高质量的外部输入——前者有人系统性提了 26 条安全 issue，后者有人实测列出 8 处规则缺陷并附了 5 个修复 PR——但**两边的外部输入都停在了零响应状态**。这比 stars/subscribers 比值更能说明问题：比值高只是说明关注的人多于跟进的人，而"提了没人理"说明项目当前的吞吐瓶颈在维护者本人。对想在这两个项目上投入时间的人，合理的观察窗口是接下来一两周这批 PR 有没有被处理。

顺带一提，`marin-community/marin` 是今天的反向对照：2,703 星、33 subscribers，绝对数都很小，但 584 个 open issue 和 8,700+ 的 PR 编号说明它是个真在跑的研究仓库。**star 少不等于冷，issue 与 PR 的流转速度才是社区活性的直接读数。**
