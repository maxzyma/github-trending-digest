### [mvt-project/mvt](https://github.com/mvt-project/mvt) — NEW ⭐ 13,618（+169）| Python | 信源：强

**它是什么**: 一个命令行取证工具。你把 iPhone 的 iTunes 备份，或 Android 的 bugreport 交给它，它拿这些数据去比对已公开的商业间谍软件痕迹清单（Pegasus、Predator、Graphite、NoviSpy 等），然后告诉你这台手机上有没有被这些软件打过的迹象。它由国际特赦组织（Amnesty International）安全实验室开发，2021 年在震动全球的 Pegasus Project 调查中首次公开。项目自己反复强调：这是给技术人员和调查员用的取证工具，**不是给普通人自查手机的杀毒软件**。

**解决什么问题**: 在它之前，判断一台手机是否被国家级间谍软件入侵，基本只能把设备交给少数几家实验室做人工分析——对记者、活动人士、律师这类高风险人群来说，这条路既慢又不可规模化。MVT 把这套分析流程固化成可复现的开源工具：任何懂命令行的人都可以在自己的机器上跑一遍备份分析，输出可供第三方复核的取证记录。它把"我的手机是不是被监控了"从一个无法自证的疑问，变成一个有标准流程、有可审计输出的技术问题。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: Amnesty 安全实验室与 Citizen Lab 把它作为标准工具链的一环（配合 AndroidQF 采集），用于确认记者与活动人士设备的感染证据——近期的 Pegasus / Graphite 一手报告都走这条路。
- 场景 2: 社区在要求它输出更贴近实战的检测维度。#773（9 条评论，已推进成 PR）与 #744（5 条评论）都在要"列出设备上启用了哪些无障碍服务"，因为无障碍权限是间谍软件常用的驻留面。
- 场景 3: 个人安全研究者用它做公开的设备体检报告（如 `Mecapixel/ios-mvt-security-assessment`），把输出当作可发布的证据材料。

**社区怎么评价**:
- 正面: HN 上有真实口碑沉淀——2025-03-17 一帖 151 分 / 73 评论，2021-07-18 首发帖 93 分 / 17 评论。X 上的传播路径不在开发者圈，而在人权与新闻圈层：WikiLeaks、Amnesty 前秘书长 Agnès Callamard 都转发过，Amnesty 的 Rasha Abdul-Rahim 还专门发声明澄清"这是面向技术受众的工具"。近期 PR 多是真实使用踩坑修复（#937 mountinfo 检测、#922 AppleDouble 旁挂文件）。
- 负面: 误报是最热议题。#495（11 条评论，2024 年开，至今未关）报告"非应用商店/MDM 安装的可疑应用"疑似误检。上手门槛也长期被质疑：#167、#97 都是普通用户在问"我没有 Mac 或 Linux，怎么查 Pegasus"；#458（5 条评论）是备份路径报错，#680 是 Windows 测试挂。
- 健康度: 13,618 ⭐ / 286 subscribers ≈ 48:1，对成熟工具属正常量级，不构成虚高信号；open issue 仅 54，1,328 forks；发版节奏是每周一，且有 CI 机器人自动跟进新 iOS 版本号。贡献集中在 botherder（541）、DonnchaC（216）、Te-k（197）、besendorf（101）——头部四人占绝大多数，但是四个活跃维护者而非单人。
- Reddit: 两次 `site:reddit.com` 检索均未返回结果，记为未核实，不等于无讨论。

**风险与争议**:
- **compliance**: License 被 GitHub 识别为 `NOASSERTION`——它是自改的 MPL 变体，明文禁止用于"对抗性取证"，不是 OSI 标准开源许可。商用或集成前必须走法务确认。
- **bus_factor**: 贡献高度集中在 Amnesty 内部四人，项目与该机构的资源绑定较深。
- **误报判读**: #495 长期未解，输出需要人工解释，不能当"扫一下就知道有没有中毒"用。误读输出对高风险用户的后果是实际的。

**技术备注**: Python CLI，通过 pip / pipx 安装。输入为 iOS 加密或未加密 iTunes 备份、完整文件系统镜像，或 Android bugreport / AndroidQF 采集包；IOC 走 STIX2 格式，可外挂第三方指标库。输出为结构化 JSON 时间线，便于第三方复核。

### [zhouxiaoka/autoclip](https://github.com/zhouxiaoka/autoclip) — NEW ⭐ 8,290（+250）| Python | 信源：中

**它是什么**: 把一段长视频自动切成能直接发布的短片。你给它一场访谈、一期播客、一节课程或一段直播回放，它读字幕、让大模型挑出高光段落并打分、生成标题，再用 FFmpeg 切片、组成合集，最后按抖音 / 小红书 / YouTube Shorts / B 站各自的尺寸预设导出。三种用法：macOS ARM 与 Windows x64 桌面包、Docker Web 版、以及 CLI / MCP 接入。

**解决什么问题**: 做二创的人原本要把两小时素材整个看完、手动标记时间点、逐段裁切、再为每个平台调一遍尺寸和标题——这是一整晚的活。它把"找高光"这一步交给大模型评分，把"多平台适配"变成预设，目标是把一晚压缩到一次任务。它不解决创意问题，解决的是重复劳动问题。

**谁在用、怎么用**（来自 Issues/中文社区）:
- 场景 1: 个人二创者跑桌面包或 Docker 处理单条长视频。Release 页面有真实下载量（1,551 / 232 / 345），说明确实有人在装。
- 场景 2: 社区里最有价值的使用证据其实是自救型贡献：#18（7 条评论）有用户自己列出四处补丁；#35 是 Windows 部署修复；#56、#40 有人直接把能跑通的 fork 甩出来给别人用——#40 里甚至出现了受它启发另写的衍生项目 OpenClip。
- 场景 3: 真实效果反馈偏负面。#59 里有用户报告用 gpt-5.4 处理 5 分钟视频，结果切出 3 个 2 分钟片段、章节识别失效。

**社区怎么评价**:
- 正面: 更新确实在推进——9 月内连发 v1.2.1（9-06）、v1.3.0（9-20）、v1.3.1（9-21）。作者对 #59 的质疑有正面回应，称 Docker 路径问题已在 v1.2.1 修掉（#88）并补了 CI。
- 负面: "跑不通"是 issue 区的主旋律，而且很具体：#59「这么多 Star 是咋刷出来的。数不清的错误。」（7 条评论，多人同感）、#26「连个视频都导入不了」、#42「根本用了各种错误」、#24 进度显示错误、#11 切片数为 0、#14 加模型报网络错误。
- 健康度: 8,290 ⭐ / 35 subscribers ≈ 237:1，是今天榜上最高的比值；1,575 forks（fork:star ≈ 19%，异常高，但检索显示大量是整仓原样 fork 而非贡献）；open issue 16；contributors 只有 3 人，其中作者 111 次提交，另两位分别 2 次和 1 次（其中一个是 Cursor Agent 账号）——实质是单人项目。
- HN: 无讨论（Algolia 命中的全是同名或近名的其他项目）。
- Reddit: 无讨论。
- 中文社区: 只有推荐式内容（知乎专栏、CSDN 项目推荐、AITOP100 等聚合站），未见独立实测；部分聚合站还把参数吹到与 README 不符（"处理 5000 万条视频""接入 Google Vision"）。真实使用证据最集中的地方反而是 issue 区的报错串。

**风险与争议**:
- **vanity**: 237:1 的 stars/subscribers 比、HN 与 Reddit 双零讨论、中文侧无独立评测、README 自挂 Trendshift 徽章作为"社区成就"——这几项同时出现，说明它的 star 数远领先于可验证的使用痕迹。
- **stability**: 装不上、导不进、切片为 0 是 issue 区的主要形态。把它当生产工具用，预期要自己动手修。
- **bus_factor**: 单人维护，且部分提交由 Cursor Agent 代提。
- **cost**: 需自备 API key，按视频长度计费。用云端模型处理长视频时成本不可忽略。
- **compliance**: 内置 B 站 / YouTube 下载能力，产品定位是"二创"，涉及平台 ToS 与版权风险。

**技术备注**: Python。大模型侧支持通义千问 / DashScope、OpenAI 兼容接口、Gemini，也可接本地 Ollama / LM Studio（qwen2.5:7b）；无字幕时用 faster-whisper 本地转写。FFmpeg 为必需依赖；Web 模式额外需要 Redis 与 Celery，CLI 模式不需要。MIT。

## 如何理解今天的热度信号

今天是最近一周里榜单最"平"的一天：前六名日增彼此相差不到 2 倍，没有单一爆点项目，昨日靠超大基数占位的 `affaan-m/ECC` 与靠单日增量领跑的 `cloudflare/security-audit-skill` 同时掉榜。这种形态下，排名本身的信息量下降，更值得看的是单个项目的热度来源是否落地。

三条可以直接用的判读方式：

1. **stars/subscribers 比要按项目类型分档，不能一刀切。** 今天最低的是 `ruanyf/weekly`（24:1，内容订阅型仓库），最高的是 `yynxxxxx/Codex-X`（265:1）与 `BuilderIO/agent-native`（372:1）。但 `mvt` 的 48:1 与 `quiche` 的 73:1 对成熟基础工具都属正常——同一个比值放在四个月龄的新项目和八年龄的协议实现上，含义完全不同。
2. **把 star 曲线和代码活动放在一起看。** 今天有两项出现明显落差：`OpenStock` 连续三天加速到 +844，但仓库侧只有 README 与 cron 文案改动；`project-nomad` 日增从 +40 跳到 +394，而最后一次正式发版停在 9-02。热度来源在仓库之外时，star 不能读成采用度。
3. **issue 量的含义取决于 issue 的内容。** `cua` 的 1,036 个和 `coder` 的 1,078 个是使用密度的证据，`ruanyf/weekly` 的 9,159 个是内容仓库的正常形态；而 `autoclip` 只有 16 个 open issue，却集中在"装不上、跑不通"——数量少反而是坏信号。

今天需要明显打折的只有 `autoclip` 一项：237:1 的比值、HN 与 Reddit 双零讨论、中文侧只有推荐式聚合内容、issue 区以运行失败为主。它的技术路线不假，但 8,290 ⭐ 目前支撑不起"可用"这个结论。
