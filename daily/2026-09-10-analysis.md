**主线三：昨天点出的"OpenAI 插件生态换仓、装错风险就在榜单上"今天自我修正了。** 昨日 `openai/skills`（已弃用）排 #3、继任仓 `openai/plugins` 排 #16，旧仓排名高出新仓 13 位。今天旧仓直接掉榜，新仓从 #16 升到 #9（+7 位，6,213 ⭐，+498）。新仓 9-08 的提交是 `Add Qodo to curated marketplaces`，仍在按 marketplace 收录节奏迭代。这是一个值得记下的读榜经验：**Trending 上"弃用仓排名高于继任仓"的错位通常只持续几天**，因为它靠的是搜索结果和转发链的惯性，而这两者会跟着官方 README 的迁移告示逐步更新。要给 Codex 装 skill 的读者，现在认 `openai/plugins` 已经和榜单一致。

**主线四：榜单解读提醒 — 今天两个新面孔的"仓龄"和"许可"都不能按表面读。** `vastsa/PI-Desktop` 的 GitHub 创建日期是 2023-03-22，看起来是个三年半的老项目，实际不是：仓内 2,039 个 commit 全部在 2026 年，最早一条是 2026-07-24 的 `chore: initial commit`；而这个仓最老的一批 fork（2023-04）全都叫 `openai-apikey-query`，描述是"批量查询 OpenAI 账号已用余额，判断 apikey 的状态"。也就是说这是一个 2023 年的 OpenAI key 余额查询工具在 2026-07-24 被改名、重写历史后变成的 agent 桌面端（同日作者另建 `PI-Desktop-Legacy` 存放重构前代码线），真实年龄约 7 周，1,694 ⭐ 里含一部分从旧工具继承来的星。`liquidslr/system-design-notes`（NEW #8，18,032 ⭐）的问题在另一头：它是 Alex Xu 那本付费书《System Design Interview》全 28 章的逐章笔记，仓内**没有 LICENSE 文件**，而配图经本地实测是书内插图直接截取——`04. Rate Limiter/images/fixed-window-counter.png` 底部还残留着被裁掉一半的书本图注 "Figure 4-…"。两个样本的共同点是：**GitHub 页面上最显眼的那几个数字（创建日期、star 数）恰好是最不能直接用的**。看新面孔时，先看最早一条 commit 的日期、再看 LICENSE 有没有，然后才看 star。

### [Tencent/teamai-cli](https://github.com/Tencent/teamai-cli) — NEW ⭐ 3,040（+556）| TypeScript | 信源：中

**它是什么**: 一个团队级的"AI 使用经验同步器"。你的团队里每个人都在用 Claude Code / Cursor / Codex，每个人都在自己电脑上攒了一堆提示词、规则、skill 和踩坑笔记，彼此互不知情。这个工具的做法是：把这些东西放进一个团队共享的 Git 仓库，然后自动分发到每个人本地对应工具的目录里。谁摸索出好用的做法就 `teamai push` 开一个 MR，评审合并后其他人下次开会话时自动 `teamai pull` 拿到。

**解决什么问题**: 以前团队里"AI 用得好"是个人技能——同一个坑五个人各踩一遍，好用的规则只在某人的本地 `~/.claude/` 里。已有的解法要么是发到群里靠人手抄，要么是搭一个内部知识库平台（然后没人维护）。这个工具的取舍是不另建平台，直接复用 Git 已有的评审、版本和溯源机制：skill 变更走 MR，谁改了什么、为什么合并都有记录。此外它还带按角色/标签分发（不同岗位只同步自己那套）、会话结束按"摩擦度"（被打断、被纠正、工具调用失败）自动沉淀踩坑经验，以及 BM25 + 图谱的团队知识召回（默认关闭）。

**谁在用、怎么用**（来自 Issues/X）:
- 场景 1: 管理员建一个共享仓库，成员在项目内 `teamai init`，SessionStart hook 在每次开会话时自动把仓内 skill 拉到 `~/.claude/skills/`、`~/.codex/skills/`、`~/.cursor/skills/` 等对应目录。仓内 `src/known-agents.ts` 列了 34 个 agent 的目录约定，覆盖面是这个仓最实的部分。
- 场景 2: 团队 wiki 与代码知识召回——仓内 `skills/team-wiki-codebase` 与 `agents/teamai-recall.md` 提供从共享仓检索团队既有结论的入口，但 issue #360 反映该 skill 依赖外部 CLI，纯 IDE 用户装不上。
- 场景 3: 按 Git 托管平台适配——TGit 用户需 `gf` CLI、CNB 用户需 `cnb` CLI，`init` 会自动安装第三方 CLI。

**社区怎么评价**:
- 正面: 讨论集中在"Git 原生"这个取舍上，认为不去搭知识库平台而直接复用 Git 的评审与溯源是对的。第三方评测则指出它更适合定位成"分发层"而不是知识库——没有权限管理、没有浏览体验、没有讨论区。
- 负面: 都是具体缺陷而非架构质疑。#436：`teamai status` 对子目录里的 rules 计数为 0（但 pull 正常）；#440：Codex Stop hook 返回不兼容的 JSON；#424：过期或退订的 skill 不自动清理；#360：team-wiki skill 依赖外部 CLI。
- 健康度: 3,040 ⭐ / 10 subscribers = **304:1**（极端偏斜）；191 forks（6.3%，正常）；open issues 24，其中 bug 标签 16；已关闭 issue/PR 编号已到 466，说明吞吐是真实的；contributors 34，但 `jeff-r2026` 一人 534 次提交、第二名 89 次。创建于 2026-04-27（约 4.5 个月），MIT。

**风险与争议**:
- **vanity**: 304:1 的 stars/subscribers 比配上 HN 两条提交各 3 分 0 评论、Reddit 零讨论，传播主要靠中文 AI 资讯号转述 README，缺英文社区的独立使用报告。
- **bus_factor**: 主维护者 `jeff-r2026` 账号创建于 2026-04-27 09:12Z、本仓创建于同日 09:42Z（相隔 30 分钟），且独占 534/约 640 次提交；34 个 contributors 的分布高度集中。
- **stability**: Team Context 与 Team Improvement 两层自标 beta，9-09 一天内连发 v0.24.0-beta.1/2/3 三个预发布版本；hook 会改写各 AI 工具的本地配置。
- **dependency**: 按 Git 托管平台需要不同的第三方 CLI（TGit 的 `gf`、CNB 的 `cnb`），`init` 会自动安装。

**技术备注**: TypeScript，npm 分发，MIT。核心是 SessionStart hook + 各 agent 的 skills 目录适配层（`src/known-agents.ts` 34 项：29 个 coding 类、5 个 lobster 类、1 个 `.agents/skills` 中央目录）。仓内 `skills/` 只有两个自带 skill，主体是分发与同步逻辑。

### [vastsa/PI-Desktop](https://github.com/vastsa/PI-Desktop) — NEW ⭐ 1,694（+417）| TypeScript | 信源：中

**它是什么**: 把终端里的 AI 编程 agent 搬进一个独立桌面应用——本地项目、会话、diff review、终端输出、通知、插件市场都收在一个窗口里。自带模型接入（OpenAI / Anthropic / 本地 / 任意 OpenAI 兼容 API），不需要注册账号，特权操作走一个权限层审批（Agent / Plan / Goal 三档批准边界）。

**解决什么问题**: 现有的 agent 编程工具要么绑在 IDE 插件里、要么只能在终端跑，会话历史、diff 审阅和权限确认散在几个地方。这个项目的取舍是"本地优先 + 用户自己拿钥匙"：数据落在本地 SQLite，模型 key 是自己的，插件由用户自行安装。

**谁在用、怎么用**（来自 Issues/中文社区）:

- 场景 2: 与终端侧 agent 会话互通——#67、#134 要求能和终端 pi CLI / ZCode 的会话打通。
- 场景 3: 插件使用与隔离——#167 规划模式调不起浏览器插件，#159 SSH 插件报错，#168 在讨论插件的权限隔离边界。

**社区怎么评价**:

## 如何理解今天的热度信号

**第一件事：今天最该看的不是比值，是"最早一条 commit 的日期"。** 今日 stars/subscribers 比最高的三个是 `PI-Desktop` 847:1、`diagram-design` 336:1、`teamai-cli` 304:1。但这三个的性质完全不同：`diagram-design` 有连续的功能提交和 issue 编号（#191、#192、#207），高比值只说明大量人收藏当模板库；`teamai-cli` 的 466 号已关闭编号说明吞吐真实，问题在英文社区零 grounding；而 `PI-Desktop` 的 847:1 之所以特别，是因为它的 1,694 ⭐ 里有一部分不是这个项目挣来的——那是 2023 年一个 OpenAI key 查询工具的遗产。**这三种情况用同一个比值表达不出来，得看具体信号的组合。**

**第二件事：日增和排名今天再次大面积脱钩。** `i-have-adhd` +4,650 排 #1，`diagram-design` +2,249 排 #6（且下滑 4 位），`system-design-notes` +1,397 排 #8，`ECC` +1,133 排 #13（跌 9 位）；反过来 `pascalorg/editor` 只 +107 却排 #4，`text-to-cad` +124 排 #5。今日排名前五里有两项的日增在全榜倒数。这个现象在昨天的分析里也出现过，可以当成常态：**Trending 的排序不是日增排序，把它当热度排行读会得到相反的结论。**

**第三件事：教材/资料类的高 fork 率不等于高使用率。** 今日三项学习资料的 fork 率分别是 `system-design-notes` 18.9%、`ai-engineering-from-scratch` 17.4%、`awesome-gpt-image-2` 9.7%，明显高于工具类（`i-have-adhd` 5.9%、`teamai-cli` 6.3%）。fork 在这类仓里的主要用途是"先存一份"，不是参与开发——`system-design-notes` 的 3,408 个 fork 对应的是 3 个 contributors 和 5 个 open issue。判断这类仓有没有人真在维护，看 issue 里有没有关于**内容本身**的讨论（纠错、补章、质量争议）；`system-design-notes` 一条都没有。

**一条实操建议**：今天两个新面孔的教训可以合成一个动作清单。看到一个陌生的高星仓，按这个顺序查三样东西——① `git log` 最早一条 commit 的日期（不是 GitHub 显示的创建日期）；② 有没有 LICENSE 文件，内容如果来自第三方（书、课程、上游代码）有没有署名或授权说明；③ 有没有对应的公开讨论（HN/Reddit 的独立帖，而不是作者自荐或资讯号转述）。这三样任一项为空，star 数就不能按面值用。
