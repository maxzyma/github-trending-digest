## NEW 项目

### [magnitudedev/magnitude](https://github.com/magnitudedev/magnitude) — NEW ⭐ 1,970（+161）| Python / TypeScript | 信源：中

**它是什么**: 一个装在你自己电脑上的"模型供应商"。你现在用的编码 agent（Claude Code、Codex、OpenCode、Cline、Hermes 等）默认要连 Anthropic 或 OpenAI 的云端模型，Magnitude 在本机起一个推理服务，让这些 agent 改连本机——不花 token 费、不联网也能用、代码和提示词不出机器。

**解决什么问题**: 在它之前，想让 agent 用本地模型的人通常自己装 Ollama 或 llama.cpp 再手动挑模型。难点不在"装"，而在"挑"：不知道自己这台机器的显存和带宽能吃下哪个模型、该用哪档量化、跑起来会不会慢到没法用，也不知道并发和投机解码该怎么配。Magnitude 的做法是先探测硬件（芯片、内存、带宽），据此给出一份算过的模型推荐清单，选定后自动下载、调参、按需加载与空闲卸载，避免长会话一直占着显存。安装后只要把一句话交给 agent（`magnitude docs onboarding`），由 agent 自己完成后续配置并切换到本地模型。

**谁在用、怎么用**（来自 Issues/外部报道）:
- 本地跑编码 agent 的开发者是主要人群，Issue #20 在问 MLX 支持（Apple 芯片路线），#44 报告 AMD Strix Halo 上只读到非 VRAM 那部分内存——都是自建本地推理的人才会踩的问题。
- 想接自己现有后端的用户：Issue #42 描述 CLI 把只有 thinking 的助手轮次序列化成 `content: null`，Ollama 这类严格的 OpenAI 兼容后端会返回 400，之后会话永久卡死，属于对接层的真实使用反馈。
- Issue #43 提出可配置的本地 agent 权限，说明已经有人把它当日常工作流在跑，而不只是试装。

**社区怎么评价**:
- 正面: 外部技术 newsletter（Daily Dose of DS）以"不用再猜该跑哪个本地模型"为角度做过介绍，切中的正是选型这个痛点；Issue 讨论集中在硬件适配而非"这是什么"，说明来的人目标明确。
- 负面: 跨平台成熟度不足是最集中的抱怨——Issue #22（非 Ubuntu 的 Linux 安装问题，9 条评论，是全仓最热）、#36（Windows 下 `/bin/sh.exe` 问题）；官方明确只支持 macOS 与 Linux，Windows 需走 WSL。
- 健康度: 1,970 ⭐ / 13 subscribers / 143 forks / 13 open issues。stars:subscribers 约 151:1，但在这个绝对体量下参考价值有限。贡献者高度集中：anerli（380 次提交）与 thrgreenwald（173 次）合计占九成以上。npm 包 `@magnitudedev/cli` 当前版本 0.0.11，最近三个版本都发在 9 月 1—2 日，仍在高频迭代期。
- 外部讨论: HN 只有一条 2 分 1 评论的提交（2026-08-18），基本无讨论；X 上的主要传播来自联合创始人本人的发布推文；未检索到 r/LocalLLaMA 等垂直社区的独立讨论。

**风险与争议**:
- **stability**: CLI 仍在 0.0.x（0.0.11），已知安装与后端兼容缺陷会导致会话不可恢复地卡死（#42），不适合放进关键工作流。
- **bus_factor**: 两名核心贡献者占九成以上提交，无外部维护者接手迹象。
- **dependency**: 依赖自维护的 llama.cpp / llama-cpp-rs 分支，以及各 harness 的 OpenAI 兼容接口——上游任一侧改动都可能打断对接。
- **cost**: 卖点是省掉 token 费，但代价转移到硬件——推荐的模型档位受显存和带宽限制，低配机器上的实际可用性还没有独立评测支撑。

**技术备注**: CLI 用 TypeScript 发布在 npm（`@magnitudedev/cli`），推理侧基于 llama.cpp 生态的自维护分支，仓库主语言标记为 Python。Apache-2.0 许可。建仓 2026-06-12，支持 macOS / Linux，Windows 经 WSL。

## 如何理解今天的热度信号

今天最容易误读的是 skill 盘的集体上行。9 个 skill 项目里，ponytail、superpowers、mattpocock/skills、humanizer 四个的代码更新都停在两周到一个月前，却贡献了当日最大的几笔 star 增量。这类仓库的传播路径是"被推荐 → 被转发 → 上榜 → 被更多人看到"，与它是否在演进基本无关；用 star 日增判断一个 skill 包是否成熟，方向就错了。可用的替代判据有三个：最近一次实质提交改了什么、有没有版本化发布、issue 里有没有具体的使用场景而不只是"能不能加个 X"。

另一头，今天唯一的 NEW 项目 magnitude 只有 1,970 ⭐，在 24 万星级的邻居中间几乎看不见。但它的 issue 全部是硬件适配和后端对接的具体故障，这类讨论只会来自真的把它跑起来的人。**体量小、讨论具体**和**体量大、讨论稀薄**在同一张榜单上并存，正好说明 Trending 排名反映的是当日注意力分配，不是项目的采用深度。
