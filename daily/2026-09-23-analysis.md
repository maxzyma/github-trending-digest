## 首次上榜项目

### [google/ax](https://github.com/google/ax) — NEW ⭐ 7,674（+2,305）| Go | 信源：强

**它是什么**: Google 官方开源的"agent 版 Kubernetes"。你写一个 YAML 文件，声明"我要跑一个什么任务、它需要哪些代码仓库和工具、允许它访问哪些网站、用哪个模型"，ax 就负责把它塞进沙箱、把 Git 仓库和 MCP server 预装好、把出网流量锁到白名单里，然后调度起来。CLI 刻意做成 `kubectl` 的形状——`ax apply -f task.yaml`、`ax watch`、`ax ssh`，用过 Kubernetes 的人几乎不用学。它明确不是 ADK / LangGraph 那类"写 agent 逻辑"的框架，作者本人在 HN 澄清过：ax 是作业编排层。

**解决什么问题**: 一个编码 agent 跑起来可能占用几小时，大部分时间在等人回话；它会装依赖、改文件、调外部 API，还可能在循环里把钱烧光。传统办法要么一个会话一个常驻容器（贵、冷启动慢），要么杀掉会话（状态全丢）。ax 给出四个原语来声明式地处理这些：`Task`（隔离沙箱 + CPU/内存上限）、`Workspace`（预热好的仓库、MCP server、skill 包）、`Gateway`（出网白名单）、`Model`（平台自己用哪个 LLM，凭据从 K8s secret 取），外加 `ax suspend` / `ax resume` 把闲置 agent 冻起来。它跑在 `agent-substrate/substrate` 之上，后者提供亚秒级快照挂起恢复的沙箱执行能力。

**谁在用、怎么用**（来自 Issues/HN）:
- 场景 1: 批量跑编码任务——README 的示例直接是"克隆 golang/go 的某个分支，确保工具链能从源码构建"，并用 `ax ssh` 进沙箱看 agent 在干什么。
- 场景 2: 需要严格出网管控的场景——`Gateway` 把 agent 的出站流量锁到显式主机白名单，这是目前 issue 里被试用最多、也报错最多的能力（见下）。
- 场景 3: 可观测性接入，issue #13 有人在推 OpenTelemetry 集成；#362 的 roadmap 讨论说明有人在认真评估能不能上生产。

**社区怎么评价**:
- 正面: HN 首页第一，657 分 / 297 评论，讨论质量高。多位评论者把"google org 下、Apache-2.0、README 里没有 'not officially supported' 免责声明"当作可以认真对待的依据。
- 负面: HN 上两条批评反复出现——README 号称 ergonomics，实际要求你先有 Kubernetes 集群 + ko + 镜像仓库；以及"Google 已经弃过一次 agent 框架"的信任问题。X 上主要是作者本人和 Google 侧放大，独立开发者反馈少；Reddit 未找到可核实的一手帖。
- 健康度: 7,674 ⭐ / 36 subscribers（约 213:1，典型 launch 尖峰），32 open issues，359 forks。发版节奏正常：v0.2.0（7/21）→ v0.2.3（8/13）→ v0.3.0（9/20）。贡献者高度集中：rakyll 472 commits，第二名 56。

**风险与争议**:
- **stability**: `ax.io/v1alpha1`，README 顶部自己挂 WARNING 说稳定版前会有重大破坏性变更；launch 后 48 小时内提的 issue 质量很高但也很吓人——#345 Gateway 按 hostname 配白名单会连白名单本身都 block 掉所有 TLS，#346 命令退出后 Task 永远停在 `phase=Running`，#349 无 spec 的 Task 触发 controller nil-pointer panic，#372 默认快照桶硬编码成 Google 内部测试桶且 override 无效，#358 Makefile 写死 linux/amd64、arm64 集群跑不了。
- **bus_factor**: 单人主导（rakyll 472 commits vs 第二名 56），且项目当前暂停接收外部 PR。
- **dependency**: 强绑 `agent-substrate/substrate` 和 Kubernetes，不是能单机试一下的东西。
- **Google 弃坑史**: 这是 HN 上被提得最多的非技术顾虑，属于信任成本而非代码缺陷，但影响是否值得投入迁移。

**技术备注**: Go，Apache-2.0，google 官方 org。声明式 manifest（`ax.io/v1alpha1`），四原语 `Task` / `Workspace` / `Gateway` / `Model`，CLI 形态对齐 kubectl。部署需要 Kubernetes 集群、ko 和镜像仓库。

### [dream-num/univer](https://github.com/dream-num/univer) — NEW ⭐ 15,489（+255）| TypeScript | 信源：中

**它是什么**: 一套能嵌进你自己产品里的在线办公套件内核——表格、文档、幻灯片、画布、关系表、PDF 都在一个运行时里。它不是一个你打开就能用的网页版 Excel，而是给开发者嵌入用的 SDK：你的产品需要一块"能算公式、能和 Excel 互转、能多人协同"的表格区域，就把它装进去。它是 2022 年开源的老项目（Luckysheet 团队的后续作品），今天上榜的直接原因是重新定位：9 月 18 日 README 换成 "The Office Harness for AI Agents"，主打"让 AI agent 直接读写办公文档"。

**解决什么问题**: 过去在产品里做一块可用的电子表格，要么用商业控件（贵、封闭），要么自己实现公式引擎和 Excel 格式兼容（几乎做不完）。univer 把这部分做成开源内核，还提供 Node headless 模式——服务端不开浏览器也能读写工作簿、批量生成报表。新叙事这一层的主张是：agent 时代不需要给模型截图看表格，直接给它一套结构化的文档操作 API（经 univer-mcp 仓暴露成 MCP 工具）。

**谁在用、怎么用**（来自 Issues/GitHub 提交记录）:
- 场景 1: 嵌入式在线表格 / 文档——这是 issue 里最实在的一类，用户在反馈公式引擎、Excel 互转保真度、协同编辑这些真在用才会碰到的问题。
- 场景 2: 服务端批量处理——Node headless 读写工作簿、生成报表，不依赖前端环境。
- 场景 3: agent 调用——通过独立的 univer-mcp 仓（2025-09 就已存在）让 agent 执行表格操作。注意这条能力不在本仓里。

**社区怎么评价**:
- 正面: fork/star 比约 9%（1,383 / 15,489），对一个 SDK 型项目来说是很强的真实集成信号——fork 通常意味着有人在改造后接进自己的产品。贡献者 67 人，头部 jikkai 1,176 commits，前 6 人占大头但不是单人仓，提交每日多条。
- 负面: 外部讨论近乎为零。HN 只有两条自投帖（2024 年 Show HN 1 分 0 评论；2025 年 Univer Go 2 分 1 评论）；X 上是官方 @univerHQ 自宣为主，未见独立开发者实测；Reddit 搜索被 university / universe 完全污染，无有效讨论。issue 里的保真与一致性问题长期挂 `backlog 📚`：#6087 从 Excel 粘贴数字格式错乱、#5617 协同撤销后两端数据不一致、#4764 未注册公式插件即崩、#2177 字体切换无效（2024 年报至今未关）、#3108 整列公式缺失。
- 健康度: 15,489 ⭐ / 129 subscribers（约 120:1，但这是 2022 年老仓的长期沉淀，不能与新仓尖峰同等看待），138 open issues。发版节奏放缓：v0.25.1（2026-06-27）→ v0.25.2（2026-09-17）近 3 个月空档，README 的「1.0 Coming Soon」从 2026 年 5 月挂到现在未兑现。

**风险与争议**:
- **叙事与代码落差**: README 改成 agent 定位是 9 月 18 日的 commit #7705，距上榜只有 5 天；而本仓近 25 个 commit 全是 sheets/docs 常规功能（背景图、粘贴、格式刷），无一条 agent / AI 代码。agent 能力实际散在 univer-mcp 仓与 Pro 层。想按新定位选型的读者需要先确认能力到底在哪个仓。
- **dependency**: open-core 结构——协同编辑、服务端、企业集成属于闭源的 `@univerjs-pro/*`，README 明写 Pro「独立开发」。你真正想要的协同能力可能不在开源包里。
- **stability**: 协同一致性（#5617）与 Excel 保真（#6087、#3108）的 bug 未清，1.0 延期近半年。

**技术备注**: TypeScript，Apache-2.0（不是 AGPL）。浏览器端 + Node headless 双模式；agent 侧能力经独立的 univer-mcp 仓暴露；商业能力在闭源 `@univerjs-pro/*`。

### [superdesigndev/treg](https://github.com/superdesigndev/treg) — NEW ⭐ 2,248（+230）| Python | 信源：中

**它是什么**: 给 AI agent 用的"工具总代理"。用它的类比：OpenRouter 让你一个 token 调所有模型，treg 想让你一个 token 调所有工具——60 多家厂商、约 3,000 个 API 端点（SEO 外链数据、社媒趋势、人企信息富化、广告、爬虫、图像视频生成），按次计费，低到一分钱，**你不需要去每家注册账号**，因为 treg 自己持有那些订阅。第二半功能是团队密钥托管：把你自己的 API key、OAuth 连接、厂商 CLI、SKILL.md 注册进去，队友的 agent 能调用，但明文凭据不离开服务端。托管站是 treg.to，也可以自托管。

**解决什么问题**: agent 要做真实工作时，需要的数据往往锁在没人愿意为单次调用买的订阅后面——Semrush 每月 139 美元、Moz 99 美元、Crunchbase 99 美元、Apollo 每席 59 美元——或者干脆没有公开 API（邀请制、合作伙伴制）。treg 的主张是"问任务，不问工具"：你不需要知道哪家卖外链数据，搜索你想做的事、看价格、直接调。另一半解决的是团队协作中的凭据问题：密钥在服务端注入，调用方永远拿不到 key。

**谁在用、怎么用**（来自 Issues/PR）:
- 场景 1: GTM / 增长自动化——注册流反欺诈、线索信息富化、意向分级，这是作者自己主推的用法。
- 场景 2: 把自家 API 接进目录——issue #308 Orshot 要求新增创意生成类目、#143 请求上架第三方目录，说明有厂商主动来对接。
- 场景 3: 多源路由——#261 的 RFC 讨论人企身份解析与分页搜索的路由策略，说明有人真在跑多供应商 waterfall。

**社区怎么评价**:
- 正面: 两个月内已合并 / 关闭 544 个 PR，其中大量是外部开发者各自提交的 catalog provider（BeLazy167、rishimohan、ironman5366、Anil-matcha、pkpio 等）。贡献者分布是核心两三人（JayZeeDesign 1,073、stonexer 460、unclecode 272）加一条社区长尾。219 forks 多为提 PR 的工作副本。
- 负面: 外部独立讨论缺席——HN 无讨论、Reddit 无讨论，X 上基本是作者 Jason Zhou（@jasonzhou1993，同一个 org 还做 superdesign）自推，最近主推 "Jev + Treg" GTM 自动化、声称三条工作流省 8,000 美元/月，未见第三方实测。issue 回复率是明显短板：#353、#549 两条安装失败（`ERR_PNPM_GIT_RESOLVE_FAILED`、打包分发不完整）至今 0 回复。
- 健康度: 2,248 ⭐ / 7 subscribers（约 321:1，全榜最高），仓龄仅 2 个月（2026-07-15 创建）。需要注意的口径问题：GitHub 显示的 72 个 "open issues" 里 66 个其实是 PR，**真正的 issue 只有 6 个**——按 open issues 数量判断这个项目的活跃度会得出相反结论。

**风险与争议**:
- **compliance**: 商业模式是"我持有订阅、按次转卖调用"，直接触碰各家供应商 ToS 的转售条款。License 也不是标准开源：Apache-2.0 加一条附加限制——禁止用它对第三方提供托管 / 托管 / 嵌入式服务（即禁止做竞品 SaaS），需书面授权；贡献者还需同意作者可商业化其贡献。GitHub 识别为 NOASSERTION。
- **dependency**: 60+ 上游 API 任何一家变更接口或封掉 treg 的账号，对应品类即断供。
- **privacy**: 团队密钥与 OAuth 凭据入库由服务端注入，README 自承 at-rest 密钥管理加固还在 roadmap。
- **vanity**: 321:1 比值 + HN / Reddit 零讨论 + 增长节奏与作者 X / Discord 推广同步，仓内还带一个 `marketing/` 目录，内含程序化 SEO 的选题与投放计划（对标 Pipedream 的关键词矩阵），最近一次合并的 PR 标题就是 `seo/consolidated-2026-09-23`。**但这不等于空心项目**：544 个 PR、外部厂商主动对接、具体的路由 RFC 都是反证。准确的说法是"传播由作者影响力与 SEO 驱动，技术侧也有真实社区活动"，两件事同时成立。
- **bus_factor**: 核心两三人，长尾贡献集中在目录条目而非核心代码。

**技术备注**: Python（CLI + 服务端），tools-registry License（Apache-2.0 + 托管服务限制）。代理层只做转发不建模上游，凭据服务端注入；托管站 treg.to 用预付余额计费，新验证团队送 1 美元额度，也支持自托管。
