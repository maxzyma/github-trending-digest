### [antirez/ds4](https://github.com/antirez/ds4) — NEW ⭐ 20,032（+139）| C | 信源：强

**它是什么**: Redis 作者 Salvatore Sanfilippo（antirez）用纯 C 手写的本地大模型推理引擎。它有一个反直觉的设计选择：**只跑 DeepSeek V4 Flash/PRO 和 GLM 5.2 这几个模型，不做通用工具**。目标场景是让 128GB 的 MacBook、DGX Spark、Strix Halo 这类个人高配机器直接在本地跑 284B 参数的 MoE 模型，内存不够时用 SSD 流式加载权重。

**解决什么问题**: 以前想在本地跑大模型，基本只有 llama.cpp / Ollama 这类通用 runtime 一条路。通用 runtime 要支持几百种模型架构，结果是"每个模型都只能做到还行"。ds4 的赌注是：把模型加载、prompt 模板渲染、tool call 协议、KV cache 布局、HTTP server、内建 coding agent 全部围绕少数几个模型一起端到端调优，能在同样硬件上换到明显更好的吞吐和更少的踩坑。README 里也坦白披露了另一件事：代码由 GPT 5.5/5.6 + Claude Fable 大幅辅助编写，人负责设计与调试，并大段致谢 llama.cpp/GGML 并保留其版权声明。

**谁在用、怎么用**（来自 Issues/HN/独立评测）:
- 场景 1: **消费级 Mac 本地跑 coding agent**。多篇独立评测与 r/LocalLLaMA 的引述显示 M3 Max 96GB 可跑 q2-imatrix 量化到 250k context；低于 96GB 内存目前没有可行路径。
- 场景 2: **AMD / ROCm 平台自组社区**。issue #16 有 251 条评论，Strix Halo 与 ROCm 用户自发在里面协作调参，说明真的有人在多平台上编译部署，而不只是 star。
- 场景 3: **老卡服务器改造成内部 LLM 服务**。8×L40S 配置报出 120 t/s 聚合生成、2000 t/s prefill；另有 RTX PRO 6000 单卡 Q2 达 43 t/s、双 Mac 走 RDMA 做张量并行的用法。
- 场景 4: **接进现成 agent 客户端**。issue #500 是把 ds4 挂到 Claude Code 扩展上跑本地模型；issue #389（130 条评论）是社区自发跑 SWE-Bench Verified 来验证 q2-imatrix 的质量损失。

**社区怎么评价**:
- 正面: HN 两个主帖分别 499 分 / 159 评论与 440 分 / 190 评论，热度是真实讨论撑起来的；X 上由 antirez 本人 5 月 7 日发布并致谢 Gerganov，靠口碑而非投放扩散。
- 负面: HN 上最集中的抱怨是 **prefill 太慢**——"31 t/s 的 prefill 在 agent 场景基本不可用，10k context 要等 5 分钟"；早期 tool call 不稳定，出现过"说改完文件其实没改"；96GB 内存起步的门槛把绝大多数人挡在外面。issue #635、#468 在催新模型版本（0731、DSpark）与 GLM 5.2 的适配滞后。
- 健康度: stars/subscribers = 20,032/160 ≈ 125:1，对一个高传播的消费级项目属正常区间；1,776 forks 说明有真实编译使用者；385 open issues 是活跃技术讨论而非堆积；仓龄仅约 3 个月（2026-05-06 建仓），2026-08-01 仍有推送。贡献者高度集中：antirez 251 commits，第二名仅 7 commits。

**风险与争议**:
- **bus_factor**: antirez 一人占约 90% 提交，无第二维护者，项目命运与作者个人投入完全绑定。
- **stability**: 作者自称 beta，CLI 与参数快速变动，内建 agent 模式明确标注为实验性。
- **dependency**: 只跟随少数模型，上游 DeepSeek 一发新版就需要等适配（#635 正是这个诉求），README 也预告过"模型换代可能移除支持"。
- **cost**: 96GB+ 内存是硬门槛，不是普适工具；想复现评测里的数字需要相当量级的硬件投入。
- **AI 生成代码争议**: README 主动披露主体代码由 LLM 辅助生成，HN 上被拿来与 llama.cpp 拒收 AI 代码的政策直接对比，是该项目讨论中最有分歧的一点。

**技术备注**: 纯 C，MIT，支持 Metal / CUDA / ROCm 三套后端，附带 HTTP server 与内建 coding agent；内存不足时走 SSD 流式加载权重。

### [esengine/DeepSeek-Reasonix](https://github.com/esengine/DeepSeek-Reasonix) — NEW ⭐ 29,146（+333）| Go | 信源：强

**它是什么**: 一个跑在终端里的 AI 编程助手，专门为 DeepSeek 模型定制。单个 Go 静态二进制，配置走 `reasonix.toml`，另有桌面端与 VS Code 扩展。

**解决什么问题**: 用 AI 写代码时，每一轮对话都要把之前的全部上下文重新发一遍，长会话的费用会滚雪球。DeepSeek 提供了 prefix cache（命中的前缀按折扣计费），但只要历史里有任何字节发生变化，缓存就会失效。Reasonix 的全部工程重心就是这一件事：把对话历史做成**只追加、字节稳定**的结构，让缓存尽可能全部命中。社区实测过单日 99.82% 命中率、12 美元 vs 不缓存 61 美元的对照。因此它的使用姿势也变了——不是"用完就关"，而是"开着别关，让它长期跑"。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: **长时间无人值守的重构与 TODO 批处理**。这是"leave it running"定位的直接落点，用户把大批机械改动扔给它连续跑。
- 场景 2: **双模型分工**。HN 与第三方指南里反复出现同一套流程：用 Claude Code / Codex 写规格和方案，交 DeepSeek + Reasonix 做实施，理由是实施环节的 token 消耗最大、最吃成本。
- 场景 3: **并行多 agent 代码审查**。靠单二进制 + 稳定缓存的组合同时开多个实例。
- 场景 4: 官方渠道背书——**DeepSeek 官方 API 文档收录了 Reasonix 的集成页**，这是它合法性最硬的一条证据。

**社区怎么评价**:
- 正面: HN 主帖 729 分 / 288 条评论，另有数十条跨帖的自发提及；多个独立账号长期把它当日常主力，反复出现"实际免费""silly cheap"的说法。X 上 DeepSeek 圈头部账号 Teortaxes 背书并直接 @ DeepSeek 员工。
- 负面: 高速迭代带来的回归很集中。issue #6078 标题就是"请不要以毁灭用户体验为代价瞎搞安全性"——Auto 模式仍对写操作弹窗、YOLO 模式有 session 冲突；#7173 报 1.19.1 强制进安全模式且无法退出；#5831 编辑工具反复失败、模型写不进文件；#5909 报事件循环卡顿 3574ms；#2793 要求回退 UI。HN 上也有人质疑"跟直接 OpenCode + DeepSeek API 有什么区别"，还有一人怀疑 astroturfing。
- 健康度: stars/subscribers = 29,146/76 ≈ **384:1，是全榜最极端的比值**——但这是它唯一的异常指标。1,391 个"open issues"里含 234 个 open PR，真实 open issue 1,157；对面是**已关闭 issue 2,000、已合并 PR 2,816**；最近 100 个 issue 来自 60 个不同作者；30 天内 100+ commits，v1.19.0 到 1.19.3 三天连发。issue 普遍带版本号、截图、复现步骤和交叉引用（如 #6078 引用 #5996），标签体系完整（bug 44 / windows 36 / desktop 18 / crash 9）。这是高吞吐维护，不是堆积，也不是 spam。贡献者集中度偏高：SivanCola 2,311 commits、esengine 518，第三名仅 121。仓龄 3.5 个月（2026-04-21 建仓）。

**风险与争议**:
- **bus_factor**: 提交高度集中在单一核心贡献者，第三名与前两名差两个数量级。
- **stability**: 日更节奏持续引入回归，安全模式、编辑工具、更新器是故障最集中的三处（#7173、#5831、#5909）。
- **dependency**: 全部工程价值建立在 DeepSeek 的 prefix cache 具体实现上；**DeepSeek 官方已宣布将发布自己的 Harness**，一旦官方方案覆盖同一场景，Reasonix 的差异化空间会被直接压缩。
- **cost**: 省钱是核心卖点，但完全依赖缓存命中——长会话被打断或历史被改写时，成本会回到无缓存量级，实际账单波动比宣传数字大。

**技术备注**: Go 单静态二进制，MIT，`reasonix.toml` 配置，附桌面端与 VS Code 扩展；核心机制是只追加、字节稳定的会话历史序列化。

### [HarbourMasters/Lighthouse](https://github.com/HarbourMasters/Lighthouse) — NEW ⭐ 227（+65）| C | 信源：强

**它是什么**: 1998 年 N64 游戏《Banjo-Kazooie》（班卓熊大冒险）的**原生 PC 移植版**——注意，不是模拟器。社区先把原版游戏反编译成可读的 C 代码，Lighthouse 在此基础上重建出能在 Windows / Linux / macOS 上原生编译运行的程序。HarbourMasters 就是做《塞尔达传说：时之笛》PC 移植（Ship of Harkinian）的那个团队，Lighthouse 是他们在马里奥 64、时之笛、姆吉拉之后的新作。

**解决什么问题**: 在模拟器上玩老游戏，你受限于模拟器能做什么；原生移植后能做 N64 上不可能的事——高分辨率、帧插值、DX11 / OpenGL / Metal 多后端、内建手柄映射器、随机化器（Randomizer）、"Anchor" 在线联机合作、ROM hack 与自定义素材加载、把 PAL / 日版当语言包用的多语言支持。仓库本身**不含任何游戏资产**：玩家必须自备正版 ROM（README 列出 4 个 SHA-1 校验和），首次运行时从 ROM 抽取资源生成 `bk.o2r`。

**为什么今天上榜**: 2026-07-31 发布 v1.0.0（"Split Rock Alfa"），08-01 跟进 1.0.1（"Split Rock Bravo"）。这是典型的**发版驱动热度**，长期低调开发 20 个月后才发 1.0，不是空心传播。

**谁在用、怎么用**（来自 Issues / GBAtemp / ResetEra / GameBanana）:
- 场景 1: **PC 上重玩并加料**。8BitDo N64 手柄重映射后被评价为"flawless"；随机化器与 ROM hack 支持是社区最主要的新玩法入口。
- 场景 2: **联机合作**。玩家反馈需要开启 share items，否则两人抢到不同的 Mumbo Token 会导致无法 100% 完成。
- 场景 3: **下游二次移植**。已出现基于 1.0.1 的 Switch 移植 **Docklight**。
- 场景 4: **与竞品对比**是社区最大的讨论话题——Mr Wiseguy 的 BanjoRecomp 走静态重编译路线，有用户报告老机器跑不动 Recomp 但 Lighthouse "works perfectly"。

**社区怎么评价**:
- 正面: 发布帖在 GBAtemp、ResetEra、Time Extension、GameBanana 均有独立讨论，评价偏正面，重点是可玩性与手柄支持。
- 负面: 1.0.0 发布即暴露问题——#305 Windows 游戏中音频杂音、#313 FP/CCW 雪花粒子特效损坏、#321 随机化器在 Clanker's Cavern 崩溃、#341 romhack "New Horizons" 无法通关、#344 Furnace Fun 按键绑定错误、#318 Fedora 编译修复。也有人吐槽"高清下画面反而显丑"。
- 健康度: 227 stars / 10 subscribers ≈ **22.8:1，是全榜最低的比值**——面向玩家的应用型项目本该长这样。34 个 open issues 全是具体 bug 报告；12+ 贡献者（banjo-decomp 445 / Caladius 420 / JeodC 133 / Malkierian 69），不是单人项目；发版前后 PR #290–#301 密集，提交活跃到今天。
- **HN 无讨论**: 唯一相关帖是竞品 BanjoRecomp（2026-01，2 分 0 评论），Ship of Harkinian 的历史帖也全在 1–4 分。这不是空心信号——HN 根本不是这个社区的场子，讨论主战场在 GBAtemp / ResetEra / Time Extension / GameBanana。这是"信源强度要看对场子"的好例子。

**风险与争议**:
- **compliance**: 这是主要风险。任天堂对粉丝项目历来强硬。项目用"不分发资产 + 要求自备 ROM + CC0 许可 + README 明示不支持盗版"来降低暴露面，但从 ROM 抽取资产的合法性各司法辖区不一，且从未被判例检验。历史模式是任天堂针对**含资产的预编译二进制**发 DMCA、纯源码项目暂时存活；Lighthouse 恰好发布了预编译 Release（不含资产）。目前未发现针对本仓库的实际 DMCA。
- **stability**: 1.0.0 即暴露音频、特效与崩溃问题；romhack 支持自述"大多未完整测试"。
- **dependency**: 依赖上游 banjo decomp 项目与 libultraship / Kenix3 的持续维护。
- **bus_factor**: 中低——主导开发集中在 Malkierian / Caladius / JeodC 三人。

**技术备注**: C，CC0-1.0，DX11 / OpenGL / Metal 多渲染后端，跨 Windows / Linux / macOS 编译；资产在首次运行时从用户自备 ROM 抽取为 `bk.o2r`。

## 如何理解今天的热度信号

今天是一个适合校准方法的日子，因为三个 NEW 的 grounding 都很扎实，反而把"哪些指标真的有判断力"暴露得很清楚。

**第一，stars/subscribers 比值单独不构成 vanity 判据，今天有教科书式的反例。** Reasonix 的比值是 384:1，全榜最极端；但它同时有 2,000 个已关闭 issue、2,816 个已合并 PR、最近 100 个 issue 来自 60 个独立作者、30 天 100+ commits、HN 729 分主帖，以及 DeepSeek 官方文档收录。这个组合下，384:1 的合理解释是"1,391 条 issue 的通知量把 watch 意愿压掉了"，而不是"star 是刷的"。反过来，Lighthouse 的比值只有 22.8:1（全榜最低），因为它是面向玩家的应用，装了就玩、不需要 watch。**比值反映的是项目类型和通知负担，需要和 issue/PR 吞吐、外部信源一起看才有意义。**

**第二，"HN 无讨论"要先问"这个项目的场子在哪里"。** Lighthouse 在 HN 上几乎零讨论，但在 GBAtemp、ResetEra、Time Extension、GameBanana 都有独立发布帖，还催生了下游 Switch 移植 Docklight。这属于信源强，不属于信源弱。与之对比，k-skill 的 HN/Reddit 双缺席之所以仍是缺口，是因为目前也没有等价的韩语侧具名独立信源可以替代。**判断 grounding 要按目标受众所在的社区去找，而不是默认 HN 缺席就等于空心。**

**第三，今天真正需要谨慎的不是 star 数，而是 star 与代码活动的脱节。** 三个例子：AI-For-Beginners 拿到全榜最高的 trending 日增量（+2,629），push 停在 12 天前；build-your-own-x 排第五，push 停在 07-14；Agent-Reach 一个半月涨了 3 万多 star，push 已停 9 天。这三者都不是坏项目，但它们说明同一件事——**trending 的日增量衡量的是当天的注意力，与项目当下的维护强度是两条独立曲线**。把 `pushed_at` 和 star 曲线并排看，这一层误读就消失了。

**第四，今天最实质的风险集中在"专用化"本身。** ds4 与 Reasonix 的技术优势直接来自深度绑定 DeepSeek——ds4 明确说模型换代可能移除支持，Reasonix 的全部价值建立在对方的 prefix cache 实现上，而 DeepSeek 官方 Harness 已在路上。这是 `dependency` 风险的典型形态：**不是依赖一个会挂掉的免费 API，而是依赖一个供应商既定义规则、也随时可以自己进场的位置**。想在生产里用这两个项目的团队，应该把"官方方案落地后怎么迁"当成前置问题，而不是事后再想。
