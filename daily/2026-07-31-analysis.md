**主线二：agent 产出多了之后，"人在回路审查"开始有专门工具了。** 今日唯一的工程型 NEW 项目 [tuicr](https://github.com/agavra/tuicr)（1,878 stars，+190，Rust）不是又一个 agent，而是审 agent 产出的工具：把 uncommitted diff、commit range 或 GitHub PR 用 vim 键位在终端里当 PR 审，逐行留评论，然后既能推成真实的 GitHub/GitLab review，也能导出结构化 markdown 直接喂回 coding agent。它的两个热门 issue 直接暴露了真实需求方向——#286 要求加 agent review CLI 与 review API（16 条评论），#221 要求加 MCP channel 直连 Claude Code（9 条评论）。配合排名第 4 的 openwork（Claude Cowork 开源替代，今日 +915 领涨全榜），今天这条线的含义很清楚：过去一年 trending 的主角是"让 agent 写更多代码"，现在开始出现"人怎么在可控成本内看完 agent 写的代码"这一层工具。对做 agent 工程的读者，这比榜首的语音项目更值得点开。

## NEW 项目分析

### [agavra/tuicr](https://github.com/agavra/tuicr) — NEW ⭐ 1,878（+190）| Rust | 信源：中

**它是什么**: 一个跑在终端里的代码审查界面。你让 AI agent 改完一堆代码，通常只能用 `git diff` 一屏屏翻，或者先推上 GitHub 再在网页上审。tuicr 把 GitHub 网页版 PR 的审查体验搬进终端：连续滚动的 diff、可展开的折叠上下文、vim 键位导航（j/k、Ctrl-d/u、gG、`/` 搜索）、在某一行或某几行上直接留评论。审完可以选三种出口——推成真实 GitHub/GitLab review、复制成 markdown、或输出到 stdout。作者念作 "tweaker"。

**解决什么问题**: 在 agent 大量生成代码的工作流里，瓶颈从"写"移到了"看"。以前的两条路都不顺：`git diff` 没有评论和进度记忆，翻到第 8 个文件就忘了前面看到什么；推上 GitHub 走网页审查则要为每次 agent 迭代开一个 PR，太重。tuicr 提供第三条路——本地就能按 PR 的粒度审，审查进度（哪些文件/hunk 已看过）跨会话持久化，评论可以一次性打包成结构化反馈交回 agent 修。它同时支持 git、jj 和 mercurial，可以审未提交改动、commit range，或直接 `tuicr pr 125` 拉远端 PR。

**谁在用、怎么用**（来自 Issues/HN/评测）:
- **审 AI agent 的改动，评论导回 agent**：项目自身提供 Claude Code skill，在 tmux 分屏里打开 tuicr，审完把评论喂回 Claude Code。issue #221（9 条评论）进一步要求做 MCP channel，让 tuicr 与 Claude Code 直连而不必经剪贴板。
- **把审查能力做成 agent 可调用的接口**：issue #286（16 条评论）要求加 agent review CLI 和 review API，即让 agent 自己发起/读取 review，而不只是人审 agent。
- **审大型 PR 与非 GitHub 托管**：issue #475 处理超过 300 个改动文件的 PR，#498（6 条评论）要求 Bitbucket 支持，#288（6 条评论）针对大 diff 做流式高亮与延迟优化——这几条说明有人拿它审真实的大变更，不只是玩具 demo。

**社区怎么评价**:
- 正面: 定位清楚、装法齐全（install.sh / brew / cargo / mise / nix），发版节奏密集（v0.18.0 → v0.19.0 → v0.19.1 在 6 月下旬到 7 月中的三周内），Linux 工具站 LinuxLinks 已收录评测，同时以 Rust crate 形式暴露库 API（`ReviewStore` 可列会话、加行级/区间评论）。
- 负面: 90 个开放 issue 里相当一部分是大 diff 性能与平台覆盖缺口；Bitbucket 等托管尚未支持。
- 健康度: 1,878 stars / 11 subscribers（171:1，比值高但绝对量小，参考价值有限）；161 forks；90 open issues；贡献者结构是今天最好的一点——作者 agavra 128 次提交，但 martintrojer(15)、ptoussai(13)、thiblahute(10)、N4M3Z(8)、natebrennand(8)、abhinav(7) 等 8 位以上外部贡献者已有实质提交，不是单人仓；`pushed_at` 为昨日（2026-07-30），在活跃开发中。

**风险与争议**:
- **stability**: v0.19.x，仍在 0.x 阶段；大 PR（>300 文件）与大 diff 高亮性能是已知在修问题（#475、#288），不宜当作稳定生产工具。
- **vanity**: HN 侧几乎没有形成讨论——1 月两次投稿（"Show HN: Tuicr – Review Claude Code diffs like a PR from your terminal"、"Tuicr – Terminal UI for Code Review"）与 6 月一次投稿均为 2–3 分、0–1 评论，Reddit 未检索到成规模的讨论帖，可见曝光主要来自 GitHub Trending 与作者 LinkedIn 投放，而非社区自发扩散。
- **bus_factor**: 作者一人占约 60% 提交（128/约 210），路线图由其单点决定；外部贡献者虽多但都是零散提交。

**技术备注**: Rust，MIT，crates.io / docs.rs 已发布（tuicr 0.19.1）。支持 git / jj / mercurial 三种 VCS，GitHub 与 GitLab 两种 review 出口，官网 tuicr.dev。

### [WhiskeySockets/Baileys](https://github.com/WhiskeySockets/Baileys) — NEW ⭐ 10,444（+19）| JavaScript | 信源：强

**它是什么**: 一个用 TypeScript/JavaScript 直接说 WhatsApp Web 协议的库。它不通过浏览器，也不走 WhatsApp 官方的 Business API，而是用 WebSocket 直连 WhatsApp 的服务端，把你的手机号以"已链接设备"的身份接进去，然后你就能在代码里收发消息、读群组、处理媒体文件。

**解决什么问题**: 想让程序收发 WhatsApp 消息，官方路径是 WhatsApp Business Platform——要注册、要审核、按条计费，且自 2026 年 1 月起 Meta 明确禁止开放式 AI 助手类机器人接入，只允许下单、FAQ、留资、订单状态这类结构化机器人。另一条常见路径 whatsapp-web.js 靠 Puppeteer 驱动真实浏览器，每个会话背一个 Chromium，资源开销大。Baileys 两个都绕开：无浏览器、无官方审核，一个 Node 进程就能跑多会话，代价是走在 WhatsApp 服务条款之外。

**谁在用、怎么用**（来自 Issues/HN/外部资料）:
- **给 WhatsApp 造 AI agent 框架的底座**：HN 2026-03-08 的 "Show HN: Wa-agent – Framework for building AI agents on WhatsApp" 明确写了 "uses Baileys under the hood for WhatsApp"；HN 另一条 2026-03-04 讨论里也有开发者提到 Baileys 是做 WhatsApp 集成时被推荐的 SDK。这条线正好承接 Meta 封杀开放式 AI 机器人后的需求外溢。
- **企业机器人与客服自动化**：issue #2710 是社区提交的 "feat(framework): implement enterprise bot framework"，说明有人在它之上做企业级机器人分层。
- **协议侧的持续对抗与补齐**：#2672（88 条评论，全仓最热）跟踪 WhatsApp 的 Passkey/"Continue on WhatsApp Web" 变更对链接流程的影响；#1769（44 条评论）是长期存在的加解密疑难集合帖（"Bad Mac"/"Failed to decrypt"/"No session"）；#2067 在推进 libsignal 的 wasm 化；#1561（68 条评论）要求贴纸包支持。这些 issue 的形态本身就是"有大量真实生产部署在踩坑"的证据。

**社区怎么评价**:
- 正面: 事实上的非官方 WhatsApp 集成标准，文档站 baileys.wiki 齐全，下游生态（wa-agent、各类 bot 框架、WAHA/Evolution 之类的服务化封装）都以它为底座。
- 负面: 7.0.0 引入多处破坏性变更；auth state 管理不当会陷入重连循环；官方明确不推荐 Bun 运行时（在 Bun 上连接与消息处理不稳定，Node.js 下无此问题）；封号问题反复出现在 issue 区。
- 健康度: 10,444 stars / 209 subscribers（50:1，今日全榜最健康）；3,254 forks；337 open issues；贡献者高度集中——adiwajshing 1,166 次提交、purpshell 317 次，第三名 jlucaso1 仅 58 次；`pushed_at` 2026-07-29，维护活跃。

**风险与争议**:
- **compliance**: 违反 WhatsApp 服务条款。项目自述不使用 WhatsApp Business API、与 WhatsApp 无关联、不背书；维护者明确反对垃圾消息、跟踪软件与批量自动发送。第三方分析称此类逆向 WhatsApp Web 的方案通常在 2–8 周内被自动化检测识别（该数据来自有商业倾向的 Cloud API 服务商博客，需打折看），也有人指出封禁没有可预测规律——可能几个月无事，也可能一周内被封。
- **dependency**: 依赖 WhatsApp Web 的私有协议，上游任何认证/加密变更都可能直接打断服务，#2672 的 Passkey 问题就是现例。
- **bus_factor**: 两位维护者占绝大多数提交（1,166 + 317 vs 第三名 58），协议对抗又是高强度持续工作，维护者变动风险直接传导给下游。
- **供应链风险**: 该生态曾出现针对 Baileys 变体包的供应链攻击（一个下游项目记录了 2025 年 9 月一起涉及约 5.6 万次下载的事件），选用第三方 fork 或"anti-ban 中间件"时需额外审计。

**技术备注**: JavaScript/TypeScript，MIT，WebSocket 直连（无 Puppeteer/Selenium），通过 Linked Devices 接入个人或商业号，文档 baileys.wiki，当前主版本 7.x。

## 如何理解今天的热度信号

今天这张榜适合用来练一个判断动作：**先看 `pushed_at`，再看比值，最后才看 stars**。

- `pushed_at` 在最近一两天的（tuicr、Baileys、openwork、chrome-devtools-mcp、speech-to-speech、editor、last30days-skill、ansible、PowerToys、aspnetcore）说明还有人在改；停在 2025-01 的 awesome-systematic-trading 无论涨多少星，都不该被读成"这个方向正在被建设"。
- stars/subscribers 比值只在**同量级项目之间**有意义。PowerToys 112:1、ansible 37:1 是超大仓的正常结构；同为短龄仓的 openwork 250:1 与 ECC 193:1 才值得对照着看。tuicr 的 171:1 因为绝对量太小（1,878/11），本身几乎不携带信息，应改看它的贡献者结构与发版节奏——那两项恰好是今天最健康的。
- 今日 star 增量前五全部是仓龄 2 年以内或话题驱动型项目，后六名全部是十年量级的老项目且增量不足三位数。这不是"老项目衰落"，而是 Trending 榜同时叠加了两套不同的机制：传播扩散与算法回流。把它们放在同一个排序里比较大小，本身就是误读的起点。
