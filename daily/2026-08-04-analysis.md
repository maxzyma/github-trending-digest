## 首次上榜项目

### [firecrawl/pdf-inspector](https://github.com/firecrawl/pdf-inspector) — NEW ⭐ 8,364（+1,699）| Rust | 信源：中

**它是什么**: 一个判断「这份 PDF 到底是不是扫描件」的 Rust 库。给它一个 PDF，它在几十毫秒内告诉你：这是原生文本型、纯扫描图片型、图文混合，还是介于之间；并按页给出「这页需不需要 OCR」的建议。顺带它也能把文本型 PDF 抽成带位置信息的文字，或者直接转成干净的 Markdown（标题、列表、表格、代码块、多栏阅读顺序都识别）。由 Firecrawl 团队开发，除 Rust 外还提供 Python、Node.js 和浏览器 WebAssembly 三套绑定。

**解决什么问题**: 在这个库之前，把 PDF 灌进 RAG 或 agent 管道的常见做法是「一律送 OCR」——因为你事先不知道哪份是扫描件。代价是 GPU OCR 服务的钱和延迟，而按项目自己的统计，约 54% 的 PDF 本来就是原生文本、完全不需要 OCR。用了之后的差别是多一道 10-50ms 的本地前置判断：文本型直接本地抽取（200ms 内），只把真正的扫描件交给 OCR。对批量处理文档的团队，这是一次纯粹的成本和延迟削减，而不是新增能力。附带收益是敏感文档（合同、财务、医疗）可以走 WASM 在浏览器内解析，不出本机。

**谁在用、怎么用**（来自 Issues/HN/X）:
- RAG / agent 管道的 OCR 路由前置，是项目自己主推也是 issue 里出现最多的用法：先 `classify_pdf` 再决定是否调 OCR。
- Python 数据处理管道：issue #3（10 条评论）里社区成员自建 PyO3 绑定并把 PyPI 包归属移交给项目，另有 @rth 独立跑基准后评价速度与 markdown 质量的比值不错——这是本项目最实在的一条外部使用证据。
- 部署侧诉求集中在容器化：#216 要求 Alpine / ARM64 支持。
- 浏览器内解析（WASM）用于不能上云的合同与病历类文档。

**社区怎么评价**:
- 正面: 公开 benchmark 可复现（opendataloader-bench 200 份语料，overall 0.875 / 表格 TEDS 0.814 / 200 份 0.470s，均为该对比中最好），且 #191 里 LlamaIndex 的 logan-markewich 质疑 README 中对 LiteParse 的对比数据后，维护者重跑并公开了 benchmark 代码与分支——处理质疑的方式透明。中文乱码问题 #105 报出后在 #106 快速修复。
- 负面: 正确性缺陷相当密集且都还开着——#211 文本型 PDF 抽出逐字符拆散的结果（「J O H N D O E」）、#238 带删除线／修订标记的 PDF 被误判成表格（附真实马里兰州法案 PDF）、#228 缺少 xref 恢复能力，pypdf/pdfium 能修的文件它直接报 Invalid PDF、#227 与 #231 指出 `extract_pages_markdown` 的 `needs_ocr` 结论与 `classify_pdf` 自相矛盾、#219 双栏页按光栅顺序输出导致行交错、#5 有 0.1% 文档处理极慢。
- 健康度: stars 8,364 / subscribers 21 ≈ 398:1，属极端值；forks 552；创建于 2026-02-06，仓龄约 6 个月。`open_issues_count` 61 实际是 25 个 issue + 36 个开放 PR。近 100 次提交中 abimaelmartell 占 98 次，另两人各 1 次。HN 两帖均为 5 分、评论 0-1 条；Reddit 两轮检索（含去掉 `site:` 的宽泛查询）无相关讨论。

**风险与争议**:
- **vanity**: 398:1 的 stars/subscribers、HN 与 Reddit 近零讨论，热度传播链条几乎完全落在 Firecrawl 官方号与创始人的 Fire-PDF / PDF Parser v2 / `/parse` 发文序列上，独立开发者反馈稀少。
- **bus_factor**: 98/100 次近期提交来自单一维护者，36 个 PR 积压，消化速度明显落后于提交速度。
- **stability**: 维护者自述处于「very experimental phase，API 可能变化」，且乱码抽取、xref 恢复缺失、`needs_ocr` 自相矛盾、双栏阅读顺序这些核心正确性问题仍未关闭——不适合直接放进不可人工复核的生产链路。
- **可疑贡献模式**: issue/PR 中有相当比例来自少数新账号（al-ashalash 6 条、knealfortegra 3 条、MADENIYOU 多个 PR），格式高度模板化（RED/GREEN、附 commit hash 证据），更像 agent 批量产出或悬赏驱动，而非自然用户报障；读 issue 数量时需要打折。

**技术备注**: Rust 2021，当前 crates.io 版本 0.1.7（README benchmark 用 0.2.6），MIT license。核心解析只依赖 `lopdf`，无 ML 模型、无外部服务；文档解析一次后在分类与抽取之间共享，避免重复 I/O。绑定通过 PyO3（Python，abi3-py38）、napi（Node.js）、wasm（浏览器与 Web Worker，内嵌 CMap）三路提供。字体侧支持 Type0/Identity-H 的 ToUnicode CMap 解码及 UTF-16BE / UTF-8 / Latin-1；表格检测双模式（PDF 绘图指令的矩形检测 + 文本对齐启发式）。

### [livekit/agents](https://github.com/livekit/agents) — NEW ⭐ 12,014（+148）| Python | 信源：强

**它是什么**: 一个搭建「能实时对话的语音 AI」的框架。你要做的是那种打过去就能说话、能被打断、听得懂就立刻回答的语音助手——比如自动接电话的客服、AI 语音面试官、医院预约电话机器人。这个框架负责把中间最麻烦的部分接起来：音频进出、什么时候算用户说完了、用户中途插话怎么停下、把语音送给哪个模型、模型回话怎么变成声音、以及怎么接进真实电话网络。由 LiveKit 开发（同一家公司提供 ChatGPT 高级语音模式所跑的实时传输层）。

**解决什么问题**: 在这个框架之前，自己拼一套语音 agent 意味着分别处理 WebRTC 或 SIP 传输、VAD 与轮次检测、STT/LLM/TTS 三段串流、以及打断时的状态回滚——每一段都有自己的坑，而且延迟预算要在几百毫秒内摊完。用了之后的差别是这些环节变成可插拔组件：换 TTS 供应商是换一个 plugin，接 Gemini Live 或 OpenAI Realtime 的 speech-to-speech 是换一种模式，接电话号码是开 SIP，已有的 LangGraph agent 可以只加一层语音壳。它并不替你解决「说什么」，只解决「怎么实时地说和听」。

**谁在用、怎么用**（来自 Issues/HN/X/厂商 PR）:
- 电话客服与外呼：SIP + Phone Numbers 是官方一方能力，用来替代自己桥 Twilio；X 上可见的真实 stack 分享是 LiveKit + OpenAI + Deepgram + Twilio 组合。
- 语音面试与医疗预约：Assort Health 作为生产用户公开背书。
- 给已有文本 agent 加语音层：把 LangGraph 之类的编排结果接到语音通道上，而不是重写 agent。
- Gemini Live / OpenAI Realtime 的 speech-to-speech 接入，是 issue 区讨论最密集的用法（也是问题最多的用法，见下）。
- 厂商侧的用法是「把自己接进来」：近期合入的插件 PR 来自 Bland TTS、Deepgram Flux、Cerebras、Cartesia、FunASR、Azure Voice Live 等。

**社区怎么评价**:
- 正面: 插件生态活跃且由厂商主动推动；1.5.0 的自适应打断模型与 1.6.0 的 async tools 解决了「长工具调用期间 agent 静默」这个真实痛点。forks 3,459 占 stars 的 29%，是真实动手使用而非收藏的强证据。
- 负面: 最热的 issue 几乎全部集中在 realtime 模型适配与打断语义两处——#2356 Gemini native-audio 的 function calling 失效（44 条评论，2025-05 至今未结）、#3515 `min_interruption_duration` 被 `min_interruption_words` 覆盖（26 条）、#3863 AudioStreamDecoder 解码报错（25 条）、#391 缺多参与者支持（25 条）、#3685 电话场景延迟翻倍（17 条）、#5260 `gemini-3.1-flash-live` 首轮 `generate_reply` 超时（16 条）。另有独立开发者在 HN 做 Pipecat vs LiveKit 的 WebRTC 基准测试，顺带吐槽两家的 Python SDK 无法在同一进程共存。
- 健康度: stars 12,014 / subscribers 103 ≈ 117:1，但在 29% fork 率和厂商 PR 流入的背景下不构成 vanity 判断。open 项 736 拆开是 217 issues + 519 PRs，PR 堆积明显（多为排队中的第三方插件）。近 100 次提交贡献者分散：chenghao-mou 11、longcw 10、tinalenguyen 10、u9g 10，其余 39 人各 ≤5，且相当部分来自厂商账号。发布节奏 1-2 周一版，1.6.4(6/24) → 1.6.5(7/9) → 1.6.6(7/18) → 1.6.7(7/25) → 1.6.8(8/3)。仓库 2023-10 创建，属成熟项目首入本 tracker。HN 侧热度分散，最高分主贴仍是 2022 年的 WebRTC 基础设施帖（160 分 / 25 评论），语音 AI 时代的帖子普遍 5-8 分。

**为什么今天上榜**: 最可能的原因是 08-03 发布的 **1.6.8** 含破坏性变更——`python agent.py console` / `dev` 模式被废弃、改走 `lk agent` CLI（#6656），另有 Cartesia Ink-2 的 speech-onset 打断修复（#6630）。强制迁移会驱动大量现存用户回访仓库，与 12K 存量、+148 的温和增幅（全榜今日增量最低）也吻合。没有找到独立新闻事件支撑更强的解释；此判断为中等置信度推断。

**风险与争议**:
- **dependency**: 能力强弱直接绑定 OpenAI / Gemini / Deepgram 等第三方 realtime API，最热的几个 issue 全是上游模型适配失效，上游一变就是全链路问题。
- **stability**: 打断阈值语义互相覆盖、电话场景延迟翻倍尚未收敛，且 1.6.8 带来破坏性 CLI 迁移——版本升级不是无痛的。
- **cost**: 自建在低于约 1 万分钟/月的量级下不如托管划算，Inference / Cloud 存在从开源框架向商业服务上钩的路径。
- **PR 积压**: 519 个开放 PR，插件贡献的消化速度落后于提交速度，第三方插件何时进主干不可预期。

**技术备注**: Python 框架，当前 1.6.8。传输层走 LiveKit 自家 WebRTC，电话侧走 SIP；agent 侧支持两种模式——STT/LLM/TTS 三段流水线，或直连 speech-to-speech 的 realtime 模型。轮次检测与打断由自适应模型处理，1.6.0 起支持 async tools 以避免长工具调用期间静默。CLI 自 1.6.8 起统一为 `lk agent`，原 `python agent.py console/dev` 已废弃。

## 如何理解今天的热度信号

今天有三处容易读错的地方，建议按这个顺序看：

**第一，名次跌幅不等于热度消退。** kaneo ↓13、invidious ↓9 是今日跌幅最大的两项，但两者单日 star 增量分别是 +665（占存量 9.7%）与 +402，都还在正常增长区间。名次下滑更多是因为头部被 DeepSeek 线与大仓回流挤占，而不是自身失去关注。

**第二，最后一次提交时间是本日最有信息量的一列。** 今日 16 项里有 4 项已静默一个月以上：Kronos（2026-04-13）、system-design-primer（2026-03-20）、voicebox（2026-07-27，release 停在 04-25）、Agent-Reach（2026-07-25，release 停在 06-11）。前两项完全属于周期性收藏回流，读者不必期待新功能；后两项仍在缓慢维护，但如果你打算依赖它们，需要自己评估停更风险。反过来，08-03 或 08-04 仍有 push 的项目（Reasonix、Agent-Memory、reverse-skill、ds4、kaneo、invidious、free-claude-code、livekit/agents、pdf-inspector）才是真正在动的那批。

**第三，同样的 stars/subscribers 比值在不同项目上含义不同。** livekit/agents 的 117:1 和 pdf-inspector 的 398:1 都偏高，但前者有 29% 的 fork 率、多家厂商主动提插件 PR、两周一版的发布节奏，比值高只是因为 star 的社交成本远低于 watch；后者则是 HN 评论近零、Reddit 无讨论、传播链条集中在厂商官方号，比值高与其他信号一起指向传播先于采用。同理，generative-ai-for-beginners 的 53% fork 率不是「使用强度高」，而是教程仓库 fork 即上课的结构。判断热度真实性要看多个信号的组合方向，单一比值不构成结论。
