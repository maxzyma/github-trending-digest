## 首次上榜项目

### [cordiverse/cordis](https://github.com/cordiverse/cordis) — NEW ⭐ 4,089（+599）| TypeScript | 信源：强

**它是什么**: 一个"什么业务都不做"的底座框架。它不提供 HTTP 服务、不连数据库、不带任务调度，只提供一套**装配规则**：功能怎么拆成插件、插件之间怎么互相依赖、插件被卸载时它注册过的东西（事件监听、服务、定时器）怎么按相反顺序全部收回去。核心卖点是**可逆性**——装上和卸下是对称的，进程不用重启就能热插拔一块功能。作者 shigma 已经用它当聊天机器人框架 Koishi 的底座跑了四年，核心体积不到 350KB。

**解决什么问题**: 做长期运行的服务型程序时，最麻烦的不是加功能，而是**减功能**：一个模块被卸载后，它注册的事件监听器、起的定时器、往全局注入的服务往往留在原地，导致内存泄漏和幽灵行为，最后只能靠重启进程兜底。cordis 把"插件做过的一切"统一建模成可回收的 effect，卸载时逆序回滚。对 agent 类程序尤其相关——agent 的能力集合本来就是运行期动态增减的。

**谁在用、怎么用**（来自 Issues/HN/中文社区）:
- **最大的一个使用者是 DeepSeek**：8-13 开源的 agent harness（dsh，口号 "Everything is a Plugin"）把 cordis 作为插件内核 vendor 进自己仓库，改 scope 为 `@deepseek-ai/cordis`；cordis 仓库的 homepage 现在直接指向 deepseek-harness 的文档。今天的热度基本来自这条线。
- 四年存量用法在 Koishi 生态：整个 Koishi 插件体系（5.9K ⭐）就是跑在这套可逆插件模型上的，官方文档有专门的 disposable 设计章节。
- issue 区是真实的工程活动而非提问区：#51（dispatch symbol 与 prototype 命名事件）、#34（并发下 fiber epoch 复用导致的 ABA race，附最小复现）、#65/#70（`exactOptionalPropertyTypes` 严格模式下的类型不兼容）——都是有人真的在跑才会碰到的问题。
- 最热的 issue 是 #59「未来发新版本可否同步发布中文 paper？」（5 条评论），侧面说明主力受众仍在中文开发者圈。

**社区怎么评价**:
- 正面: 四年生产验证（Koishi）+ 大厂选型（DeepSeek Harness）+ 一篇成体系的范式论文，三者同时到位；中文技术圈已出现源码解读长文。X 上有 KOL 称 DeepSeek Harness 是"见过最干净的 agent 架构表达"。
- 负面: HN 三条提交（cordis 2 分、paper 3 分、PDF 1 分）**均无讨论热度**，仅有的评论偏负面调侃——"word salad"、"README 除了安装说明什么也没写，看不出它到底干嘛"。这批评有实据：仓库 README 只有五行，把说明全推给外部论文和 deepseek-harness 文档站。Reddit 无讨论。
- 健康度: 4,089 stars / 20 subscribers = **205:1**，比值高，但这是**三天内爆发**造成的短期失衡，不是长期空心——202 forks、34 open issues、2022 年建仓、8 月仍在提交 core 层 bugfix。真正的问题在贡献者结构：shigma 537 commits，第二名 Hieuzest 7 commits。

**风险与争议**:
- **bus_factor**: 单人主导（537 vs 7 commits），且**没有任何 Release / tag**，版本靠 `chore: bump versions` 手动推——下游要 pin 版本只能盯 commit。
- **stability**: README 首屏自述 "API is not yet stable and may change without notice"，v4 仍在 rc；已知并发缺陷 #34（epoch ABA race）尚未修复。
- **dependency**: 当前热度依附于 DeepSeek Harness，而后者是 developer preview 且**已经 vendor 了源码副本**（`@deepseek-ai/cordis`）——上游若就此分叉自维护，主仓的注意力可能同样快地回落。
- **命名稀释**: 与医学名词 commotio cordis、欧盟项目库 cordis.europa.eu 严重撞名，外部检索信号被稀释，这也是它在 HN/Reddit 难以形成讨论的原因之一。

**技术备注**: TypeScript monorepo，packages 下拆为 core / loader / hmr / group / include / timer / logger-console / utils / create。MIT。最后提交 2026-08-13，8 月提交集中在 core 的 service shadow、fiber 状态与事件派发性能。

### [MakazhanAlpamys/Soup](https://github.com/MakazhanAlpamys/Soup) — NEW ⭐ 1,683（+297）| Python | 信源：中

**它是什么**: 一个微调大模型的命令行工具。写一份 `soup.yaml`（模型、数据集、量化方式、训练参数），敲一条 `soup train`，就在自己这台机器上把开源模型微调完，不用租云 GPU、不用 SSH 到远程机器、不用自己拼 PyTorch 训练脚本。招牌功能叫 **layer streaming（层流式加载）**：LoRA 微调时基座模型是只读的，所以把它整份放在主机内存里，按解码器层一层一层送进显存，显存峰值只等于一层的大小——由此宣称 **4 GB 笔记本显卡能微调 8B 模型**。

**解决什么问题**: 想微调一个 8B 模型，常规路径要么租云 GPU（有钱有配置成本），要么本地显存不够直接放弃。Soup 把门槛压到"一台带独显的笔记本"，并把配置从一堆脚本压成一份 YAML。README 给的实测是 Llama-3.1-8B-Instruct + NF4 + LoRA、batch 1、seq 512，在 RTX 3050 Laptop 4 GB 上峰值 3.32 GB、119.6 tok/s。

**谁在用、怎么用**（来自 Issues/HN）:
- HN 上有一次实质讨论：Show HN「Fine-tune an 8B model on a 4 GB laptop GPU」（2026-08-04，**138 分 / 28 评论**）。评论区有人分享在社区银行用 4B 模型跑反洗钱场景的微调需求，也有"小的开源模型才是未来"这类共鸣。
- 但**质疑同样集中**：显存占用仍随模型规模变化、流式相对常驻有约 1.43x 的时间开销、14B 以上在 4 GB 卡上仍跑不动；讨论里**没有人复现**，也**没有与 Unsloth / accelerate offload / ZeRO-Infinity 的横向对比**。
- issue 区不能当社区活跃度读：90 个 open 项实为 78 issue + 12 PR，而**78 个 issue 全部由作者本人开**（大量挂 `good first issue` 标签用于派活），外部提交的 open bug report 为**零**；已关闭 issue 也是 64/69 出自作者。最有信息量的两条恰恰是作者自查缺陷：#327 层流式的显存预检算错、#339 非量化模型一律以 float32 加载导致 bf16 权重白占两倍显存。

**社区怎么评价**:
- 正面: **证据披露规格明显高于 Trending 平均水平**。`benchmarks/` 公开了每一次 gate 的原始记录（H100 验证、NF4、preference losses、measured VRAM fit、T4 Colab 免费档跑法），并且**把失败的和测完被丢弃的读数一并留在里面**。预印本 v3（8-13）主动撤回 v2 中"层流式受主机到显存传输带宽约束"这一条从未实测的论断，并公布推翻它的测量（删掉全部 host-to-device 字节只快 1.4%，真正最大的流式开销是每层 NF4 反量化，占 9.8%）；v1/v2 保留各自版本 DOI 不做修改，"让我们当时声称过什么"的记录保持完整。README 还诚实写出对自己不利的结果——八卡 ZeRO-3 比单卡常驻训练更慢。
- 负面: **核心宣称至今无第三方独立验证**。119.6 tok/s、3.32 GB 峰值、bit-exact 全部是作者自测；README 所称"在完全不同的硬件上复现"实为作者本人在借用的 8×H100 上跑；Zenodo 预印本为自发表，非同行评审。Reddit（含 r/LocalLLaMA）与 X **均无讨论**，可见的外部传播是 Product Hunt、GIGAZINE 这类稿件。
- 健康度: 1,683 stars / 10 subscribers = **168:1**；仓龄约 6 个月（2026-02-20 建仓）；262 forks；作者 745 commits，第二名 11——有约 10 位外部贡献者在合小 PR，但都是作者派发的任务。发版极频繁，当前 v0.73.2。

**风险与争议**:
- **vanity**: 168:1 的 stars/subscribers 比 + issue 区零外部 bug report + Reddit/X 无有机讨论，热度主要沿 HN 单次曝光和 Product Hunt/媒体稿传播；star 曲线快于真实使用者沉淀。
- **bus_factor**: 745/≈780 commits 出自作者一人，issue 议程也由作者单方设定。
- **stability**: 自述 BETA，且已自曝显存预检算错（#327）与 float32 加载缺陷（#339）；发版节奏极快，跨版本行为可能漂移。
- **无独立复现**: 这是最需要读者自己把关的一条——性能与 bit-exact 主张的证据链完整但**闭环在作者一人手里**，要用它做技术选型，应当先按仓库提供的 Colab T4 notebook 自跑一遍再下结论。

**技术备注**: Python 3.10–3.12，Apache-2.0，PyPI 包名 `soup-cli`，带 Dockerfile / docker-compose。支持 NF4 量化、LoRA、以及 DPO / ORPO / SimPO / KTO 等偏好优化在层流式下运行（v0.72.4 起）。概念 DOI `10.5281/zenodo.21771064`。

## 如何理解今天的热度信号

今天最值得注意的不是某个项目虚不虚，而是**热度来源的三种类型第一次在同一张榜上分得很清楚**：

**第一类：被上游选型带起来的。** cordis 是最纯粹的样本——四年老仓、无 release、自身无发版，因为 DeepSeek 的 agent harness 选它当插件内核，三天内登顶。这类热度的可靠性取决于**选型方**而不是项目方，判断时应该去看 deepseek-harness 的成熟度和它会不会长期依赖上游（它已经 vendor 了源码副本，这是个减分信号）。

**第二类：项目侧真的在动。** FluidVoice（一周七个蓝牙音频稳定性修复）、spec-kit（发版 + 五条目录扩展）、needle（文档精修 + 错误处理）、ToolJet（双轨同日发版）、unsloth（三天四个 beta）。这几项的 star 增长有对应的代码事件，但注意 unsloth 的"动"是**未收敛的快速迭代**，不等于可以放心装。

**第三类：存量声誉被流量顶上来。** public-apis（460K 长青清单，周期性回榜，今日 +2,260 全榜第一）、holehe（停更近两年仍在第 9）、CLI-Anything（registry 内容两周未动，近期提交只在改官网移动端性能）。这三项今天合计 +2,760 stars，没有一项能用项目侧事件解释。

关于 stars/subscribers 比值的用法，今天有两个对照值得记：ego-lite 333:1（仓龄 4 个月 + 核心路径缺陷 #183 挂着 18 条评论 + 无新提交）与 diagram-design 252:1（比值三天持续走高 + 主动挂榜单徽章 + 外部有机讨论薄）**属于需要结合其他信号谨慎解读的组合**；而 cordis 的 205:1 与 Soup 的 168:1 是**三到六个月内爆发造成的短期失衡**，单独看这个数字容易误判——cordis 有四年 Koishi 生产验证托底，Soup 有公开到失败读数的 benchmark 记录托底，真正该盯的分别是"DeepSeek 会不会分叉自维护"和"有没有第三方复现"。

最后一条方法提醒，来自 Soup：**证据披露的完整度和结论的可信度是两件事**。Soup 公开了每次 gate 的原始测量、保留了被推翻的读数、还主动撤回了自己已发表的一条解释性论断——这个透明度在 Trending 上属于罕见的高标准。但所有数字仍然出自作者一人，HN 的 138 分讨论里无人复现，issue 区没有一条外部 bug report。**披露得越完整，越应该有人去复现它；没有复现的完整披露，仍然只是单方证词。**
