### [Dicklesworthstone/destructive_command_guard](https://github.com/Dicklesworthstone/destructive_command_guard) — NEW ⭐ 2,969（+444）| Rust | 信源：中

**它是什么**: 给 AI 编码 agent（Claude Code / Codex / Gemini CLI / Cursor / Aider 等）用的「破坏性命令拦截器」（简称 dcg）。作为 agent 执行命令前的 pre-execution hook，拦截 `git reset --hard`、`rm -rf`、`DROP TABLE` 这类会造成不可逆损失的操作。

**解决什么问题**: AI agent 自动跑 shell 命令时可能「好心办坏事」——一条 `rm -rf` 或 `git reset` 就抹掉未提交工作。没有它时开发者只能靠人工盯屏或事后 git 恢复；用了之后由白名单优先（whitelist-first）的规则在命令执行前判定放行/拦截，宣称 SIMD 加速、亚毫秒延迟。

**谁在用、怎么用**（来自 Issues/HN）:
- 场景 1: 挂到 Codex CLI 做 hook，但 #183 报告 Windows 上 Codex 0.144.x 集成静默失败，hook 判 deny 被当成 hook 出错、命令仍被执行（安全绕过）。
- 场景 2: #189 报告命令预处理对嵌套/未闭合 `$(` 有指数级时间复杂度，触发 200ms fail-open 超时，破坏性命令被放行。

**社区怎么评价**:
- 正面: 定位切中 agent 时代的真实痛点，功能/建议类 issue（#187）有人认真参与。
- 负面: 多个 issue 显示防护可被绕过；#185 dcg skill 的校验脚本指向 404 仓库。
- 健康度: stars/subscribers ≈ 297:1，open issues 9，作者独占 1,752 次提交（实质单人），2026-01-07 建、约半年龄。

**风险与争议**:
- **vanity**: stars 远超 subscribers，HN/Reddit 几乎零独立讨论，传播靠作者推广 + 聚合站转载。
- **stability**: #183/#189 显示 fail-open 场景下核心防护可被绕过。
- **bus_factor**: 实质单人维护。

**技术备注**: Rust 实现，whitelist-first + SIMD 加速；仅防「善意但犯错的 agent」，非对抗性攻击防护。

## 如何理解今天的热度信号

今日榜单的可信度分层比较明显：sharpemu 有多论坛媒体独立报道 + 具体兼容性 issue，是「强」grounding 的真信号（尽管媒体标题夸大）；而 destructive_command_guard、hallmark、Wand-Enhancer 三者都呈现「stars 高、subscribers 极低、站外讨论近乎为零」的组合，其中 Wand-Enhancer 更有 forks 近 3 倍于 stars 的异常。这类项目的热度是真实的（确有人点星），但热度不等于采用——判断价值时应结合 issues 的真实使用场景、站外独立讨论、维护集中度，而非只看 star 增速。
