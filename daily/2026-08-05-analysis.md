**主线二：agent 安全从"攻"这一侧扩到"守"这一侧。** 昨天榜上只有 reverse-skill 这类逆向/渗透技能路由包（今天仍稳在第 2，日增 +2,297，总数 18,254），今天 Uber 把 ADR（Agentic Detection and Response）开源上榜。这是第一个带**企业生产实证**的 agent 安全项目：论文进 MLSys 2026，Uber 内部部署 10 个月、覆盖 7,200+ 主机、日处理 10,000+ agent 会话。它给出的三条运营结论比代码本身更值得读：安全的最小单元是 workflow 而不是单个 tool call；**凭据泄露在真实环境里远比 prompt injection 常见**；单会话 50+ 次人工批准会造成 approval fatigue，人工审核实际退化成橡皮图章。攻守两侧同日在榜，说明 coding agent 已经跑到了"要被安全团队当资产管起来"的阶段，而不再只是开发者个人工具。

## NEW 项目

### [uber/ADR](https://github.com/uber/ADR) — NEW ⭐ 763（+148）| Python | 信源：中

**它是什么**: 把杀毒软件里的 EDR（端点检测与响应）那一套，搬到 AI agent 上。公司里现在到处是 Cursor、Claude Code、Codex 这类会自己读写文件、调 API、执行命令的 agent，安全团队面对的问题是：传统监控只能看到"某个进程写了一个文件"，看不到"是哪句 prompt、经过什么推理链，最后决定写这个文件的"。ADR 采集的是完整因果链 `prompt → 推理 → 工具调用 → 结果`，让安全团队第一次能回答"这个 agent 刚才为什么这么干"。

**解决什么问题**: 在 ADR 之前，企业要么完全放任 coding agent（出事之后靠 git log 和运气复盘），要么靠人工逐次批准（Uber 自己的数据是单会话 50+ 次批准，人根本看不过来，最后全点同意）。ADR 之后，agent 行为变成可采集、可回放、可自动检测的遥测数据，安全团队能在 CI 之前就发现"这个 agent 会把生产库凭据打进日志"。

**开源了什么、没开源什么**（README 与论文实证）:
- `Sensor/`：解析 Cursor / Cline / Claude Code / Codex / Warp 等 7+ 工具在本地留下的 SQLite / JSONL 缓存，重建成统一 schema 的会话。
- `Detection/`：ADR-Bench（302 个任务、133 个 MCP server、729 个工具，覆盖论文归纳的全部 17 种 agent 攻击手法）+ 两级检测器（廉价高召回 triage，可疑会话再交给深度推理 agent）。
- **未开源**：Prevention（实际拦截动作）和 Explorer（上线前红队引擎）。也就是说现在拿到的是"看得见"，不是"拦得住"。

**谁在用、怎么用**（来自论文/Issues/X）:
- 场景 1：Uber 自己的生产部署是唯一可引的实战案例——10 个月、7,200+ 主机、日均 10,000+ agent 会话，发现 26 类共数百起凭据泄露，shift-left 拦截精度 97.2%。Uber 据此封禁了 OpenClaw，并要求新 agent 上线前过安全评审。
- 场景 2：学术/评测复现。`docs/REPRODUCIBILITY.md` 给了完整流程（解包 benchmark → 跑各家检测器 → 出论文图），`--detector llamafirewall` 支持无 key 冒烟测试，适合想横向对比 agent 安全方案的团队。
- **外部第三方部署案例目前为零。**

**社区怎么评价**:
- 正面：技术侧 grounding 很硬——MLSys 2026 收录论文（arXiv:2605.17380）、可复现 benchmark、真实规模的生产数据，不是 demo 仓库。Apache-2.0。
- 负面：外部贡献者提交的全是**代码缺陷报告，没有一条使用者反馈**。#21 指出 CursorParser / ClineParser 根本没有 Windows `%APPDATA%` 分支，README 却宣称支持 Windows，实际在 Windows 上静默返回零遥测；#17 指出 WarpParser 缺 `max_age_days` 上限（同目录其他 parser 都有 14 天 cutoff），每次全表重扫；#18 指出 benchmark 超时后 claude CLI 子进程未 kill 造成进程泄漏。配套的 PR #19 / #20 **均未合并**；两个依赖 CVE 修复 PR（#23 deepdiff、#24 jupyter-server）同样挂着未处理。
- 健康度：763 stars / 10 subscribers（76:1，Uber 官方组织下 watch 低属常态，但绝对值确实很小），72 forks，10 open issues。贡献者高度集中在 4 名 Uber 内部作者（`lghupan` 8 次、`cm-howard` 5 次、`cmvan` 4 次、`barisozbas` 2 次），其余是 dependabot。
- ⚠️ **issue 评论数不可用作活跃度指标**：#17 / #21 / #18 分别挂着 41 / 33 / 27 条评论，全部是与 issue 内容无关的中文泛化 emoji 灌水（"状态管理别过度抽象就好 🔥"、"热更新支持吗 📦💡🚀"），来自一批批量注册账号。这批评论是养号行为，不代表社区讨论。
- HN 无讨论（Algolia 搜 "Agentic Detection and Response" 零命中）；X 上有传播但主要来自 Uber 官方（Praveen Neppalli 的长推）；Reddit 无讨论，且 "ADR" 这个缩写被 Architecture Decision Record 严重污染，搜索不可靠。

**风险与争议**:
- **bus_factor**: 4 名 Uber 内部作者贡献全部实质代码，外部 PR（含两个 CVE 修复）全部积压未合，看不出接纳外部维护的意愿。
- **stability**: README 宣称的 Windows 支持在两个 parser 中并不存在（#21），会静默产出空遥测——对安全工具来说是最危险的失败模式。
- **vanity**: 证据侧并不空（论文 + 生产数据 + 可复现 benchmark 都真实存在），但热度来源单一，几乎全靠 Uber 品牌和官方 X 传播，HN/Reddit 无有机讨论，issue 区还被水军填充，763 stars 里真实评估者比例存疑。
- **cost**: 默认 detector 路径需要 ANTHROPIC_API_KEY + OPENAI_API_KEY，跑完整 302 任务 benchmark 有实打实的 token 开销。
- **dependency**: 两个未处理的依赖 CVE 挂在一个安全工具仓库里，观感和实质风险都不好。

**技术备注**: Python，`uv sync` 安装，Apache-2.0；`Detection/benchmark/agentdojo/` 为 vendored 第三方代码（MIT）。适合安全团队当**参考架构和评测基准**读，不适合直接当产品部署——真正的拦截层没开源。

## 如何理解今天的热度信号

今天有两类容易误读的地方，值得单独说明：

**第一，排名不等于增速。** 前面提到 DeepSeek-Reasonix 和 airllm 的排名与日增反向。GitHub Trending 的排序综合了增速、绝对量、时间衰减等因素，单看排名变化写"某项目热度下滑"在今天会写错。本文的排名变化列只反映位次，判断动能请看日增列。

**第二，两位数日增的老项目上榜是槽位效应，不是事件。** 榜单今天扩到 18 条，而真正高动能的项目只有 8 个左右。webpack、spdlog、Cypress、Angular 这些项目日增 10-13 星，逐个核对过近期 release 也没有事件，它们出现在榜上不构成任何"技术回潮"信号。反过来说，这类槽位效应也提醒：**榜单长度本身会影响你看到什么**，跨日对比"上榜项目数"时要留意这个变量。

至于 stars/subscribers 比，今天头部几个项目普遍在 250:1 以上，但这个比值单独不足以下判断——superpowers 的 263:1 出现在一个有 23,837 forks、1,014 watchers 的成熟项目上，性质与 pdf-inspector 的 414:1（仅 25 watchers）完全不同。要结合 fork 形态、issue 内容质量、外部讨论一起看。uber/ADR 是今天最好的对照：它的社区侧 grounding 很弱（HN/Reddit 零讨论、X 仅官方传播、issue 评论区被水军填充），但技术侧 grounding 很强（MLSys 论文 + 10 个月生产数据 + 可复现 benchmark）——只看社区信号会低估它，只看 Uber 品牌又会高估它的开源可用性（拦截层没开源、外部 PR 无人合并）。
