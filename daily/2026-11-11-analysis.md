## 新上榜项目

### [we-promise/sure](https://github.com/we-promise/sure) — NEW ⭐ 12,012（+159）| Ruby | 信源：中

**它是什么**: 一个自己部署的个人记账和资产管理应用。你把银行账户、信用卡、券商持仓接进来，它汇总成净值曲线、收支分类和预算。README 写明它是已归档的 Maybe Finance 项目的社区 fork，由社区继续维护。

**解决什么问题**: Maybe Finance 原团队停止开发并把仓库归档后，已经在用它的人没有了后续版本。Sure 接手这份代码继续发版，补银行和券商的数据接入。对不想把流水交给商业记账服务的人，它提供一个可以放在自己服务器上的选项。

**谁在用、怎么用**（来自 Issues/README）:
- 自托管净值跟踪：#10（26 条评论，2025-07 至今未关闭）报告净值要手动建一笔交易才算对，说明有人长期用它盯净值。
- 银行流水同步：#88（24 条评论）、#2720（16 条评论）讨论 SimpleFIN、Enable Banking 同步后的总额错乱和去重误删交易。
- 从其他记账工具迁移：#641（21 条评论）要求导入 Mint、YNAB 数据。
- 券商接入：评论最多的 PR 在加新的数据源，如 StashAway（#4742，40 条评论）、eToro（#4700，27 条评论）。

**社区怎么评价**:
- 正面: 贡献者较分散，jjmata 428 次提交、zachgoll 230、Shpigford 220、gariasf 208、sokie 131；11 月以来新开 issue 44 个，连发三个 alpha 版本。
- 负面: 核心的净值和余额计算问题长期未关（#10、#243）；#4790 报告 SimpleFIN 同步约 15 天后永久失败（已关闭）。
- 健康度: 12,012 stars、892 forks、39 subscribers（约 308:1），896 个 open issue/PR（其中约 418 个是 PR），仓库 2025-07 创建，今天仍有推送。HN 只有一篇 1 分、0 评论的帖子；X 上没有检索到相关讨论；Reddit 本次未能检索到，热度未知。

**风险与争议**:
- **stability**: 净值、余额、同步去重等核心计算的 bug 积压时间长，财务数据出错的代价高。
- **dependency**: 银行流水依赖 SimpleFIN、Enable Banking 等第三方聚合服务，覆盖范围和稳定性受它们限制。
- **compliance**: AGPL-3.0 许可，修改后对外提供服务需要开放源码；README 另有商标使用限制，不能沿用 Maybe 的名称。
- **PR 积压**: 约 418 个 open PR，合入速度跟不上提交速度。

**技术备注**: Ruby on Rails，AGPL-3.0；提供 Docker 部署，最新正式版 v0.7.6（10-31）。

### [tokio-rs/topcoat](https://github.com/tokio-rs/topcoat) — NEW ⭐ 6,853（+192）| Rust | 信源：强

**它是什么**: 一个用 Rust 写完整网站的框架，README 的标语是"The full full-stack framework for Rust"。页面由服务器生成，按钮点击、展开收起这类交互也用 Rust 写，框架负责把它变成浏览器能跑的 JavaScript。路由、UI 组件、资源打包、Tailwind、会话、邮件和 OpenAPI 都自带。

**解决什么问题**: 用 Rust 做 Web 应用，过去通常要后端一套 Rust、前端一套 JavaScript 工程，或者把 Rust 编译成 wasm 发到浏览器。Topcoat 让组件直接在服务端查数据库并渲染，省掉单独的 API 层；简单交互不用回服务器，也不需要 wasm 包和前端构建步骤。

**谁在用、怎么用**（来自 Issues/HN）:
- 个人项目：#486 的作者说自己在个人项目里用它并且喜欢，同时报告约 5k 行的项目改一行后 dev 重建要 37 秒，宏里的代码得不到语言服务器支持。
- 多应用工作区：#517（5 条评论）报告多个应用共用 target 目录时，`topcoat dev` 会清掉其他应用的资源包。
- 没有找到生产环境落地的案例。

**社区怎么评价**:
- 正面: HN 两次讨论都上了百分，7-17 的首发帖 134 分，9-25 的第二篇 114 分；有评论把它类比 Phoenix LiveView，Rails 背景的开发者认可这个方向。
- 负面: HN 上有人质疑它没有数据库层却自称 full-stack，也有人担心它靠 Tokio 的名气而不是技术获得采用。#275（8 条评论，最热）提议把客户端代码从真实 Rust 编译成 JS，替换现在的表达式转译方式，核心设计仍在争论。
- 健康度: 6,853 stars、302 forks、43 subscribers（约 159:1），58 个 open issue/PR，仓库 2026-04 创建，11-10 仍有推送。提交集中在 pikaju（965 次），Tokio 作者 carllerche 12 次。X 上以官宣和转述为主，没有看到独立使用反馈；Reddit 本次未能检索到。

**风险与争议**:
- **stability**: README 自述早期、实验性，0.x 版本从 10-24 的 v0.11.0 走到 11-10 的 v0.12.1，升级要预期破坏性变更。
- **bus_factor**: 绝大部分提交来自一位开发者。
- **开发体验**: 增量构建慢、宏内代码缺少 IDE 支持（#486）。
- **功能缺口**: 与 Toasty ORM 的更好集成仍在 README 的 Roadmap 里，表单到数据库这一段还要自己写。

**技术备注**: Rust，MIT 许可；服务端渲染加表达式转译，另有 htmx 和 Datastar 集成；最新版本 v0.12.1（11-10）。
