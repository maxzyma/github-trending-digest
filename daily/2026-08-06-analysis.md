## NEW 项目

### [cloudflare/computer](https://github.com/cloudflare/computer) — NEW ⭐ 3,094（+891）| TypeScript | 信源：强

**它是什么**: 给 AI agent 配的一台「云端电脑」。不是真机器，而是一个住在 Cloudflare Durable Object 里的虚拟文件系统——agent 的所有文件读写落到 SQLite 权威状态里，跑命令则通过一个统一入口 `workspace.runtime.exec()` 分发到三种后端：真容器（把状态用 FUSE 挂载成真实文件系统，有完整 Linux 和网络）、轻量 isolate shell（跑 just-bash，无需容器）、isolate JavaScript（跑 ES module，带 Workspace 版 `node:fs` 和内置 git）。agent 干活的「工作台」从此持久、可审计、按需付费。

**解决什么问题**: agent 要读写文件、执行命令、操作 git，之前的选择要么是直接跑在用户本机（危险且不可审计），要么租 E2B 这类独立 sandbox 服务（状态不持久、起容器有成本）。computer 把「文件系统状态」和「执行面」拆开：状态常驻 Durable Object（几乎零闲置成本），执行后端按需懒连接，轻任务走 isolate 连容器都不用起。第三方博客 construct.computer 称已用它「给所有 agent 配电脑、几乎零成本」。

**谁在用、怎么用**（来自 Issues/HN/博客）:
- 场景 1: 拿它当 agent 的 git 工作区。上榜次日的 bug 报告全是 git/文件系统的深水区问题——#55（通过 dofs 写 symlink 静默丢数据）、#54（symlink 解析 EINVAL）、#56/#57（git status 渲染、git log 时区错误）、#58（capnweb RPC stub 泄漏计数错误），能踩到这些坑说明使用者在真实跑 git 流程。注意 #54-#59 由同一用户在同一分钟批量提交，疑似 AI 辅助审计产出，但内容具体、可复核。
- 场景 2: 官方 examples 提供容器/isolate 双后端对比 Worker 和 recipe→pandoc→PDF 教程；#50 请求暴露 runtime 后端能力发现接口，属于「想认真接入」的需求。

**社区怎么评价**:
- 正面: 架构层受到好评——SQLite-in-Durable-Object 虚拟文件系统 + isolate/container 双后端动态编排的设计被认为是把 agent 执行环境「平台原语化」的正确方向。
- 负面: preview 级质量坑密集（symlink 丢数据对文件系统来说是最危险的缺陷类别）；#59 指出文档与实际 wire contract 不符；#53 报告 Discussions 链接失效。
- 健康度: 3,233⭐ / 14 subscribers（231:1，大厂新仓官方 watch 低属结构性现象）、146 forks、20 open issues；贡献者高度集中——aron-cf 一人 568 commits，其余合计不足 25；8-05 仍在 push。HN 官方博文 13 分/3 评，热度偏低；X 以 Cloudflare 官号和媒体（Fortune、Phoronix）传播为主；Reddit 无讨论。

**风险与争议**:
- **stability**: 官方明确标注 PREVIEW ONLY、API 不稳定；symlink 静默丢数据、文档失准等基础缺陷密集，不能当生产件用。
- **bus_factor**: 单人贡献 568 commits 占绝对主导，团队化维护尚未成形。
- **dependency**: 深度绑定 Cloudflare Workers/Durable Objects/Dynamic Worker，用它等于选择整个 Cloudflare agent 平台栈，无法迁移。

**技术备注**: TypeScript，MIT，包名 `@cloudflare/computer`；容器后端经 capnweb RPC 同步（sandbox 侧守护进程 `computerd`）；`docs/` 下是前瞻性规范，官方提示「读意图，别当现状」。

### [huangruiteng/loopx](https://github.com/huangruiteng/loopx) — NEW ⭐ 2,181（+326）| Python | 信源：中

**它是什么**: 长时运行 AI agent 工作的「本地控制面」。一个 agent 一次会话能修完一个 bug，但跨几天、几周的目标（修一串 issue、跑一轮实验、持续监控）会遇到：会话上下文丢了、quota 用完了、多个 agent 之间交接混乱。loopx 把「目标、闸门（gate）、待办、证据日志、quota、交接记录」做成一层持久状态内核，让 Codex / Claude Code / Cursor 每次只执行一个有边界的回合，回合之间的连续性由 loopx 维护。作者给的心智模型是「面向 agent 的看板」：卡片带身份、权限、证据和续接信息，看板只是投影，loopx 状态才是事实源。

**解决什么问题**: 现在让 agent 干长活的普遍做法是「聊天记忆 + 定时器」——上下文会漂移，调度器会在没有有效进展时继续烧 token，人也看不清 agent 干到哪了。loopx 想把这层「控制状态」从聊天里拿出来单独治理：quota 感知的自动唤醒、需要人类判断时停下来问具体问题、每回合写证据和 handoff。它明确不替代 agent runtime，危险权限和最终决策留给人。

**谁在用、怎么用**（来自 Issues/PR）:
- 场景 1: 外部用户在 #2353 提出 bounded loop 的「look back and retain」设计建议（8 条评论，有真实往返讨论），是仓里最像有机社区互动的一条。
- 场景 2: 第三方 agent 接入 PR——TraeX 集成 #2790、KunlunCode 集成 #2791、中文本地化 #2793，说明有国内 coding agent 厂商在尝试对接。
- 主要可见用例仍是作者自己的 dogfooding：README 展示的 OpenViking issue-fix 和 Auto ML 两条轨迹各跨「200+ 小时 loop 生命周期」（作者自己澄清是墙钟时间，不是连续无人值守运行）。

**社区怎么评价**:
- 正面: 「长时 agent 工作需要独立的状态/控制层」这个问题意识被普遍认可（与今天同榜的 TencentDB-Agent-Memory 属相邻赛道）；文档完备度远超一般两个月新仓（mkdocs 站点、中英双语 README、治理文件齐全）。
- 负面: 新用户看不懂定位——#2807「这是一个增强的 plan 工具吗」、#2806「能适配 pi-agent 吗」；最热 issue #2785（55 评论）是作者自己发的。
- 健康度: 2,241⭐ / 5 subscribers（448:1，全榜最高失衡）、167 forks、28 open issues。**活跃度指标被自动化严重放大**：issue/PR 编号已到 #2807，但真实 issue 仅约 25 个，其余绝大多数是作者 agent loop 自动提交的模板化 PR（`fix(heartbeat)`、`fix(scheduler)`）；作者 3,881 commits，第二贡献者仅 17。HN 无讨论（Algolia 仅命中同名加密货币骗局旧闻）；Reddit 无讨论；X 上是作者自宣（清华 EE / 字节背景，绑定其另一项目 OpenViking），主要传播渠道是小红书（4K+ 粉丝）。

**风险与争议**:
- **vanity**: 两个月新仓 + 2,241 stars 对 5 watchers、HN/Reddit 零足迹、传播集中在作者中文社媒——star 增长与独立社区验证明显脱节。
- **bus_factor**: 单人贡献 3,881 commits 绝对主导，commit/PR 量由自身 agent 自动化灌注，不能当社区活跃度读。
- **stability**: 项目自标「loop agents early」，外部真实生产使用证据薄弱，主要实证是作者自己的运行轨迹。

**技术备注**: Python 3.11+，MIT；本地优先（local-first）控制面，不托管代码执行；文档站 + 飞书用户手册；对接 Codex / Claude Code / Cursor / 自定义 runtime。

## 如何理解今天的热度信号

今天最有教学价值的是 computer 和 loopx 这对同框样本：**仓龄相同（都约两个月）、stars/subscribers 比值同样超标（231:1 vs 448:1），但可信度判断完全相反。** computer 的比值超标来自「大厂官方仓固有的低 watch + 公告驱动的短期爆发」，其余信号全部指向真实使用：外部 bug 报告具体到 symlink 语义和 RPC 泄漏计数、HN/媒体/第三方博客留有独立足迹；loopx 的比值超标则与其他信号同向：提交和 PR 由作者自动化灌注、英文社区零讨论、传播集中于作者自己的社媒。结论是老结论，但今天的证据特别干净——比值只是入口，判断靠组合。

另外两点：一是榜单长度从 18 收回 13，昨天两位数日增的老基建全部退出，说明「榜单长度」这个变量确实在日间波动，跨日比较「上榜项目数」时要先对齐这一点；二是排名与日增继续脱钩（Agent-Memory 日增新高却 ↓2、Reasonix 日增回落却 ↑11），判断动能请始终看日增列而不是排名箭头。
