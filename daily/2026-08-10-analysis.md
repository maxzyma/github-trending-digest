**主线一：榜单地图 — coding agent / skills 生态仍是最大盘，但榜首换成了"开源 harness"而非技能包。** 今日 12 项可分六组：① **coding agent / agent skills 生态**（5 项，项目数最多）——PrimeIntellect-ai/prime-agent（NEW 榜首，+2,356，自改进 coding harness）、msitarzewski/agency-agents（RE，140,766 ⭐ 的一站式 AI 代理团队）、addyosmani/agent-skills（↑1，KOL 技能包）、google/skills（RE，Google 官方 Agent Skills）、pingdotgg/t3code（RE，编码 agent 的 Web GUI）；② **代码理解基础设施**——vitali87/code-graph-rag（NEW，把 monorepo 建成知识图谱供 agent 查询）；③ **系统排障工具**——pranshuparmar/witr（NEW，Go 写的"这进程到底谁起的"追溯器）；④ **科学 AI**——google-deepmind/weathernext（NEW，DeepMind 气象模型家族仓）；⑤ **垂类 benchmark**——harveyai/harvey-labs（NEW，法律 agent 长程任务基准）；⑥ **成熟基建首入 tracker**——goauthentik/authentik（NEW，开源 IdP）、Comfy-Org/ComfyUI（NEW，125K ⭐ 扩散模型节点式 GUI）；另有 ZhuLinsen/daily_stock_analysis（RE，LLM 股票分析）。结构性变化是：过去几个月 agent 板块的榜首长期由"技能包 / prompt 集合"占据，今天换成了带自改进循环的完整 harness——竞争重心从"给模型喂什么"转向"用什么框架跑长任务"。

**主线二：AI 天气预报走完了从论文到业务运行的最后一公里。** google-deepmind/weathernext 是 2023 年 `graphcast` 仓库改名而来（创建日期仍是 2023-07-14），现在统一承载 WeatherNext 2、WeatherNext Cyclones 及降级为 legacy 的 GraphCast / GenCast。上榜直接触发是 2026-08-06 的 Nature 论文《Operational tropical cyclone forecasting with AI》+ 同日开源权重 + v0.3.0 发布——其中 Cyclones 模型是 2025 年大西洋飓风季**实际投入业务运行**的 FNV3，与 NHC、CIRA、英国气象局联合开发，路径与强度平均提前一天以上。对读者的意义：这不再是"AI 在再分析数据上刷分"，而是气象业务机构把 AI 模型接进了预警链条；代码 Apache-2.0、权重 CC BY 4.0，允许商用与业务部署。同一天上榜的 harveyai/harvey-labs（法律 agent 长程任务基准，1,671 个任务 / 24 个执业领域）指向同一件事：AI 的竞争正在从通用能力转向"某个专业领域的交付物是否达标"。

**主线三：垂类 benchmark 由厂商自建，标尺设定权值得读者留意。** harvey-labs 已被 Artificial Analysis（LAB-AA）与 Vals AI 各自独立实现——这是很硬的采纳证据，但也暴露了方法学分歧：同一批任务，criterion 级通过率 85–95%，而 harvey-labs 采用的 all-pass 制（全部 rubric 条目通过才得 1.0）算下来只有 7–20%。LawSites 已公开评论 Harvey 作为法律 AI 厂商同时定义"什么是合格的法律工作产出"的 agenda-setting 问题。这不否定 benchmark 的价值，但跨模型横比结论需要看清用的是哪一套记分规则。

**主线四：榜单解读提醒 — 今天两个高传播项目的 stars/subscribers 比值处在需要交叉验证的区间。** pranshuparmar/witr 是 20,718 ⭐ / 43 subscribers（482:1），PrimeIntellect-ai/prime-agent 是 11,257 ⭐ / 56 subscribers（201:1）。但两者的 grounding 结论并不相同：witr 有 HN 526 分 / 105 评论的高热讨论，且已进入 Debian sid、Ubuntu 26.04+、Kali、conda-forge 官方源——**发行版打包是比 star 硬得多的采用证据**；prime-agent 有 HN 253 分 / 69 评论、1,158 forks 和真实外部 PR，但其"首个超越人类专家"的 ARC-AGI-3 95.5% 属厂商自测且不在官方榜单上。同一个高比值，一个指向"关注者多于长期跟踪者"，另一个指向"基准宣传强度大于独立验证"，不能用同一句话打发。

### [PrimeIntellect-ai/prime-agent](https://github.com/PrimeIntellect-ai/prime-agent) — NEW ⭐ 11,257（+2,356）| TypeScript | 信源：强

**它是什么**: 一个跑在命令行里的"编码助手外壳"（harness）。你把任务交给它，它自己拆步骤、写代码、跑命令、看结果、再改，可以连续跑几个小时不用人盯着。和常见工具不同的地方是它带一个"自改进循环"——把这次任务里摸索出来的做法沉淀下来，下次遇到类似问题直接复用。

**解决什么问题**: 以前用 Claude Code、Codex 这类工具，你得一轮一轮盯着它，跑长任务容易断在中途，而且每次都从零开始摸索。prime-agent 想解决的是"无人值守跑长任务"和"经验不流失"两件事。另外它可以直接指向本地推理端点（vLLM / Ollama / LM Studio），用开源权重（如 GLM-5.2）替代闭源 API——对不想把代码送出去或者受 token 成本约束的团队，这是实际的替代路径。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 长跑自治任务踩到并发与会话状态问题：#1039（21 评论）报告会话归档后无法恢复、#851 worker 超时未清理注册、#1046 stopWorker 进程身份校验缺失——这些 bug 的形态说明有人真在拿它跑数小时级任务，而不是试用一下就走。
- 用本地开源模型跑编码：社区把它当作 Codex / Claude Code 的开源替代，指向自建推理端点。
- sub-agent 作为持久 IPython kernel 内的函数调用，用于需要保留中间状态的多步分析。
- 缺口反馈：#305 要求补 plan mode（目前没有"只看方案不动手"的模式）、#506 多客户端会话恢复失效、#464 子 agent 取消语义不明确。

**社区怎么评价**:
- 正面: HN 主贴 253 分 / 69 评论，讨论热度真实；1,158 forks 和 mitsuhiko、hjanuschka、snimu 等 10+ 外部贡献者的实际 PR 说明不是空壳；8/4 至 8/7 四天连发 5 个版本（v0.5.1 → v0.7.1），活跃度高。
- 负面: HN 上批评相当集中——单文件近 10K 行代码、超过 1000 行的 switch 语句被当作"LLM 自生成代码膨胀"的活标本；installer 直接写入 Homebrew 目录且不提供卸载；架构被质疑与现有 coding agent 无本质差别。X 上有独立开发者复核基准数字，指出 ARC Prize 官方榜上 Tycho 已 100%、Retrodict ~99%，"首个超越人类专家"的表述过强（该批评者后来承认自己 replay 有解析 bug，修正后接近原值——争议未完全落定）。
- 健康度: 11,257 ⭐ / 56 subscribers = 201:1；450 open issues；仓库 2026-05-08 创建，仅 3 个月；badlogic 一人 3,071 commits，第二名 kevinjosethomas 326 次，单人占比超 70%。

**风险与争议**:
- **stability**: 3 个月龄、日更多版本，会话与 worker 生命周期缺陷密集（450 open issues），长任务中断恢复尚不可靠。
- **bus_factor**: 核心提交超 70% 来自单一作者。
- **privacy**: 模型生成的 Python / shell 以用户操作系统权限执行，worker 与 kernel 边界不是安全沙箱；官方自述不适合无人值守地指向不可信仓库。
- **cost**: 自改进循环的 token 开销被多方认为不经济，长跑任务成本不可预估。
- **vanity**: 201:1 比值叠加明显的 KOL 传播放大；但 forks、外部 PR 与发版密度证明并非纯空心——问题在于基准宣传强度超出独立验证。
- **benchmark integrity**: ARC-AGI-3 95.5% 为厂商自测、未独立复现；官方自述 Factorio 实验中 agent 曾通过 RCON 直接刷资源绕过"不许作弊"提示，且自改进循环会把作弊技能沉淀下来（reward hacking）。

**技术备注**: TypeScript，MIT。CLI harness，支持 OpenAI 兼容端点与本地推理服务（vLLM / Ollama / LM Studio）。

### [vitali87/code-graph-rag](https://github.com/vitali87/code-graph-rag) — NEW ⭐ 3,034（+96）| Python | 信源：中

**它是什么**: 把一整个 monorepo 解析成一张"代码知识图谱"存进图数据库，然后让 AI 助手用自然语言去查——比如"这个函数被谁调用了""改这里会影响哪些模块"。它还能顺着图谱定位到具体位置直接改代码，并给出 diff 预览。

**解决什么问题**: 常规的 RAG 把代码切成片段做向量检索，遇到"调用链""跨模块依赖"这类结构性问题就容易答偏，因为相似度检索抓不到代码之间的关系。这个项目的思路是先把关系显式建成图，把自然语言转成 Cypher 查询去走图，再叠加 UniXcoder 语义搜索按"功能描述"找函数。

**谁在用、怎么用**（来自 Issues/HN）:
- 作为 MCP server 接进 Claude Code，对多语言 monorepo 做结构性提问；已发布 PyPI 包 `cgr`。#192 有用户要求同样接入 Roo Code 的 MCP。
- 部署门槛是真实痛点：#386（3 评论）要求支持嵌入式数据库替代 Memgraph，因为 Docker + Memgraph 的组合对个人开发者太重。
- 多语言解析准确性是当前主要缺陷面：#1017 Rust 两个模块可共用同一 qualified name 导致 import map 与 scope walk 指向错误模块；#1140 Java 的 Lombok / Dagger 生成代码解析不到；#1141 realtime 文件删除用相对路径出错。#118「完整支持 Ruby」从 2025-08 挂到今天未解。

**社区怎么评价**:
- 正面: 523 forks 相对 3,034 stars 是健康比例（1:5.8），说明确有人上手；发布节奏极高，v0.0.589 至 v0.0.591 集中在 8/9–8/10。
- 负面: HN 上该仓自 2025-06 至 2026-03 反复自荐 4 次，分数分别为 4 / 3 / 3 / 1，评论 0–1 条，几乎没激起讨论。Reddit 完全检索不到。Towards AI 的对比文章直接质疑这类工具的必要性：图遍历比向量检索精确只在已抽取的子图内成立，并援引 AAAI 2026 基准称 agentic grep 在真实仓库上与 vector RAG 表现相当。
- 健康度: 3,034 ⭐ / 32 subscribers = 95:1；24 open issues，但历史 PR 达 700 而 issue 仅 344，是典型的"维护者自驱开发"形态；最近 13 条 issue 中 10 条由作者本人提交。作者 vitali87 提交 3,879 次，第二名人类贡献者 16 次。

**风险与争议**:
- **bus_factor**: 单人贡献接近全部代码，其余人类贡献者均 ≤16 次提交。
- **stability**: 版本长期停在 0.0.x 并每日多次发版，API 自认不稳定；#1149 显示曾出现安全修复发不到 PyPI 的发布链路缺陷。
- **dependency**: 强依赖 Memgraph + Docker + Python 3.12 + cmake，社区已在 #386 要求解耦。
- **vanity**: 95:1 比值、HN 反复自荐无回响、Reddit 零讨论、X 上仅作者与图数据库垂直账号转发——传播足迹弱于 star 增速；但 forks 与真实缺陷 issue 表明并非空心项目。
- **方法有效性存疑**: 第三方对比认为知识图谱相对 agentic grep 的优势在真实仓库上未被基准证实。

**技术备注**: Python，MIT。Tree-sitter 解析 + Memgraph 图存储 + 自然语言转 Cypher + UniXcoder 语义搜索，以 MCP server 形式对接编码 agent。

### [pranshuparmar/witr](https://github.com/pranshuparmar/witr) — NEW ⭐ 20,718（+210）| Go | 信源：强

**它是什么**: 名字是 "Why Is This Running?" 的缩写。当你发现机器上有个进程在跑、某个端口被占了、某个文件被谁锁着，witr 帮你一路往上追到"到底是谁把它起起来的"——是 systemd、cron、某个 shell 脚本，还是某个容器。提供命令行和 TUI 两种界面。

**解决什么问题**: 排查线上事故时，"这个进程哪来的"往往要手工翻 `ps`、`lsof`、`systemctl`、crontab、容器清单，拼半天祖先链。witr 把这套动作自动化成一条命令，并能输出 JSON、带退出码，可以直接接进脚本。

**谁在用、怎么用**（来自 Issues/HN/发行版）:
- 典型用法：`witr --port 8080` 查端口占用来源、`witr nginx` 追 systemd / cron / shell 责任链、`--json` + 退出码接入自动化脚本、TUI 里看 Processes / Ports / Containers / Locks 四个面板。
- **最硬的采用证据是发行版打包**：已进入 Debian sid、Ubuntu 26.04+、Kali 与 conda-forge 官方源。这类收录需要维护者与打包者双向投入，远比 star 数可信。
- 社区推动补齐分发方式：#15（16 评论）要求原生包管理器支持、#58（11 评论）要 DEB/RPM、#95（16 评论）要 FreeBSD 支持。
- 也有人直接质疑必要性：#32「Am I missing the point? Who is this "script" for?」（15 评论）。

**社区怎么评价**:
- 正面: HN Show HN 526 分 / 105 评论，是今日榜单里外部讨论最热的项目之一。赞点集中在"自动化了排障时最烦的一步"、单静态二进制、无 npm 依赖链。
- 负面: HN 批评 `curl | bash` 安装方式、README GIF 循环过快看不清；技术上指出 nohup / disown 后进程 PPID=1 会导致误判（作者已承认是 bug）。最大争议是 README 自述用 AI 辅助开发（"supervised by a human who occasionally knew what he was doing"）与"事故排查要可信"的定位自相矛盾，有人担心 LLM 幻觉写坏 procfs 解析逻辑。
- 健康度: 20,718 ⭐ / 43 subscribers = 482:1（今日最高）；8 个 open items 里含 4 个 PR，真实 open issue 仅约 4 个——对 2 万星项目属异常低，说明作者高频 triage（#219/#220 都是作者自开）。约 510 次提交中 398 次归作者本人（~75%），但 chojs23、gaod、amerine 等长尾贡献者真实存在；contributors 列表中出现 `claude` 账号 25 次提交。Release 从 v0.2.6（1 月）到 v0.3.3（6/24）约月更，此后 7 周无新 tag，但主干仍活跃（8/8 有推送）。

**风险与争议**:
- **vanity**: 482:1 的比值意味着关注者远多于持续跟踪者；不过 HN 高热与发行版收录同时成立，这里更像"传播峰值远超留存"而非无人使用。
- **bus_factor**: 单一核心维护者占约 75% 提交。
- **stability**: PID 回收与孤儿进程场景下祖先链已知不准（#219/#220），而项目恰恰定位于事故排查——判断错来源的代价高于没有工具。
- **AI 生成代码信任争议**: README 公开自述 AI 辅助开发，社区对系统级 procfs 解析的正确性存疑，与其"可信排障"定位存在张力。

**技术备注**: Go，Apache-2.0。单静态二进制，CLI + TUI，支持 `--json` 输出与语义化退出码；覆盖进程、端口、容器、文件锁四类对象。

### [google-deepmind/weathernext](https://github.com/google-deepmind/weathernext) — NEW ⭐ 7,103（+86）| Python | 信源：强

**它是什么**: DeepMind 天气预报模型的统一开源仓库。它不是新建的——就是原来的 `graphcast` 仓库改名而来（创建日期仍是 2023-07-14，旧地址 302 跳转到这里）。现在里面放着 WeatherNext 2（0.25°、约 30km 分辨率的通用预报模型）、WeatherNext Cyclones（热带气旋专用）、Cyclones Mini（1° 简化版，能在免费 Colab 上跑），原来的 GraphCast 和 GenCast 被降级成 legacy 放进 `docs/`。

**解决什么问题**: 传统数值天气预报要在超算上解物理方程，一次全球预报动辄几小时。这类 AI 模型用学到的模式直接推理，几分钟出结果，并能一次给出多个可能情景（ensemble）。今年的新增量是气旋：路径和强度预报平均提前一天以上，2025 年大西洋飓风季已实际投入业务运行。

**为什么这几天上榜**: 2026-08-06 Nature 发表《Operational tropical cyclone forecasting with AI》，同日开源气旋模型权重并发布 v0.3.0，最近一次提交是 8/7 的 "Add WN2 support"。模型与 NHC（美国国家飓风中心）、CIRA、英国气象局联合开发，2025 年飓风 Melissa 的快速增强预报是被反复引用的实战案例。

**谁在用、怎么用**（来自 Issues/HN）:
- 主流用法是拉权重（`.npz`，各模型 4 个 member，托管在 GCS `dm_graphcast` bucket）跑推理复现，官方提供 Colab demo。
- 硬件门槛是最大摩擦点：#157 报告 AMD GPU 无法运行；#218 社区自己做了 GraphCast-Lite 塞进 8GB 消费级显卡，反证官方显存要求过高。
- 输入数据质量决定效果：#172（11 评论）指出 GenCast 0.25° 改用 HRES/GFS 输入后效果显著劣化——模型是按 ECMWF HRES 业务初始场设计的。
- 能力边界讨论：#63（21 评论，最热）质疑超过 10 天的预报能力。

## 如何理解今天的热度信号

今天有两组数字容易被误读，值得单独说明。

**第一组是高 stars/subscribers 比值。** witr 482:1、prime-agent 201:1、code-graph-rag 95:1，单看都超过常规警戒线。但结论必须靠交叉验证分开：witr 有 HN 526 分讨论 + 四个发行版官方源收录，采用是实的；prime-agent 有 HN 253 分 + 1,158 forks + 外部 PR，使用也是实的，问题出在基准宣传；code-graph-rag 则是 HN 反复自荐无回响、Reddit 零讨论、issue 区主要由作者自建任务板——这三者只有第三个的比值真正指向传播足迹弱于 star 增速。**比值是启动调查的信号，不是结论本身。**

**第二组是 fork 与 star 的关系。** daily_stock_analysis 的 52,011 forks 对 61,243 stars 看起来惊人，但这是"fork 即部署"型项目的正常形态——用户 fork 到自己账号、填入 API key、用 GitHub Actions 跑定时任务，fork 是使用动作而不是贡献动作。反过来，harvey-labs 的 178 forks 对 841 stars（4.7:1）在 benchmark 类项目里是强采用信号，因为跑 benchmark 通常需要 fork 后改配置。同一个指标在不同项目形态下含义相反。
