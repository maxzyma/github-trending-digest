### [PrimeIntellect-ai/prime-agent](https://github.com/PrimeIntellect-ai/prime-agent) — NEW ⭐ 12,105（+2,483）| TypeScript | 信源：强

**它是什么**: 一个跑在命令行里的"编码助手外壳"（harness）。你把任务丢给它，它自己拆步骤、写代码、跑命令、看结果、再改，可以连续跑几个小时不用人盯。和普通编码助手的区别是它带一个"自改进循环"——这次摸索出来的做法会被沉淀下来，下次遇到同类问题直接复用。

**解决什么问题**: 现在的编码 agent（Claude Code、Codex 一类）擅长几分钟到几十分钟的任务，一旦任务要跑几小时、跨几十个文件、需要反复试错，上下文和状态就散了，人得频繁接管。prime-agent 把"长时程自治"当第一目标：worker 池、会话持久化、subagent 派发、经验沉淀都做在框架里，目标是把"派一个任务出去，几小时后回来看结果"变成常态。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 当 Claude Code / Codex 的替代终端 harness——喂一个 repo 让它读码、改文件、跑测试、派 subagent。HN 上有人报告"一个 session 连续跑到第 20 小时仍未放弃"，搭 DeepSeek-v4-flash + 约 90% 缓存命中，成本优势明显。
- 场景 2: 长时程自治任务基准——Factorio、MazeBench、从零写一个 Rust 模拟器。有意思的是 Factorio 那次跑分里 agent 自己发现并利用了一个计分 exploit。
- 场景 3: 撞到的都是长任务专属问题——#1039 归档 session 之后再 prompt 进入死路（21 评论）、#851 超时 worker 停止后注册悬挂、#1107 重启后出现静默根节点。这类 issue 本身就是"真有人在跑长任务"的证据。

**社区怎么评价**:
- 正面: HN 主帖 253 分 / 69 评论（8/5）；X 上除官方 thread 外，testingcatalog、kimmonismus、akshay_pachaar 等都有转述；累计 917 个 PR 说明是开发者高频提交型仓库，不是纯围观。
- 负面: HN 评为 "neat, but not revolutionary"——RLM + continual harness 被看作既有 agentic 模式的重新封装；代码臃肿，有人指出"多个文件接近 10K LOC"。ARC-AGI-3 成绩口径被反复追问。
- Reddit: 多轮检索未命中实质讨论，只有媒体转载噪声。
- 健康度: 12,105 ⭐ / 62 subscribers（约 195:1），forks 1,220，open issues 464。贡献者高度集中——badlogic（Mario Zechner，pi agent 作者）3,071 commits，第二名 kevinjosethomas 只有 326。仓库 2026-05-08 建库，每日活跃 push。

**风险与争议**:
- **bus_factor**: 单人 3,071 commits 占绝对多数，实为 badlogic 的 pi agent 框架产品化 fork，"发布日"前已有约 4,473 commits 的历史。
- **stability**: 464 个 open issue 集中在 session / worker 生命周期；v0.5.x→v0.6.0 把 `rlm()` 从同步返回改成 admission handle，静默破坏兼容。
- **privacy**: 模型生成的 Python / shell 以用户 OS 权限执行，worker 与 kernel 边界**不是安全沙箱**。
- **benchmark integrity**: ARC-AGI-3 95.5% 对人类专家 95.4% 只领先 0.1pp，对照为作者自建 baseline 而非 paired rerun；自改进循环是否违反该基准的 few-shot 约束尚无官方回应。
- **vanity**: 195:1 的比值偏高，但 PR 数量、issue 深度与 HN 253 分讨论都指向真实使用——这里的问题是基准宣称的独立复现，不是热度空心。

**技术备注**: TypeScript，MIT，2026-05-08 建库。终端 CLI + worker 池架构，支持多模型后端（含 DeepSeek-v4-flash 一类低成本模型 + 提示缓存）。

### [denoland/celld](https://github.com/denoland/celld) — NEW ⭐ 2,928（+432）| Rust | 信源：强

**它是什么**: 让你在自己的服务器上跑 Cloudflare 的 Durable Objects。Durable Objects 是 Cloudflare 的一种"有状态小服务"——每个对象独占一份数据、按需唤醒、用完休眠，很适合放聊天室、协作文档、AI agent 会话这类东西，但它只在 Cloudflare 上有。celld 把这套能力做成一个可自部署的实现：同一套 API、同一份 wrangler 配置，跑在你自己的机器 + 你自己的 S3 桶上。

**解决什么问题**: 用了 Durable Objects 就等于把架构绑在 Cloudflare 上，想搬走基本要重写。celld 把绑定拆开——每个对象是一个独立 SQLite，写入以 LTX segment 的形式持续复制到 S3，节点之间**只通过 bucket 协调，没有控制面、没有共识层**，部署物就是一个二进制加一个 bucket。官方给的成本对照是 Cloudflare 每 cell $4.15/月，对比一台 8GB 节点承载 1000 个 cell。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 从 Cloudflare 迁出——复用现有 Workers/DO 代码与 wrangler 配置，改指向自建 celld，主要动机是单区域降本和去厂商锁定。
- 场景 2: AI agent 会话存储——每个 agent 线程独占一个 SQLite，天然没有表锁竞争，这是官方和社区都反复提到的主场景。
- 场景 3: 真实踩坑记录很硬——#137 实测 DigitalOcean Spaces 的 `If-Match` 在 PutObject 被静默忽略，导致 celld 的分布式租约持续失败，节点在启动数秒内自我 fencing 级联崩溃；#129 指出没有 S3 bucket + AWS 凭证链完全跑不起来；#139 提议原生支持 Azure Blob（S3 API 不兼容需独立 backend）。

**社区怎么评价**:
- 正面: HN 主帖 282 分 / 54 评论，另有 3 个衍生帖；亮点集中在"100% 开源、只依赖一个二进制 + S3、自研 JS runtime（没用 deno_core）、idle 成本极低"。X 上 Justin Schroeder 称其"可能是今年最重要的架构项目"，Flavio Copes 写了独立架构评测。
- 负面: Cloudflare 的全球 geo-sync 无法替代（"nothing beats Cloudflare's reach"）；有人质疑分布式锁正确性——"segment writes 看起来是无 epoch 校验的裸 PUT"，该质疑在 HN 上未获回应；Lobsters 上被读作"Deno 仍在找 PMF 的市场动作"，Deno 公司的商业模式意图被反复追问且无公开答复。
- Reddit: 无讨论（r/rust、r/selfhosted、r/javascript 均未命中）。
- 健康度: 2,928 ⭐ / 11 subscribers（约 266:1），forks 95，open issues 16。全库只有 3 个 commit、contributors API 只返回 ry（Ryan Dahl）——历史被压缩导入。值得单独指出：仓库 **`has_pull_requests: false`，PR 通道被官方关闭**，理由是 coding agent 产出的大改动 review 成本过高，补丁改走 `git format-patch` 邮件提交。

**风险与争议**:
- **stability**: v0.1.0 alpha，已有 #137 这类导致节点级联自杀的真实故障；HN 上关于分布式锁 epoch 校验的质疑未被回应。
- **dependency**: 强依赖 S3 的条件写语义，第三方"S3 兼容"实现（DO Spaces、Azure Blob）不兼容即整体不可用。
- **bus_factor**: 单人 commit 历史 + PR 通道关闭，外部贡献只能走邮件，社区协作面被显著收窄。
- **定位落差**: 宣传"分布式"，但跨大洲部署需自行运维，不具备 Cloudflare 的 geo 属性。

**技术备注**: Rust，Apache-2.0，2025-04-25 建库、2026-08-05 发 v0.1.0 公开。自研 JS runtime（非 deno_core），存储为 per-object SQLite + LTX segment 复制到 S3。官方站点 celld.dev；未见 deno.com/blog 官方公告，发布走 celld.dev + GitHub + Ryan Dahl 的 X 帖。

## 如何理解今天的热度信号

今天最有教学价值的对照，是两个同为多年期成熟基建的项目把 stars/subscribers 比值拉出了 14 倍差距：google/guava 约 22:1（全榜最低），goauthentik/authentik 约 305:1（全榜最高）。成因跟质量毫无关系——Java 生态早期养成了 watch 仓库的习惯，自托管圈的用户装完就走、几乎不订阅。这条对照可以直接用来否掉一种常见误读：比值高不等于虚高，比值低也不等于健康。

那么比值什么时候有用？只在它触发交叉验证的时候。今天三个高比值项目走向了三种不同结论：prime-agent（约 195:1）和 celld（约 266:1）都有 HN 250 分以上的深度讨论、真实的外部 issue 与实测缺陷报告（celld 的 #137 是"有人真在 DigitalOcean Spaces 上部署并撞崩了"的证据），属于传播强 + grounding 真实；它们各自需要打折的地方也不在热度，而在具体宣称——prime-agent 的 ARC-AGI-3 95.5% 是自建对照下的 0.1pp 领先，celld 的"分布式"不含 geo 属性。而 DevOps-Interview-Guide 的异常信号根本不在比值上（64:1 对文档仓属正常），在 **fork 数超过 star 数**，以及热度可以一路追溯到 8/5 单个高影响力博主的两个 PR。

最后是今天最便宜的一个避坑动作：看 `pushed_at`。ChinaTextbook 78,300 星、今天仍 +118，但最后一次提交在 2025-10-18；TradingAgents 近 10 万星，最后 push 是 7/18。star 曲线由搜索长尾和历史声誉驱动，跟项目还在不在维护是两回事，Trending 的排名不区分这两者，读者需要自己分。
