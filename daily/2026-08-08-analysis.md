### [PrimeIntellect-ai/prime-agent](https://github.com/PrimeIntellect-ai/prime-agent) — NEW ⭐ 12,136（+2,293）| TypeScript | 信源：强

**它是什么**: 一个跑在命令行里的"编码助手外壳"（harness）。你把任务丢给它，它自己拆步骤、写代码、跑命令、看结果、再改，可以连续跑几个小时不用人盯。和普通编码助手的区别是它带一个"自改进循环"——这次摸索出来的做法会被沉淀下来，下次遇到同类问题直接复用。

**解决什么问题**: 现在的编码 agent（Claude Code、Codex 一类）擅长几分钟到几十分钟的任务，一旦任务要跑几小时、跨几十个文件、需要反复试错，上下文和状态就散了，人得频繁接管。prime-agent 把"长时程自治"当第一目标：worker 池、会话持久化、subagent 派发、经验沉淀都做进框架，目标是把"派一个任务出去，几小时后回来看结果"变成常态。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 当 Claude Code / Codex 的替代终端 harness——喂一个 repo 让它读码、改文件、跑测试、派 subagent。HN 上有人报告"一个 session 连续跑到第 20 小时仍未放弃"，搭低成本模型 + 约 90% 缓存命中，成本优势明显。
- 场景 2: 长时程自治任务基准——Factorio、MazeBench、从零写一个 Rust 模拟器；Factorio 那次跑分里 agent 自己发现并利用了一个计分 exploit。
- 场景 3: 撞到的都是长任务专属问题——#1039 归档 session 之后再 prompt 进入死路（21 评论）、#851 超时 worker 停止后注册悬挂、#1046 worker 身份校验与心跳残留。这类 issue 本身就是"真有人在跑长任务"的证据。

**社区怎么评价**:
- 正面: HN 主帖 253 分 / 69 评论（8/5），另有多条衍生投稿；X 上 testingcatalog、kimmonismus、akshay_pachaar 等均有转述；PR 数量级说明是开发者高频提交型仓库，不是纯围观。
- 负面: HN 评为 "neat, but not revolutionary"——RLM + continual harness 被看作既有 agentic 模式的重新封装；代码臃肿，有人指出"多个文件接近 10K LOC"。ARC-AGI-3 成绩口径被反复追问。
- Reddit: 多轮检索未命中实质讨论，只有媒体转载噪声。
- 健康度: 12,136 ⭐ / 62 subscribers（约 196:1），forks 1,223，open issues 464，8/10 仍在每日 push。贡献者高度集中在 badlogic（Mario Zechner，pi agent 作者）。

**风险与争议**:
- **bus_factor**: 单人 commit 占绝对多数，实为 badlogic 的 pi agent 框架产品化 fork，"发布日"前已有数千 commit 的历史。
- **stability**: 464 个 open issue 集中在 session / worker 生命周期；v0.5.x→v0.6.0 把 `rlm()` 从同步返回改成 admission handle，静默破坏兼容。
- **privacy**: 模型生成的 Python / shell 以用户 OS 权限执行，worker 与 kernel 边界**不是安全沙箱**。
- **benchmark integrity**: ARC-AGI-3 95.5% 对人类专家 95.4% 只领先 0.1pp，对照为作者自建 baseline 而非 paired rerun；自改进循环是否违反该基准的 few-shot 约束尚无官方回应。

**技术备注**: TypeScript，MIT，2026-05-08 建库。终端 CLI + worker 池架构，支持多模型后端与提示缓存。

### [denoland/celld](https://github.com/denoland/celld) — NEW ⭐ 2,929（+516）| Rust | 信源：强

**它是什么**: 让你在自己的服务器上跑 Cloudflare 的 Durable Objects。Durable Objects 是 Cloudflare 的一种"有状态小服务"——每个对象独占一份数据、按需唤醒、用完休眠，很适合放聊天室、协作文档、AI agent 会话，但它只在 Cloudflare 上有。celld 把这套能力做成可自部署的实现：同一套 API、同一份 wrangler 配置，跑在你自己的机器 + 你自己的 S3 桶上。

**解决什么问题**: 用了 Durable Objects 就等于把架构绑在 Cloudflare 上，想搬走基本要重写。celld 把绑定拆开——每个对象是一个独立 SQLite，写入以 LTX segment 持续复制到 S3，节点之间**只通过 bucket 协调，没有控制面、没有共识层**，部署物就是一个二进制加一个 bucket。官方成本对照是 Cloudflare 每 cell $4.15/月，对比一台 8GB 节点承载 1000 个 cell。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 从 Cloudflare 迁出——复用现有 Workers/DO 代码与 wrangler 配置，改指向自建 celld，动机是单区域降本与去厂商锁定。
- 场景 2: AI agent 会话存储——每个 agent 线程独占一个 SQLite，天然没有表锁竞争，是官方和社区都反复提到的主场景。
- 场景 3: 真实踩坑记录很硬——#137 实测 DigitalOcean Spaces 的 `If-Match` 在 PutObject 被静默忽略，导致分布式租约持续失败、节点在启动数秒内自我 fencing 级联崩溃；#129 指出没有 S3 bucket + AWS 凭证链完全跑不起来；#139 提议原生支持 Azure Blob。

**社区怎么评价**:
- 正面: HN 主帖 282 分 / 54 评论（8/5），另有多个衍生帖；亮点集中在"100% 开源、只依赖一个二进制 + S3、自研 JS runtime、idle 成本极低"。X 上 Justin Schroeder 称其"可能是今年最重要的架构项目"，Flavio Copes 写了独立架构评测。
- 负面: Cloudflare 的全球 geo-sync 无法替代（"nothing beats Cloudflare's reach"）；有人质疑分布式锁正确性——"segment writes 看起来是无 epoch 校验的裸 PUT"，该质疑在 HN 上未获回应；Lobsters 上被读作"Deno 仍在找 PMF 的市场动作"。
- Reddit: 无讨论（r/rust、r/selfhosted、r/javascript 均未命中）。
- 健康度: 2,929 ⭐ / 11 subscribers（约 266:1），forks 95，open issues 16。commit 历史被压缩导入、contributors 仅 ry（Ryan Dahl）。值得单独指出：仓库 **PR 通道被官方关闭**，理由是 coding agent 产出的大改动 review 成本过高，补丁改走 `git format-patch` 邮件提交。

**风险与争议**:
- **stability**: v0.1.0 alpha，已有 #137 这类导致节点级联自杀的真实故障；HN 上关于分布式锁 epoch 校验的质疑未被回应。
- **dependency**: 强依赖 S3 的条件写语义，第三方"S3 兼容"实现（DO Spaces、Azure Blob）不兼容即整体不可用。
- **bus_factor**: 单人 commit 历史 + PR 通道关闭，外部贡献只能走邮件。
- **定位落差**: 宣传"分布式"，但跨大洲部署需自行运维，不具备 Cloudflare 的 geo 属性。

**技术备注**: Rust，Apache-2.0，2025-04-25 建库、2026-08-05 发 v0.1.0 公开。自研 JS runtime（非 deno_core），存储为 per-object SQLite + LTX segment 复制到 S3；官方站点 celld.dev。

### [pranshuparmar/witr](https://github.com/pranshuparmar/witr) — NEW ⭐ 21,039（+234）| Go | 信源：强

**它是什么**: 名字是 "Why Is This Running?" 的缩写。当你发现机器上有个进程在跑、某个端口被占了、某个文件被谁锁着，witr 帮你一路往上追到"到底是谁把它起起来的"——是 systemd、cron、某个 shell 脚本，还是某个容器。提供命令行和 TUI 两种界面。

**解决什么问题**: 排查线上事故时，"这个进程哪来的"往往要手工翻 `ps`、`lsof`、`systemctl`、crontab、容器清单，拼半天祖先链。witr 把这套动作自动化成一条命令，并能输出 JSON、带语义化退出码，可以直接接进脚本。

**谁在用、怎么用**（来自 Issues/HN/发行版）:
- 典型用法：`witr --port 8080` 查端口占用来源、`witr nginx` 追 systemd / cron / shell 责任链、`--json` + 退出码接入自动化脚本、TUI 里看 Processes / Ports / Containers / Locks 四个面板。
- **最硬的采用证据是发行版打包**：已进入 Debian sid、Ubuntu 26.04+、Kali 与 conda-forge 官方源。这类收录需要维护者与打包者双向投入，远比 star 数可信。
- 社区推动补齐分发方式：#15（16 评论）要求原生包管理器支持、#58（11 评论）要 DEB/RPM、#95（16 评论）要 FreeBSD 支持；也有人直接质疑必要性：#32「Am I missing the point?」（15 评论）。

**社区怎么评价**:
- 正面: HN Show HN 526 分 / 105 评论，是本周外部讨论最热的项目之一。赞点集中在"自动化了排障时最烦的一步"、单静态二进制、无依赖链。
- 负面: HN 批评 `curl | bash` 安装方式、README GIF 循环过快；技术上指出 nohup / disown 后进程 PPID=1 会导致误判（作者已承认是 bug）。最大争议是 README 自述用 AI 辅助开发，与"事故排查要可信"的定位存在张力。
- 健康度: 21,039 ⭐ / 43 subscribers（约 489:1，今日全榜第二高）；open items 仅 9 且含多个 PR，真实 open issue 极少——对 2 万星项目属异常低，说明作者高频 triage。主干活跃（8/8 有推送），但自 v0.3.3（6/24）后约 7 周无新 tag。

**风险与争议**:
- **vanity**: 489:1 意味着关注者远多于持续跟踪者；不过 HN 高热与发行版收录同时成立，更像"传播峰值远超留存"而非无人使用。
- **bus_factor**: 单一核心维护者占约 75% 提交。
- **stability**: PID 回收与孤儿进程场景下祖先链已知不准，而项目恰恰定位于事故排查——判断错来源的代价高于没有工具。
- **AI 生成代码信任争议**: README 公开自述 AI 辅助开发，社区对系统级 procfs 解析的正确性存疑。

**技术备注**: Go，Apache-2.0，2025-12-20 建库。单静态二进制，CLI + TUI，支持 `--json` 输出与语义化退出码；覆盖进程、端口、容器、文件锁四类对象。

### [unclebob/swarm-forge](https://github.com/unclebob/swarm-forge) — NEW ⭐ 2,079（+81）| Clojure | 信源：中

**它是什么**: Robert C. Martin（Uncle Bob，《Clean Code》作者）自己写的多 AI agent 协作工具。它不是一个框架，而是一套 shell 脚本：给每个 agent 角色分配一个独立的 git worktree 和一个 tmux 窗格，让它们在同一个项目上同时干活又互不覆盖，彼此之间靠消息传递沟通。

**解决什么问题**: 多个 coding agent 同时改一个仓库，最直接的麻烦是互相踩文件、改动无法审计、谁负责哪一步说不清。swarm-forge 用最土的办法回避了这些：worktree 做物理隔离，tmux 做可视化，然后把工作流固定成 specifier → coder → cleaner → architect → hardener → QA 的角色链。更关键的是它带一部 "Constitution"——TDD、变异测试、DRY、CRAP（Change Risk Analysis and Predictions）复杂度门禁被写成所有 agent 都必须遵守的条款，也就是把 Uncle Bob 三十年讲的那套工程纪律直接编码成 agent 的行为约束。可选拓扑有 `two-pack` / `four-pack` / `six-pack` 三档，分别放在不同分支上。

**谁在用、怎么用**（来自 Issues/X/Clean Coders）:

## 如何理解今天的热度信号

今天这张榜恰好把 stars/subscribers 比值的整个跨度铺满了：最低是 google/guava 的 22:1，最高是 jdx/mise 的 716:1，中间还有 witr 489:1、grok2api 426:1、computer 328:1、authentik 305:1。**而比值最高的那个恰恰是全榜最没有争议的项目之一**——mise 是 2023 年建库、8 月头一周连发四个版本、open issue 只有 45 的开发者日用工具。它比值高的唯一原因是个人开发者装完就用，不会去 watch 仓库。反过来，guava 的 22:1 也不代表更健康，只是 Java 生态早年养成了 watch 的习惯。所以比值不是结论，只是"要不要往下查"的触发器。

真正能分辨真假的是三类不对称信号。**第一类是第三方投入**：witr 进了 Debian sid、Ubuntu 26.04+、Kali 和 conda-forge 官方源——发行版收录需要维护者和打包者双向投入，这是刷不出来的；celld 有 HN 282 分讨论和 #137 那种"有人真在 DigitalOcean Spaces 上部署把节点跑崩了"的实测故障报告。**第二类是 issue 的提交者结构**：semantica 的 issue 列表看上去很扎实——测试覆盖缺口、SSRF 未防护、静默吞异常——但翻一下作者就会发现几乎全部由本仓第二大贡献者自己开出，是团队自查清单而非用户反馈。工程自律值得肯定，但它证明不了"有人在用"。**第三类是 `pushed_at`**：Legendary_OSINT 今天 1,653 ⭐、+109，但最后一次提交在 2026-04-17，同时有五个以上"补充工具"的 PR 挂了数月没人合——对一份靠时效性活着的工具清单，这比比值重要得多。

另外两件容易被大数字盖过去的事。一是 **AutoGPT 的双许可**：18.6 万星、"开源 agent 鼻祖"的印象很强，但 `autogpt_platform/` 目录整体采用 Polyform Shield License，不是 OSI 开源许可，明确禁止用于竞争性产品，只有该目录之外才是 MIT。二是 **swarm-forge 完全没有 license 文件**，默认全权保留——它的 52:1 比值在今天属于最健康的一档，但企业要拿它做内部工具链前，先要解决的是授权而不是技术问题。今天这两条加上 MiroFish 的 AGPL-3.0，是比热度更值钱的三条读榜信息。
