### [NVIDIA/auto-ontology](https://github.com/NVIDIA/auto-ontology) — NEW ⭐ 5,156（+2,050）| Python | 信源：中

**它是什么**: 一个放在企业数据库旁边的"业务词典"。它读取库里有哪些表、字段和关系，自动起草一份文档，写明"营收""活跃客户"这类指标在哪张表、怎么算、口径从哪来。业务人员审核通过后，AI Agent 回答问题前先查这份词典，再生成查询，给出的数字附带出处。

**解决什么问题**: 让 Agent 直接查库，它常常连对了库却算错了数，因为同一个指标在财务系统和销售系统里定义不同。过去的办法是数据团队手写语义层或指标平台，维护成本高。auto-ontology 让机器先起草、人再核准，词典建一次，多个 Agent 共用。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 企业数据分析 Agent 的自然语言查数，官方用 Wide World Importers 示例库演示；接入方式有 MCP、CLI、API，自带 Web UI，可用 Helm 或 Docker 部署。
- 场景 2: 用户在请求接入自家数据仓库，如 BigQuery（#410）、Microsoft Fabric（#406）、DolphinDB（#407）；外部 PR 在适配 OpenAI 风格的 embedding 接口（#411）、修 DuckDB 主外键识别（#395）。
- 场景 3: X 上有一位开发者评估后决定不用，理由是"模式对，但对 1 个库、约 20 个指标来说太重"，说明它更适合指标多、系统多的团队。

**社区怎么评价**:
- 正面: HN 主帖（288 分、142 条评论）里，支持者看重它给"官方认可的数据集"立口径的治理价值。11-04 仓库把默认模型换成了 Nemotron 3.5，提交很活跃。
- 负面: HN 评论集中批评 README 难懂、示意图有错，质疑"用不可靠的 Agent 去修不可靠的 Agent"，以及为何不用 OWL/RDF 等成熟标准。#408 报告 Postgres、MySQL、SQLite 连接器在结果列重名时返回错误数据；#403 指出文档里还留着"仓库是 NVIDIA 内部的、需要凭据"的说明。HN 上没有人报告实际跑过。
- 健康度: 31 个关注者，stars/subscribers 约 166:1；没有正式 release；真实 issue 33 个，大多是 11-03 后新开的，另有 15 个 PR 未合。前 5 位贡献者（NVIDIA 员工）占约 93% 提交，README 写明暂不接受外部贡献。

**风险与争议**:
- **dependency**: 默认路径调用 NVIDIA NIM，需要 NVIDIA API key；可以换自托管模型，但要自己配置。
- **stability**: 没有发布版本，已知 bug 会返回错误数据（#408），不适合直接接生产查询。
- **bus_factor**: 开发全在 NVIDIA 内部团队，外部 PR 暂不接收，社区对路线没有话语权。
- **vanity**: "本体构建耗时降 90%"是内部测试数字，没有方法说明；仓库也没公布文本转 SQL 的准确率。

**技术备注**: Python，支持 Postgres、MySQL、SQLite、DuckDB 等连接器；MCP 接入；仓库 2026-04 创建，据报道在 10 月 GTC Berlin 作为 NVIDIA Agent 知识基础组件发布（转述，未见官方原文），11-03 登上 HN 首页后进入 Trending。

**解决什么问题**: 团队想要 AI 辅助评审，又不想把代码交给托管 SaaS。PR-Agent 可以自己部署，通过 LiteLLM 接任意模型，支持 GitHub、GitLab、Bitbucket、Azure DevOps、Gitea。今天值得关注的是归属变化：它原本是 Qodo（前身 CodiumAI）的开源项目，Qodo 在 2026-04-23 宣布交给社区，由三人治理委员会维护，打算以后捐给基金会，具体是哪家还没定。

**谁在用、怎么用**（来自 Issues/Qodo 博客/第三方报道）:

### [FareedKhan-dev/kimi-k3-in-c](https://github.com/FareedKhan-dev/kimi-k3-in-c) — NEW ⭐ 10,332（+351）| C | 信源：中

**它是什么**: 用纯 C 语言写的 Kimi K3 推理程序，能在一台只有 8GB 内存、没有显卡的电脑上跑完整的 2.78 万亿参数模型。Kimi K3 是月之暗面 2026-07 发布、07-27 开放权重的大模型。

**解决什么问题**: 万亿参数模型通常要多张高端 GPU 才能跑。这个项目利用混合专家（MoE）模型每次只激活少数专家的特点：常驻部分按内存预算留在内存里，约 1.45TB 的专家权重放在 NVMe 硬盘上按需读取。官方权重本身就是 4-bit（MXFP4），程序直接用它计算，没有再做压缩。它证明了"能跑"，代价是极慢：8GB 内存约 26.5 秒出一个 token，128GB 内存约 5.6 秒。

**谁在用、怎么用**（来自 Issues/X）:
- 场景 1: 学习 MoE 流式推理和纯 C 实现。社区 PR 集中在性能和移植，#25 让 MXFP4 矩阵乘提速约 1.6 倍，#32 加 AVX2，#36 移植 Windows，#55 加聊天交互。
- 场景 2: 想实际跑的人卡在存储上。#18 有人问"你是说要下 1.7TB？"，#3 请求更小的权重，作者回复专家已是 4-bit，没有再压缩的空间。
- 场景 3: #21 有人在 M1 Pro 上测试全部通过，但仓内诊断脚本在 macOS 上拒绝运行流式引擎，实际只支持 Linux。

**社区怎么评价**:
- 正面: X 上传播很广，有转发帖约 34.6 万浏览，评价多是"漂亮的工程证明"；仓库有 CI、测试，README 称 13 层同结构模型与 PyTorch 参考输出逐位一致。
- 负面: HN 上 3 个帖子都只有 2–4 分；没有找到第三方贴出完整 1.56TB 权重的实跑结果。
- 健康度: 93 个关注者，stars/subscribers 约 111:1；1,631 forks。作者提交 84 次，其他人各 1–3 次；最后一次推送在 10-02，已一个月没有更新。

**风险与争议**:
- **cost**: 需要约 1.56TB 权重加 109GB 打包文件和高速 NVMe，存储门槛绕不开。
- **stability**: 流式推理实际只支持 Linux，与 README 的跨平台描述有出入（#21）。
- **bus_factor**: 作者一人主导，近一个月无提交。

**技术备注**: C99，不依赖 BLAS、框架或 GPU，Apache-2.0；使用 O_DIRECT 从 NVMe 读取专家权重。README 写每 token 激活约 104B 参数，Hugging Face 博客写约 50B，两者未核实哪个准确。

### [JiaFeiMiao-K-Cat/DiscImageStudio](https://github.com/JiaFeiMiao-K-Cat/DiscImageStudio) — NEW ⭐ 6,647（+1,778）| C# | 信源：强

**它是什么**: 用普通电脑刻录机，把一张图片"刻"在空白 CD、DVD 或单层 BD-R 的数据面上，刻完肉眼能看到图案。它做的是盘面艺术，不是抓轨或镜像转换。

**解决什么问题**: 以前要在光盘上做图案，得买支持 LightScribe、LabelFlash 的专用光驱和专用盘，这些硬件都已停产。DiscImageStudio 只用软件：导入图片、排版、调灰度，导出 ISO、RAW 或 WAV+CUE 交给 ImgBurn 等工具刻录，也能直接刻（实验功能）。关键一步是标定：先刻一张测试盘，拍照取点，软件算出这款盘片的轨距参数，否则图案会扭曲。

**谁在用、怎么用**（来自 Issues/HN/媒体）:
- 场景 1: 做纪念盘、礼物盘和复古折腾。v1.3.6 的 Windows 版下载 6,416 次，三个版本合计约 9,900 次。
- 场景 2: 用户在共建盘片参数库，#87 提交铼德 DVD-R 参数，#78 提交威宝 CD-RW 参数；#49 有用户写了标定教程并做了配套工具（20 条评论）。
- 场景 3: 新手卡在标定上，#65 有人"已经花费 20 张碟片"仍越校越偏，#25 两种方式刻 CD-R 都看不到图案（17 条评论）。

**社区怎么评价**:
- 正面: HN 主帖 358 分、78 条评论，以好评为主；IT之家 11-03 报道，Adafruit、Korben 跟进，另有两个英文翻译 fork。
- 负面: HN 上做过类似实验的人说标定很难做稳；图案占用数据区，可存数据会变少，媒体提醒这类盘不要用作重要备份。
- 健康度: 14 个关注者，stars/subscribers 约 475:1，偏高，但下载量和 issue 讨论说明有真实使用。主要贡献者两人（38、27 次提交），也有外部 PR（#98）；11-04 仍在推送 v1.4.0。

**风险与争议**:
- **stability**: 直接刻录是实验功能，标定失败就报废盘片（#65、#25）。
- **dependency**: 效果取决于盘片、刻录机型号和固件；Linux、macOS 只有命令行版，不能直接刻。
- **bus_factor**: 核心开发集中在两人。

**技术备注**: C#，GPL-3.0；CD 交织代码来自 arduinocelentano/cdimage，仓库已声明衍生关系。11-02 起提供 Linux/macOS 命令行版。

### [Thysrael/Horizon](https://github.com/Thysrael/Horizon) — NEW ⭐ 12,528（+121）| Python | 信源：中

**它是什么**: 一个自己部署的"AI 新闻雷达"。它每天从 Hacker News、Reddit、RSS、Telegram、GitHub 等来源抓内容，让 AI 给每条打分、去重，补上背景和评论区摘要，生成中英双语日报，发到网页、邮件、飞书、钉钉或 Slack。

**解决什么问题**: 关注的信息源太多，每天刷不过来。Horizon 让你 fork 仓库、填上自己的模型密钥，用 GitHub Actions 每天自动出一份简报。模型可选 Claude、GPT、Gemini、DeepSeek、豆包、Ollama 等，用本地 Ollama 可以不花 API 费。

**谁在用、怎么用**（来自 Issues/fork 部署）:
- 场景 1: 大量个人 fork 部署了自己的日报页，也有人改成飞书推送；用户以中文开发者为主。
- 场景 2: 部署问题集中在网络和配置，#89、#98 是 Docker 容器没走代理导致抓不到 Reddit，#42 是 MiniMax 地址未配置，#51 是钉钉机器人收不到消息。
