## 新上榜项目

### [akitaonrails/ai-memory](https://github.com/akitaonrails/ai-memory) — NEW ⭐ 2,121（+207）| Rust | 信源：中

**它是什么**: 给 AI 编码助手用的长期记忆。你在 Claude Code 里干到一半退出，换 OpenAI Codex 在同一个目录继续，它让第二个 agent 不用你重新解释这个项目的架构、你们已经试过但失败的方案、以及还没解决的问题。它的记忆不是存在某个数据库里，而是一个普通的 git 仓库加一堆 markdown 文件——你可以 grep，可以用 Obsidian 打开看，可以 rsync 备份。

**解决什么问题**: 现在几乎所有 AI 编码 CLI 的上下文都是"会话级"的：窗口一关，agent 对这个项目的全部理解归零。跨厂商切换更糟——Claude Code 攒下的上下文对 Codex 完全不可见，用户只能靠手写 `CLAUDE.md` / `AGENTS.md` 之类的文件人肉搬运，而这类文件既不会自动更新，也记不住"这条路走不通"这种负面知识。ai-memory 的做法是挂进各家 CLI 的生命周期 hook：用户提示、工具调用、会话边界这些事件被截断、脱敏后写成观测记录，会话结束时编译成一段连贯摘要，下一个 agent 启动时收到一份有大小上限的 handoff。它明确不用向量数据库（SQLite/FTS5 只是派生索引），也不要求用户主动调用"记一笔"这类工具。

**谁在用、怎么用**（来自 Issues/X/项目文档）:
- 场景 1: **跨 agent 厂商接力**。这是项目的主线场景，`ai-memory run claude` → `ai-memory run codex` → `ai-memory run command-code` 会把三段不同厂商的会话串成同一条逻辑工作流，带一份可移植的事件账本。
- 场景 2: **压上下文成本**。X 上有独立用户（@pkfps1）给出量化反馈：配合 scoped query，单个 session 的 token 从约 90k 降到约 3k。这是目前该项目外部最具体的一条使用数据。
- 场景 3: **多项目/多客户隔离**。用 `.ai-memory.toml` 按 checkout 分域，避免不同客户的上下文互相污染——issue 区里 #387 这类"按 session UUID 彻底删除"的诉求正是从这个场景里长出来的。

**社区怎么评价**:
- 正面: 外部贡献者主动提功能 PR（#26 卸载命令、#123 web chat、#403/#404 管理命令），也有人主动请求接入新的 agent CLI（#385 Swival、#373 Command Code）——说明确有人在日常使用而非只是 star。作者响应很快，closed issues 128 对 open issues 5，不是堆积型仓库。
- 负面: 报上来的都是能复现的真实故障——#141 Claude Code 退出时 session-end hook 被取消导致 handoff 丢失；#188 Windows 原生 hook 拿不到 handoff；#144 Codex 没有 SessionEnd 导致会话永不关闭；#140 `install-instructions` 直接覆盖用户手写的 CLAUDE.md；#194 hook 把 agent 自己的 memory 文件回灌成 wiki 页；#407 在 v1.28.0 的 `upgrade` 破坏非 compose 的 Docker 容器并触发重启循环。
- 健康度: 2,121 ⭐ / 23 subscribers（约 92:1）/ 197 forks（fork 占 star 约 9.3%，对新项目属偏高的真实使用信号）/ open issues 仅 5。2026-05-21 建仓，三个月发了 30 个 release，8-18 仍在提交。贡献者 30 余人但极度集中：akitaonrails 902 commits，第二名 110。HN 零讨论，Reddit 零讨论，X 上除一条独立用户反馈外基本是作者本人推广（作者是巴西 Ruby 社区知名人物）。

**风险与争议**:
- **bus_factor**: 作者一人约占 85% 提交，第二名断崖式下跌，而项目要维护的是一个覆盖 20 多家 agent CLI 的兼容矩阵。
- **dependency**: 依赖各家 CLI 私有的 hook/MCP 契约，上游任一改动即断——README 里已经写满降级说明（Codex 无真正的 session-end、Grok 忽略 SessionStart stdout、Zero 丢弃 sessionStart 输出、Kiro 需手工 finalize）。
- **privacy**: 默认捕获用户提示与工具输出，靠 sanitize 规则兜底（#408/#409 仍在补 token 家族）；#387 显示历史上无法按 session 彻底删除，对"忘记这段对话"或 GDPR 类诉求是硬缺口。
- **stability**: 作者自述 beta；已发生升级破坏容器（#407）、hook 静默丢数据（#141/#188）、覆盖用户手写配置（#140）。
- **英文社区 grounding 弱**: HN/Reddit 均无讨论，传播主要沿作者个人渠道与巴西社群，star 增速与外部独立讨论不完全匹配——判断它是否适合自己时，issue 区的技术密度比 star 数更有参考价值。

**技术备注**: Rust（1.95+），MIT。核心是 MCP server + 各 agent CLI 的 lifecycle hook 安装器；记忆载体是 git 仓里的 markdown wiki，SQLite/FTS5 作派生检索索引。支持 Linux/macOS/WSL2（原生 Windows 为实验级），发布 Docker 镜像与 AUR 包。嵌入模型可用 OpenAI/Voyage/Gemini，也支持 Ollama、LM Studio、vLLM 这类无 key 的 OpenAI 兼容端点。

### [AlexsJones/llmfit](https://github.com/AlexsJones/llmfit) — NEW ⭐ 32,324（+198）| Rust | 信源：强

**它是什么**: 一个终端工具，回答"我这台电脑到底能跑哪些大模型"。运行一条命令，它检测你的内存、CPU、GPU（含多卡和 Apple Silicon 统一内存），然后把几百个模型按质量、速度、适配度、上下文长度四个维度打分，列出哪些能跑得好、哪些勉强能跑、哪些跑不动，并给出建议的量化档位。默认是交互式 TUI，也有传统 CLI 模式供脚本调用。

**解决什么问题**: 在本地跑模型的人，选型基本靠猜和试错——同一个 70B 模型换个量化档位、换个 runtime、换台机器，结论完全不同；显存够不够、KV cache 会吃掉多少、MoE 架构该怎么算，这些没有统一答案，只能下一个几十 GB 的权重跑跑看。llmfit 把这套估算固化下来，并且从 1.0 起做了一件更关键的事：**让估算值可以被真实测量替换**。你可以在 TUI 里直接跑 benchmark 测出本机真实 tok/s，然后一键把结果提成 PR 回传项目（不需要 `gh` CLI，也不需要第三方账号）；合并后随下个版本发布，之后任何用相同硬件的人打开工具，看到的就是带 ✓ 的实测数字而不是估算。

**谁在用、怎么用**（来自 Issues/HN/生态集成）:
- 场景 1: **本地跑模型前的选型与量化决策**。这是最主要的用法，也是 HN 上讨论认可"需求真实"的部分。
- 场景 2: **被 agent 和脚本当作自动选模的依赖**。HuggingFace 官方的 `hf-agents` 用它做硬件画像后自动选模型；`recommend --json` 是为这类程序化调用准备的。HF 的 julien-c 亲自提过 PR #259 改进 HuggingFace API 抽取，Linux 内核维护者 gregkh 也有 7 次提交。
- 场景 3: **社区共建硬件基准库**。`bench` 实测后回传 PR，逐步把估算表替换成实测表——这是它区别于 whatmodelscanirun.com 这类网页表单的核心设计。

**社区怎么评价**:
- 正面: HN 上 301 分 / 70 评论，主流意见认可需求真实；外部生态的采用（HuggingFace 官方 agent 集成、HF 与内核社区的核心人物直接提交）是比 star 数强得多的信号。
- 负面: 批评集中在两点——**推荐的模型库陈旧**（HN 上指出还在推 Qwen2.5、StarCoder2），以及**核心判定本身会出错**：#835 GPU 按总 VRAM 判定而 CPU 按可用 RAM 判定，导致显存已被占满时仍报"可运行"；#635 Apple Silicon 的 KV cache 估算过于保守，直接导致 Good/Runnable 列表为空；#638 多 GPU 检测缺失；#145 已安装的 hf 检测不到。还有一类意见是"网页表单能做的事不值得装一个可执行文件"，竞品 whatmodelscanirun.com、caniusellm.com、LM Studio 内置提示被反复提及。
- 健康度: 32,324 ⭐ / 97 subscribers（约 333:1）/ 2,002 forks / 63 open issues。2026-02-15 建仓（6 个月），v1.1.10 发布于 8-17，weekly CI 自动刷新模型库与 benchmark 缓存。贡献者集中在作者（633 commits），但第二、三名是 dependabot 和外部贡献者，长尾社区 PR 活跃。

**风险与争议**:
- **stability**: "能不能跑"是这个工具的唯一核心结论，而这个结论目前存在可复现的误判（#835 显存占用未计入、#635 Apple Silicon 估算过保守），拿它当唯一依据前最好交叉验证。
- **bus_factor**: 作者一人约占 75% 提交，模型库的更新速度绑定在其个人节奏上——HN 上"推荐模型陈旧"的批评正是这个结构的外显。
- **dependency**: 依赖 HuggingFace API 与各 runtime（Ollama、llama.cpp、MLX、Docker Model Runner、LM Studio）的探测接口，上游变动即失效。
- **高比值不构成 vanity**: 333:1 的 stars/watchers 在这里是可解释的——HN 高分讨论、外部项目集成、issue 的技术密度三方交叉都能验证，属于"工具类项目用户多、订阅少"的常态。

**技术备注**: Rust，MIT，crates.io 有包，SignPath 签名。仓库分 core / TUI / desktop / web / python 五个包，支持多 GPU、MoE 架构、动态量化选择与速度估算。安装：Windows 用 `scoop install llmfit`，macOS/Linux 用 `brew install AlexsJones/llmfit/llmfit`。有中文与日文 README。

### [agalwood/Motrix](https://github.com/agalwood/Motrix) — NEW ⭐ 53,123（+344）| TypeScript | 信源：中

> 知名老项目首入 tracker：2018 年建仓，本次为首次进入本 tracker 记录。

**它是什么**: 一个全能下载管理器，2018 年开源，界面干净、跨平台（macOS/Windows/Linux），支持 HTTP、FTP、BitTorrent、磁力链接，早年因为"长得像 macOS 原生应用的 aria2 前端"在中文社区流传很广。

**解决什么问题**: aria2 是功能最强的开源下载引擎，但它是个命令行守护进程，普通用户配置不来；Motrix 把它包成一个正常人能用的桌面应用——多任务并行、断点续传、BT 做种、限速、静默模式，都在 GUI 里点。

**为什么今天上榜**: 不是新项目，也不是老项目被随机点亮——**它在密集地发 2.0 beta**。8-16 到 8-17 两天里连发了 v2.0.0-beta.14 到 beta.18 五个预发布；近期提交里能看到内置 aria2 升到 1.37.0-motrix.4、新增 DNS 解析模式与自动回退、bridge 层引入幂等缓存、HTTP 分片进度显示修复、macOS 托盘图标位置保持，以及一份扩写的 Plugin SDK 开发指南和新增的繁体中文翻译。这是一个沉寂多年的项目正在重启的信号。

**社区怎么评价**:
- 正面: 53,123 ⭐ / 488 subscribers（约 109:1，对成熟工具类项目属正常区间）/ 4,930 forks，长期口碑稳定。
- 负面: 776 条 open issue 是历史欠账的直接体现，热门的几条都很老——#553（不支持 ed2k 协议，25 条评论）、#178（下载种子文件失败，18 条）、#361（百度网盘助手下载报 #22，15 条）、#1502（应用白屏，14 条）。#1805 甚至是社区在讨论"发现一个叫 Motrix Next 的新项目，用新代码重写了 Motrix"——说明在 2.0 之前，已经有人因为等不到更新而另起炉灶。
- 健康度: 贡献者极度集中，agalwood 1,083 commits，第二名 18 commits。

**风险与争议**:
- **bus_factor**: 单一作者占绝大多数提交，且项目已有过多年低活跃期；这次 2.0 的推进节奏能否持续，目前没有第二个人可以接手。
- **stability**: 当前活跃分支是 beta（两天连发 5 个预发布），正式版仍停在 2023 年的 v1.8.19；想稳定使用的人不应直接上 2.0 beta。
- **compliance**: license 为 NOASSERTION（GitHub 未能识别标准 SPDX 标识），在企业环境里引入前需要人工确认授权条款。

**技术备注**: TypeScript + Electron，底层是捆绑的 aria2（当前 1.37.0-motrix.4 定制版）。2.0 引入插件 SDK。本条为知名老项目首次进入本 tracker 的记录，未做完整外部社区 grounding，结论主要基于仓库自身的提交、release 与 issue 数据。

## 如何理解今天的热度信号

今天 11 个项目里，只有 3 个是本 tracker 的新面孔，且其中一个是 2018 年的老项目——**这是一个"回流日"而不是"爆发日"**。对读者更有用的判断维度不是 star 增量，而是"项目侧今天有没有真实动作"：

- **有明确项目侧事件**：Motrix（两天连发 5 个 2.0 beta）、strix（证据质量改造）、career-ops（v1.26.0 + 高频提交）、omlx（0.6.1 + 崩溃修复）、nautilus_trader（多交易所一致性）、immich（工程质量）、llmfit（v1.1.10）、ai-memory（仍在日更）。
- **热度来自外部、项目侧静止**：cordis（5 天零提交）、Anthropic-Cybersecurity-Skills（10 天零提交，release 停在 6-22）。

另外两个容易踩的坑今天各出现一次：一是**只看 Release 页判断项目死活**（Motrix 正式版停在 2023 年，实际正在密集发 beta）；二是**只看 stars/watchers 比值判断可信度**（llmfit 333:1 但 grounding 全榜最强，ai-memory 92:1 但英文社区零讨论）。比值和 release 都只是入口信号，结论要看提交记录、issue 密度和外部足迹在哪里。
