### [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill) — NEW ⭐ 10,764（+3,607）| JavaScript | 信源：强

**它是什么**: 一个给编码 agent 用的"安全审计流程说明书"。你把它装进 Claude Code、Codex 这类 agent，然后指向自己的代码仓库，agent 会按它规定的多个阶段依次走：先摸清代码结构，再找可疑点，再自己验证这些可疑点是不是真的能被利用，最后输出一份格式固定、机器可读的 `findings.json`。它本身几乎不含代码逻辑——整个仓库 143KB，主体是 markdown 提示词加少量脚本。

**解决什么问题**: 让 AI 做安全审计的老问题是"它会一口气报 40 个问题，其中 35 个是假的"。这个 skill 的设计是把发现和验证拆给不同阶段、不同上下文来做（发现者不是验证者），再用三态判定（确认 / 否证 / 待定）和一份覆盖率台账逼 agent 说清哪些地方其实没审到。用之前你拿到的是一段不可追溯的散文，用之后拿到的是带 schema 的结构化结论。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 指向本地仓库跑多阶段审计，输出 `findings.json`；官方说明单轮大约只能覆盖多轮合集的一半，所以真实用法是跑多次累加。
- 场景 2: HN 上多位用户拿自己的项目实测过。`jesse_dot_id` 在一个小型 FastAPI 项目上就撞到了 150k token 的额度上限；`drchaim` 在中型代码库上"烧掉 100 万 token 一无所获"。
- 场景 3: issue #5 反映 skill 的自动触发不可靠，要求改成直接的 slash command——这类需求只有真在日常流程里用的人才会提。

**社区怎么评价**:
- 正面: 设计被同行认真读过。X 上有日文长贴逐段拆解它的阶段划分和"发现者≠验证者"设计，评价是干净。Cloudflare 员工 `kentonv` 在 HN 帖内直接回应了讨论。
- 负面: HN 帖（194 分 / 36 评论，9-17）的主论调是成本和上下文污染，不是"好不好用"。`chrisweekly` 指出 150k token 已经进了模型"变笨区"；`qsbuilder` 批评"塞 14 份完整 schema 是懒设计"；也有人讽刺"为一个 markdown 文件建了个仓库"。最扎的一条质疑来自 X：设计干净和检出率高是两件事，想看 benchmark——目前没有。
- 健康度: 10,764 ⭐ / 41 watchers（262:1）/ 573 forks / 30 个 open issue；贡献者只有 3 人，其中一人 11 次提交、另两人各 1 次。建仓 2026-06-18，最后 push 9-14。issue 和 PR 大多零回应。

**风险与争议**:
- **cost**: 多个独立实测都指向 token 消耗失控，中小项目跑一轮就撞额度上限；这是目前最一致的负面信号。
- **stability**: 验证机制自身有漏检——issue #21 指出覆盖率校验器不检查 artifact 是否真实存在，台账可以虚报已覆盖；#36 指出两套测试各有一条"因错误原因通过"的测试。
- **dependency**: issue #13 指出在非 Cloudflare 系的 agent 平台上（Antigravity）会整波静默失败：用了一个不存在的 agent 类型，加上 pentest 式提示触发模型拒答。
- **bus_factor**: 3 名贡献者、事实上单人维护，30 个 open issue/PR 排队。
- **vanity**: 262:1 的 stars/watchers 比 + 两周涨近 3 倍，与 3 人的贡献者规模严重不匹配。但要注意这里不是纯空心——HN 和 X 上有真实的技术讨论和实测，只是讨论结论偏负面。

**技术备注**: JavaScript + markdown，MIT，143KB。要求"OS 强制的沙箱"环境（HN 上有人专门问过为什么）。已被独立团队复刻（HN 上 `gbrindisi` 分享了自建内部审计 skill 的做法）。

### [Tencent/BrowserSkill](https://github.com/Tencent/BrowserSkill) — NEW ⭐ 4,244（+1,302）| TypeScript | 信源：强

**它是什么**: 让 AI agent 借用你电脑上那个已经登录好的真实浏览器干活，而不是另起一个空白的自动化浏览器。装法是一个命令行工具加一个浏览器扩展；任何"能跑 shell 命令"的 agent（Claude Code、Cursor、Codex 等）都能调它。

**解决什么问题**: 以前让 agent 上网做事有两条路，都不好走：用 Playwright 这类自动化浏览器，就得重新处理登录、验证码、风控，很多站点直接过不去；用桌面级控制去操作你正在用的浏览器，就会抢走你的鼠标键盘和窗口。这个项目走第三条路——借你现有浏览器的一个标签页，你继续用别的标签页，遇到验证码或需要确认的弹窗就交还给人处理。

**谁在用、怎么用**（来自 Issues/X）:
- 场景 1: 主流用法是配合 DeepSeek Harness 插件（`browser-skill-dsh-plugin`）或直接挂在 Cursor / Claude Code / Codex 上，在已登录的站点上让 agent 借一个标签页取数据、填表单。
- 场景 2: issue #268（Windows，2 条评论）报的是把它接进 agent harness 时的真实冲突：`daemon start` / `status` 永不返回，harness 超时后杀掉整个进程树连带杀死了 daemon，而且只读命令 `status` 居然会副作用地启动 daemon——作者自己承认这是个 footgun。
- 场景 3: 社区在主动补功能，且多来自外部贡献者：#79 录屏、#249 后台标签页续跑、#275 `--no-wait`。

**社区怎么评价**:
- 正面: issue 质量很高——带完整版本号、复现步骤和日志，不是灌水。300 个 fork 和外部 PR 说明有人真在集成。9 月两周内连发 0.2.0 → 0.2.1 → 0.3.0，迭代很密。
- 负面: 跨平台可靠性是主要抱怨点。#272 在 macOS + Yandex Browser 上，第二个 profile 连入后 CDP 会全局卡死且黏滞，只能重启浏览器；#185 报 Windows 会话调度竞态，`stop` 无法强制中断、也没有命令超时；#219 Chrome profile 参数被忽略；#257 在 360 极速浏览器上窗口全灰。
- 健康度: 4,244 ⭐ / 13 watchers（327:1）/ 300 forks；open issue 51、closed 61（解决率约 54%）、open PR 20；16 位贡献者，但前 4 位（各 133 / 109 / 91 / 85 次提交）占了绝大多数。建仓 2026-06-22。
- 这里的 327:1 不构成 vanity 判据：issue 详实、fork 多、有外部 PR，社区足迹是真的；watcher 低更像 Tencent 组织仓库的结构性特征。

**风险与争议**:
- **privacy**: 核心设计就是把带登录态的真实浏览器交给 agent。X 上已有人指出 prompt-injection 风险，目前未见缓解方案。
- **stability**: Windows 和非 Chrome 的 Chromium 分支（Yandex、360）上有多处硬故障；daemon 的生命周期设计和 agent harness "超时就杀进程树"的模型直接冲突。
- **bus_factor**: 提交高度集中在腾讯内部 4 人。
- **默认权限**: 0.3.0 才把 `--unattended`、`--no-confirm`、`BSK_REQUEST_HELP=off` 收紧到不能再绕过确认——说明此前确实可以无人确认地操作你已登录的浏览器。

**技术备注**: TypeScript，MIT，CLI + 浏览器扩展双件套，通过 CDP（Chrome DevTools Protocol）接管标签页。HN 上仅一条 9-16 的投稿，1 分 0 评论；传播主要靠 @TencentAI_News 官方账号。

### [Tencent/WeKnora](https://github.com/Tencent/WeKnora) — NEW ⭐ 26,295（+1,125）| Go | 信源：中

**它是什么**: 一套可以自己部署的文档知识库系统。你把 PDF、Word、Notion 页面之类的原始文档丢进去，它做三件事：变成能被问答检索的知识库（RAG）、提供一个会自己多步推理的问答 agent、以及生成一份能自我维护的 Wiki。

**解决什么问题**: 企业想做内部知识问答，通常要自己拼向量库、切分策略、检索排序、模型接入和权限，落地周期长。WeKnora 把这套拼好并支持私有化部署，对接 Qdrant、外部模型 API、Notion、对象存储，也能把问答接进 IM 机器人。

**谁在用、怎么用**（来自 Issues）:
- 场景 1: 私有化知识库问答——issue #3313 展示了一个真实用法：接 Notion 大型数据库，结果被合并成单文档后触发了 Embedding 的 TPM 限流，整篇文档处理失败。

- 场景 3: 从功能诉求能看出用户跑在什么环境：要求用 MySQL 作为底层库（#1418）、要多级文件夹（#1311）、要移动端适配（#917）。

**社区怎么评价**:
- 正面: 维护者响应快。issue #98 报文档解析失败，作者当天定位为并发过高并出 PR #101 修复；也有外部贡献者做出完整的复现矩阵，工程质量不低。

- 健康度: 26,295 ⭐ / 121 watchers（217:1，大型企业开源的常态）/ 3,562 forks（fork/star 13.5%，偏高，说明有人真在部署）；open 计数 666、closed 739；**open PR 达 291 条，积压明显**；贡献者 100+ 但高度集中，头号维护者 1,996 次提交，第二名仅 128。建仓 2025-07-22，9-17 仍在推送。
- 外部信源几乎为零: HN 只有 2025-12-14 一条投稿（2 分 0 评论），X 上仅两条转发式提及且腾讯官方未推广，Reddit 零命中。

**风险与争议**:
- **热度成分**: 评论数最高的几条（#1679 76 条、#1248 49 条）几乎全是"已认领本任务"的刷屏，来自腾讯犀牛鸟开源专属任务计划，不是真实用户讨论；异常高的 fork 率和 291 条 PR 洪水同源。看这个仓库的活跃度时必须把这一层剥掉。
- **bus_factor**: 单一维护者贡献占绝对多数，291 条 PR 排队。
- **stability**: 多模态提取和流式通道在最新版本仍有未修复缺陷，一年前的解析 issue 还开着。
- **compliance**: license 字段为 `NOASSERTION`（非标准 SPDX），商用前需人工核对。

**技术备注**: Go，支持 REMOTE API 接外部模型、Qdrant 向量库、Notion / 对象存储数据接入。

## 如何理解今天的热度信号

今天这批新面孔里，高 stars/watchers 比出现了四次（262:1、327:1、616:1、89:1），但四个项目该怎么读并不一样。可用的分辨方法是看比值之外还有什么：

- **有实测反馈但反馈偏负面**（`security-audit-skill`）——HN 36 条一手用量数据，结论是 token 烧得太快。热度是真的，结论也是真的，只是两者方向相反。
- **有 fork、有外部 PR、issue 带日志**（`BrowserSkill`、`tinycast`）——高比值更可能只是 watch 功能本身没人用，不是空心。
- **依赖链不完整**（`Octop`）——比值反而不是最关键的，"核心组件不在仓库里"才是。
- **issue 热度来自非用户来源**（`WeKnora`）——评论数看着高，但排头几条是开源任务计划的认领刷屏。看活跃度时必须先剥掉这一层。

另外两个成熟项目（`cilium`、`coder`）的 80:1 和 181:1 是大仓的结构性数值，和上面几类不是一回事；它们今天的热度都能追到具体的发布日期和版本号，属于可解释的回流。
