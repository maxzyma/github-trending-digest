**主线四：榜单解读提醒 — 今天的短龄项目 subscribers 数普遍低到无法用比值判断。** `MG1937/ASC` 1,203 ⭐ / 2 subscribers（约 602:1）、`alphaXiv/OpenResearch` 3,406 ⭐ / 13（262:1）、`pacifio/atlas` 4,648 ⭐ / 24（194:1）。这三项都是三到四个月仓龄的新项目，单看比值会一律判成空心化，但它们的 fork 数、外部 PR、发版节奏差异很大——ASC 有 197 forks 和被合入的外部 PR，atlas 的 issue 区至今没有一条外部用户报障。**比值只能用来起疑，不能用来定性**；今天真正有区分度的是"有没有外部的人在提交代码和报障"。作为对照，`ghidra` 的 1,146 subscribers 是全榜唯一四位数，67:1 也是全榜最低比值。

### [Homebrew/BrewUI](https://github.com/Homebrew/BrewUI) — NEW ⭐ 1,398（+271）| Swift | 信源：中

**它是什么**: Homebrew 的官方 macOS 图形界面。Homebrew 是 macOS 上装软件用得最多的包管理器，但十几年来只有命令行——想看装了什么、有什么能升级，都得敲 `brew list`、`brew outdated`。BrewUI 把这些做成了一个原生 macOS App：搜索和浏览软件包、看依赖关系和已装版本、勾选批量升级。它随 9 月 13 日的 Homebrew 7.0.0 一起正式发布。

**解决什么问题**: 以前这块空白由第三方填：Cakebrew、Applite、Taphouse 都做过 Homebrew GUI，但它们要自己追 brew 的行为变化，brew 一改输出格式就可能出问题。官方做这件事的直接价值是不会再脱节。设计上它刻意不把 brew 藏起来——窗口底部有个 terminal drawer，实时显示当前操作对应的 brew 命令是什么，目的是让 GUI 用户仍然知道系统上在发生什么，而不是变成一个黑盒。

**谁在用、怎么用**（来自 Issues/官方发布）:
- 场景 1: 用 `brew install --cask homebrew-app` 装，然后做日常的浏览、搜索和批量升级。issue #210 请求增加导出 Brewfile 的功能——提这个需求的人是在用它管理整台机器的软件清单。
- 场景 2: 非英语用户在用。本地化是目前呼声最强的需求，社区已经交了四拨 PR：#154（葡语加本地化基座）、#177 / #181 / #187（简体中文）。这说明真的有不碰命令行的用户在装。

**社区怎么评价**:
- 正面: 维护响应快——31 条 issue 已关闭，当前 open 的只有 2 条真 issue（其余是 PR）。发版极密，五天内从 v0.3.0 走到 v0.4.2。官方背书确凿：Homebrew 官方组织下、brew.sh 的 7.0.0 发版公告明列，BleepingComputer 等媒体有独立报道。
- 负面: issue #201 报升级 cask 时 `chown: Operation not permitted`（升级 Cursor 失败），是权限模型的问题；issue #180 指出已弃用的 cask/formula 在界面上仍显示 ✅，新手会误读成"已验证"。
- 健康度: 1,398 ⭐ / 9 subscribers（155:1，但组织仓的 watch 数结构性偏低，这里不构成 vanity 判据）/ 31 forks / 8 open issues。12 位 contributor，graeme 一人 828 次提交，MikeMcQuaid 59，其余主要是 BrewTestBot 和 dependabot。2026-03-02 建仓。
- 外部: HN 上两条提交分别只有 7 分 0 评论和 3 分 0 评论——反而不如第三方 Taphouse 5 月那条（19 分 6 评论）热。X 无独立讨论，Reddit 无可验证讨论。发布只有三天，讨论少属于时间不足。

**风险与争议**:
- **compliance**: AGPL-3.0。对一个 GUI 工具来说是比较激进的许可选择，衍生分发需同等开源；已经出现 luckman212/BrewUI 这类 fork，二次分发前要看清楚。
- **stability**: 0.4.x，五天五个版本，权限类缺陷（#201）尚未解决；#180 的弃用包显示问题会误导新手。
- **bus_factor**: 单人（graeme）贡献占 80% 以上。
- **仅支持 macOS 26+**: 需要 macOS 26 Tahoe 及以上，老机器用不了，实际用户面比 star 数暗示的窄很多。

**技术备注**: Swift，AGPL-3.0，原生 macOS App，通过 `brew install --cask homebrew-app` 安装。

### [MG1937/ASC](https://github.com/MG1937/ASC) — NEW ⭐ 1,203（+129）| Python | 信源：中

**它是什么**: 一个专攻大体积 Android 安装包的反编译前端。做安全研究的人要在一个 APK 里找某个类、某段硬编码密钥、或者某个方法被谁调用过，常用的是 jadx——但 jadx 要先把整个包解压、再建全局索引，遇到几百兆的商业 App 就非常慢甚至直接内存溢出。ASC 换了条路：不建索引，直接在压缩流里定位目标，找到之后只把相关的字节码和它的依赖抽出来，在内存里拼一个最小的 DEX 再反编译。

**解决什么问题**: 它把"打开一个大 APK"从一次全量作业变成一次定点查询。作者自测的数字是搜索快 269 倍、内存省 125 倍，并称 jadx 在 352MB 的包上有 49% 的概率 OOM。CLI 只有三个子命令——`getclass`（取类）、`getmanifest`（取清单）、`findrefs`（查引用），另有 `--gui` 和 `--json`。README 里的"designed for Agents"目前指的就是这个 JSON 输出，**还没有 MCP 接口**，issue #1 正是在要 MCP。

**谁在用、怎么用**（来自 Issues/PR）:
- 场景 1: 数百 MB 商业 APK 的跨 DEX 交叉引用搜索——找硬编码 token、定位混淆后的关键方法，这是 jadx 全局索引跑不动的那类活。
- 场景 2: 外部贡献者在真跑代码并改进它。issue/PR #16 加速了大 APK 的引用搜索与 `getclass`，#24 修 Python 版本下限兼容，#25 修 GUI 子进程，#15 加了 JSON 输出——这四条都是外部提交并被合入的。
- 场景 3: 恶意 App 分析与漏洞挖掘中的定点反编译，这也是它进 Black Hat Europe Arsenal 的议题方向。

**社区怎么评价**:
- 正面: 已被 **Black Hat Europe Arsenal 收录**（议题名 Droid ASC），这是今天榜上最硬的一条外部背书。197 forks 占 star 数的 16%，比例偏高，加上外部实质 PR，说明确有人在用而不只是收藏。已发 PyPI（`droidasc` 0.1.0），昨天仍有提交。
- 负面: issue #4 直接质疑 README 的核心技术主张——在 DEX 被压缩的情况下"跳过完整解压"如何成立，尤其是字符串搜索场景，作者未见公开答复；issue #20 报字符串搜索直接报错；issue #2 是社区自己提醒作者小心工具被黑产滥用。
- 健康度: 1,203 ⭐ / **2 subscribers**（约 602:1，全榜最极端）/ 197 forks / 6 open issues / Apache-2.0。7 位 contributor 但高度集中：MG1937 45 次提交、ZacharyZcR 14 次，其余 5 人各 1 次。2026-06-09 建仓，约三个月。
- 外部: HN 零命中。X 上只有安全研究者 @blackorbird 一条转发，约 1.4K 浏览、无讨论串。Reddit 的 r/ReverseEngineering、r/netsec、r/androiddev 均无讨论。dev.to 有一篇介绍文，基本是复述作者 benchmark，属二手转述不是独立评测。

**风险与争议**:
- **未验证的性能主张**: 269× / 125× 全部来自作者自测，issue #4 对其技术前提的公开质疑至今没有答复，也没有第三方复现。这是评估它时最该先解决的问题。
- **vanity**: 602:1 的比值、HN/Reddit 零讨论、X 仅一条转发，热度来源集中在中文安全圈与 Arsenal 曝光。但 197 forks 与被合入的外部 PR 说明不是空壳，判断应为"曝光驱动 + 小规模真实使用"。
- **compliance**: 反编译商业 APK 普遍触碰平台服务条款与各地法规，项目没有任何免责声明或使用边界说明；issue #2 的担忧来自社区自身。
- **bus_factor**: 单人主导（45/64 次提交），三个月仓龄。
- **stability**: 0.1.0，已有搜索报错的 issue（#20）未清。

**技术备注**: Python，Apache-2.0，PyPI 包名 `droidasc`。自研零索引 DEX 查询引擎——Deflate 比特流内的稠密 Huffman 查表探测、利用 R8 常量重定位带来的物理集中布局做跨 DEX 搜索、O(1) 指令定位原语。

### [danny-avila/LibreChat](https://github.com/danny-avila/LibreChat) — NEW ⭐ 43,865（+254）| TypeScript | 信源：中（知名老项目首入 tracker）

**它是什么**: 一个可自托管的多模型聊天前端。你自己部署一份，把 OpenAI、Anthropic、Google、Mistral、OpenRouter、Bedrock、本地模型的 key 都接进去，在同一个界面里随时切换模型、共用同一套对话历史和搜索。多用户、带鉴权，团队可以共用一个实例。

**为什么现在上榜**: 这是本 tracker 第一次记录到它，但它不是新项目——2023 年 2 月建仓，43,865 ⭐、9,027 forks、208 subscribers（211:1，对这个体量属结构性偏高，不适用 vanity 判断）。近期开发强度很高，9 月 15 日一天就合入了多条 agent 与 MCP 相关改动：把 Content / Tool / Agent 类型从 Assistants 模块拆出（#15910）、记住上次的代码审批模式（#15973）、turn 失败时保留已流式输出的内容（#15961）、给 MCP token provider 传递 schedule 身份（#15962）。当前最热的需求是 MCP Apps 支持（#13831，54 条评论）和未读回复提醒（#15025，60 条评论）。741 个 open issue 对这个规模属正常。

**风险与争议**:
- **cost**: 自托管省的是订阅费，花的是各家 API 的 token 费；多模型并行接入很容易把成本摊开而不是降下来。
- **dependency**: 价值完全来自它接的那些上游 API，任何一家改接口或改定价都要跟。

**技术备注**: TypeScript，MIT，最新标签 v0.8.8-rc3（仍在 rc 阶段），支持 Docker 部署、多用户鉴权、MCP、Code Interpreter、Artifacts。
