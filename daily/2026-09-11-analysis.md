### [JustVugg/colibri](https://github.com/JustVugg/colibri) — NEW ⭐ 27,484（+98）| C | 信源：强

**它是什么**: 一个让普通电脑跑得动超大模型的推理引擎。现在最强的开源模型多是 MoE（混合专家）结构——模型有几百 B 参数，但每次生成只会用到其中一小部分「专家」。colibri 利用这一点：把全部专家权重留在固态硬盘上，用到哪个读哪个，于是显存装不下的模型也能加载起来。纯 C 实现，零依赖。

**解决什么问题**: 以前想在本地跑 200B 以上的模型，要么买多张显卡，要么就是跑不了。colibri 把瓶颈从「显存够不够」换成「硬盘读得够不够快」——代价是速度。实测吞吐区间是 **0.1–12 tok/s**，好的 NVMe RAID0 能到高位，消费级 SATA SSD 会退化到 2–4 tok/s，最差的报告是 20 秒出一个 token。

**谁在用、怎么用**（来自 Issues/HN/X）:
- 场景 1: 服务器级 NVMe 阵列跑 benchmark。issue #1384 有人在 Azure D128ads v7 + 4×NVMe RAID0 上提交完整测试，附 commit sha 和 `coli doctor --deep` 输出；#1379/#1380 是另外两台机型。
- 场景 2: 家用工作站试水。issue #1199（WSL2 + RTX 5060 Ti + 32GB DDR4）自测 iobench 4.78–5.52 GB/s，并自我标注「协议未完全遵守，结果可能不可比」。
- 场景 3: 性能优化贡献。外部 PR #1313 把 `matmul_fp8` 改成四路并行，+21.34% tok/s 且 bit-exact；#1309 实测 DeepSeek V4 在 Apple Silicon 上存在 5.05× TTFT / 2.81× tok/s 的差距。

**社区怎么评价**:
- 正面: HN 上 **Show HN 937 分 / 240 评论**（2026-07-09），有机讨论扎实；作者自建了衍生项目 lumabri。仓内 `docs/experiments/glm52-6x5090-2026-07-12.md` **主动公布对自己不利的结果**——colibri 0.12 tok/s vs vLLM-Moet 2.3–2.7 tok/s，优化后才追到 6.84。#1294 正在建可复现的 benchmark 协议，#867 专门写了「同一块盘测出四种带宽」的度量陷阱。
- 负面: issue #1405（17 条评论）Windows CUDA DLL 根本编不出来、文档链接 404；#441 指出 PILOT 预取跑在 NVMe queue-depth 1、DIRECT=1 会重复读已预取的页；#1050 发现缓存越大 tok/s 反而非单调。HN 上 wren6991 用 M1 Max + RTX Pro 6000 只跑到 0.7 tok/s，称「完全无法交互使用」。
- 健康度: 27,484 ⭐ / 234 watchers = 117:1（偏高），但 issue 编号已到 #1419——一个半月开了 1400+ issue/PR 且绝大多数已关闭；contributors 里作者占 1077 commits（约 63%），ZacharyZcR(163)、monotophic(112)、steve-m(60)、woolcoxm(55) 等 15+ 外部贡献者均有实质提交，**不是单人仓**。

**风险与争议**:
- **stability**: 建仓仅两个多月，Windows/CUDA 构建链断裂，PILOT 预取逻辑仍在调。
- **dependency**: 重度依赖 NVMe 的随机读特性，SATA SSD 上性能退化明显，机械盘不可用。
- **期望差**: 传播叙事是「在笔记本上跑 744B」，真实体感取决于你的存储，两端能差两个数量级。int4 量化对 MMLU/HellaSwag 的质量损失至今没测过。
- 值得对照的是：117:1 的比值很高，但社区足迹（HN 937 分、15+ 外部贡献者、带硬件配置的实测 benchmark）与热度匹配，这里**不适用 vanity 判断**。

**技术备注**: 纯 C，Apache-2.0。专家权重按需从磁盘流式载入，v1.4.0 起有 Vulkan 后端（RX 580 可跑 744B）。

### [nashsu/llm_wiki](https://github.com/nashsu/llm_wiki) — NEW ⭐ 18,150（+142）| TypeScript | 信源：中

**它是什么**: 一个桌面软件，把你硬盘里散落的文档（论文、会议纪要、EPUB 电子书、网页剪藏）喂给它，它用大模型读完、抽出概念、自动建立互相链接的条目，最后生成一个像维基百科那样可以点着看的本地知识库。

**解决什么问题**: 传统笔记软件要你自己打标签、自己建双链，文档一多就懒得维护。这个项目把「整理」这一步交给模型做增量维护——新导入一批文档，它自己更新相关条目和链接关系。可以配 Obsidian 一起用（issue #32），也能通过 MCP 接进 Claude Code。

**谁在用、怎么用**（来自 Issues）:
- 场景 1: 学术/资料库建设。issue #5（15 条评论，仓内最热）有人问 50–80 万份文档规模下的性能表现——至今没有明确答案。
- 场景 2: 批量导入既有文档。issue #470 报告 ingest 200 份文档时 index.md 大概率被截断丢失；#743 指出模型在 CoT 阶段耗尽 token 会导致生成出空正文。

**风险与争议**:
- **privacy**: 文档正文会发往用户自配的 OpenAI-compatible endpoint。虽可接本地模型，但默认路径是第三方 API——不是纯本地方案，导入敏感资料前要看清配置。

- **bus_factor**: 单人维护，近三周无提交。
- **compliance**: license 字段为 NOASSERTION（非标准协议），商用前需自行确认。

## 如何理解今天的热度信号

今天榜上有三个 stars/subscribers 比值超过 100:1 的项目——`colibri`（117:1）、`llm_wiki`（221:1）、`CloddsBot` 的 84:1 也接近——但它们的可信度差异很大，正好是一组现成的对照：

- `colibri` 比值高，但 HN 有 937 分主贴、15+ 外部贡献者提交带硬件型号和 commit sha 的实测、作者主动公布对自己不利的 benchmark。**热度有对应物。**
- `llm_wiki` 比值最高，GitHub issue 质量扎实（有人读源码到行），但 HN 一条 2 分 0 评论、X 以作者自推为主、Reddit 零命中。**热度的一部分没有对应物。**
- `CloddsBot` 比值不算最高，但最关键的验证问题（真有人赚到钱吗、风险怎么治理）在 issue 区无人回答，开放 issue 里一半是服务商推广。**这类项目该看的不是比值，是有没有人愿意公开自己的实盘结果。**

可操作的判据：比值只是提示你去查，查的对象是「热度高的那一侧有没有人在提交可复现的东西」——实测数字、带行号的 bug、外部贡献的优化 PR。这三样有任意一样成规模，高比值就不构成问题；一样都没有，star 数就只是传播量。

另外，今天有两个项目提醒我们 **GitHub 页面上最显眼的数字最不能直接用**：`PI-Desktop` 的创建日期（2023-03-22）比真实年龄（约 7 周）老了三年；`armorpaint` 的日增（+72）是全榜最低，但它是今天唯一一个由真实发版而非传播推上来的项目。看新面孔时的顺序应该是：先看最早一条 commit 的日期，再看 LICENSE，然后才看 star。
