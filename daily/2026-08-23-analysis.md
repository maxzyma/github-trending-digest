**主线一：Agent 工具链占掉一半榜单 — 官方 CLI、skills 生态仓、网关层同时在场。** 17 个项目里有 8 个属于 agent 工具链：官方侧是 `openai/codex`（+1,544，回榜第 1）、`anthropics/claude-code`（+127）、`cursor/plugins`（+286）三家；生态侧是 `mattpocock/skills`（+2,683）、`obra/superpowers`（+592）、`affaan-m/ECC`（+411）、`multica-ai/andrej-karpathy-skills`（+315）四个 skills/方法论仓；网关侧是新入榜的 `Wei-Shaw/sub2api`（+278）。这个组合说明周日的注意力不在"又一个 agent 框架"，而在"怎么把已有的 agent 工具用好、用便宜"——提示词与 skill 复用在上层，配额与路由在下层，中间的框架层反而没有新面孔。

## 新上榜项目

### [Wei-Shaw/sub2api](https://github.com/Wei-Shaw/sub2api) — NEW ⭐ 39,251（+278）| Go | 信源：强

**它是什么**: 一个自己架设的"AI 订阅中转站"。你和朋友各自买了 Claude、Codex、Gemini 的月度订阅，平时只有自己能用、额度还经常闲置；Sub2API 把这些订阅账号统一收进一个网关，对外发放普通的 API Key，谁需要就用 Key 调用，后台自动挑账号、算用量、限并发。对使用者来说，感受就是"一个 Key 打通所有订阅，成本按人头分摊"。

**解决什么问题**: 在它之前，想共享订阅只能互相传账号密码（风险高、并发会打架），或者去买第三方中转站的额度（不知道对话有没有被记录、服务随时可能跑路）。Sub2API 把这件事变成自己可部署的软件：Go 后端 + Vue 管理台 + PostgreSQL/Redis，一键脚本装完就有 Web 界面，能看到每个 Key 的 token 消耗和成本、按账号做粘性会话路由、按用户设并发和限速。它是作者前一代项目 `claude-relay-service`（CRS）的 2.0，老用户被引导迁移过来。

**谁在用、怎么用**（来自 Issues/X/生态仓库）:
- 自建给小团队/朋友分摊 Claude Code Max 订阅：这是 README 和 X 传播里最主要的场景，[向阳乔木的 X 帖子](https://x.com/vista8/status/2032641348407595238)完整演示了"装 Redis+PostgreSQL → 跑 install.sh → Web 界面配账号"的自建流程，并强调"甚至能把 OpenAI 订阅转成 Claude Code 可用的 API"。
- 生产级压力下的真实运维问题：issue [#2738](https://github.com/Wei-Shaw/sub2api/issues/2738)（143 条评论）报"最近两天很容易 502 timeout awaiting response headers，首 token 几百秒甚至卡死"，issue [#4248](https://github.com/Wei-Shaw/sub2api/issues/4248)（49 条）报"首字 15 分钟"。能吵到上百条评论，说明背后是真的有人靠它跑日常工作流。
- 配额与账号策略调优：issue [#5663](https://github.com/Wei-Shaw/sub2api/issues/5663)（43 条）讨论"两个 Pro 账号额度到 100% 差距为什么这么大"，[#5787](https://github.com/Wei-Shaw/sub2api/issues/5787)（33 条）讨论"178 版本新开 Pro 账户额度仍只有 1400 刀"。
- 卫星生态已经长出来：`touwaeriol/sub2apipay`（自托管支付网关，400 stars）、`ckken/sub2api-mobile`、`codermyxiaoc/sub2api-guardian`、`DR-lin-eng/sub2api`（性能优化二开）等十余个周边仓库，是它已被实际部署的旁证。

**社区怎么评价**:
- 正面: 部署门槛低（一键脚本 + Docker 镜像）、迭代极快（8-24 到 8-25 两天内连发 v0.1.180 / 181 / 182）、多账号调度和用量核算这两件最麻烦的事都做完了。
- 负面: 稳定性投诉集中在上游超时与首 token 延迟；额度口径不透明；Nginx 反代默认丢弃带下划线的 header（如 `session_id`）会打断粘性会话，需要额外配置。
- 争议: issue [#5992](https://github.com/Wei-Shaw/sub2api/issues/5992)（81 条评论）是一条情绪化的"别再查中转站了"长帖，直接把这个生态的合规争议摆到了 issue 区。
- 健康度: 39,251 stars / 76 subscribers（比值约 516:1，偏高）；但 8,109 forks 和 2,816 open issues 与之匹配，fork 与 issue 的绝对量说明热度不是空转。贡献者集中在作者 `Wei-Shaw`（2,193 commits）与 `IanShaw027`（697），前两名占绝大多数提交。LGPL-3.0，2025-12-18 建仓。
- 外部讨论: HN 上没有 Sub2API 本身的主题帖，只有一条相关背景讨论 "Chinese are offering Claude/Codex offers 90% off"（2026-08-03，4 分 4 评）；Reddit 未见相关讨论，中文侧讨论集中在 X、Linux.do、V2EX 与 Telegram。

**风险与争议**:
- **compliance**: README 首屏自述"使用本项目可能违反 Anthropic 等上游服务商的服务条款，风险由使用者自担"，并声明从未授权任何商业运营；订阅额度再分发的合法性在多数地区没有确定结论。
- **dependency**: 全部价值建立在上游订阅的 OAuth/额度接口之上，上游一次风控或接口调整就可能整体失效，issue 区的超时与额度差异投诉已经是这种脆弱性的表现。
- **privacy**: 网关天然经手全部 prompt 与响应；自建可控，但一旦接入他人运营的实例，隐私边界完全取决于运营方。
- **stability**: 高频发版（一天多个 patch）配合 2,816 条 open issues，说明它仍在"边跑边修"的阶段，502/首 token 超时是当前最集中的问题。
- **商业化利益纠缠**: README 赞助位上是五家中转服务商（CCTK.AI、OpenModel、ETok、APIKEY.FUN、AIGoCode），且带 aff/邀请参数——开源项目与它所服务的商业中转生态之间存在直接利益关联，读 README 的推荐内容时需要意识到这一点。

**技术备注**: Go 1.27 后端 + Vue 3 前端，PostgreSQL 15+ / Redis 7+ 依赖，提供 install.sh 一键脚本、Docker Hub 与 GHCR 镜像、goreleaser 预编译二进制；仓库内含 `skills/`、`openspec/` 目录，自身也按 agent-native 方式组织文档。

## 如何理解今天的热度信号

今天最容易读错的是**同一张榜上并存的两种热度形态**，把它们放在一起看比单独判断任何一个项目都有用：

- **传播型**：`mattpocock/skills`（235K stars / 1.3K watchers / 392 issues）、`obra/superpowers`（277K / 1.0K / 314）、`affaan-m/ECC`（243K / 1.2K / 176）、`multica-ai/andrej-karpathy-skills`（207K / 1.2K / 129，且四个月未更新）。星数是榜单里最高的一档，issue 池却只有三位数。这类仓库的内容是提示词与方法论，被收藏、被 fork 拿走用，但很少产生工程反馈——star 在这里主要代表"读到了、存下了"。
- **运行型**：`Wei-Shaw/sub2api`（39K stars / 8.1K forks / 2,816 open issues）、`anthropics/claude-code`（143K / 15,295 issues）、`openai/codex`（117K / 13,726 issues）、`n8n-io/n8n`（202K / 60K forks）。星数不一定最高，但 issue 与 fork 的绝对量说明有人真的在跑它、并且跑出了问题。

两种都不是"假热度"，但读者的动作应该不同：传播型适合当资料读，采用前要自己验证；运行型可以直接看 issue 区判断它在你的场景里会不会踩坑。
