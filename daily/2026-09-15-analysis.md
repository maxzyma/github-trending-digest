## NEW 项目

### [rlaope/oh-my-hermes](https://github.com/rlaope/oh-my-hermes) — NEW ⭐ 2,179（+77）| Python | 信源：弱

**它是什么**: Hermes Agent 是 Nous Research 去年 7 月开源的命令行编码智能体，可以理解成"终端里的编程助手"。oh-my-hermes（下称 OMH）是套在它外面的增强插件包——名字明摆着仿 oh-my-zsh。它不改 Hermes 本身，而是在上面加一层调度：先给你的请求打分分类，决定用哪个模型、拆成几条并行的活、调哪些技能，最后要求"干完的事必须拿出证据"才算完成。官网号称 116 个技能、9 套工作流、7 个能力族。

**解决什么问题**: 在它之前，用户要自己手写 prompt 模板、按任务手动切模型、每开一个新会话重新交代一遍项目背景，也没有办法确认智能体说的"做完了"是不是真做完。OMH 把这几件事打包成一次安装：长期记忆负责跨会话保住项目上下文，工作流包负责按任务类型（深度推理 / 快速响应 / 写作 / 可视化）路由到不同模型和推理强度。

**谁在用、怎么用**（来自 Issues/HN/Reddit/X/评测）:
- 外部使用者的痕迹极少。近 100 条 issue 里只有零星几条来自项目外：#1267 有人请求把 OrcaRouter 加为可选 provider，#1512 报告 OMH 的运行时状态没有绑定当前 Hermes profile，#1430 修了 symlink 插件目录导致的安装失败。
- 其余 94 条由作者本人及其两个账号提出——README 明确写着 `sionic-khope`（Killua）与 `frirenai`（Friren）是**作者自己的 AI agent**，#1553 / #1551 / #1549 就是同一天自开自办的一串。
- 作者自办的 benchmark issue（#1333、#1327、#1056）目前还没跑出"OMH 比裸 Hermes 好在哪"的数字。

**社区怎么评价**:
- 正面: 无可引用的独立开发者评价。
- 负面: 同样没有——不是口碑好，是几乎没有外部使用者在提问题。HN 检索命中数为 0，Reddit 无讨论，X 上只有作者 @rlaope 自己的更新帖；唯一的第三方提及来自 SkillsLLM、SkillsMP、RepoRadar 这类自动抓取的聚合站。
- 健康度: 2,179 ⭐ / **8 subscribers**（约 272:1），fork 168 而 watch 只有 8；open issues 19，但累计 issue 269、PR **1,284**，7 天内 100+ commits。贡献者 rlaope 1,743 + sionic-khope 1,034 + frirenai 580，合计占 98% 以上。仓龄 3 个多月（2026-06-03 建）。

**风险与争议**:
- **vanity**: 272:1 的比值叠加零 HN / Reddit / X 有机讨论和 3 个月仓龄，热度与社区足迹严重不匹配；"1,284 个 PR"里绝大多数由作者及其 AI 账号产出，不能读作社区参与度。
- **bus_factor**: 单一作者加其两个 AI 账号占 98% 以上贡献，没有第二个实质维护者。
- **stability**: v1.x 刚起步，日均数十次提交，已有安装类缺陷（#1430、#1512）。
- **security**: 主推 `curl … | sh` 与 `irm … | iex` 一键安装，还提供"把这段话粘给你的 AI agent 让它自动装"的 prompt，供应链暴露面偏宽。
- **命名混淆**: 另有 witt3rd/oh-my-hermes 同名项目，且存在完整镜像 fork，安装前请核对来源。

**技术备注**: Python，MIT 许可，2026-06-03 建仓。依附 NousResearch/hermes-agent 运行，本身是插件层而非独立 runtime。

### [peetzweg/opendisplay](https://github.com/peetzweg/opendisplay) — NEW ⭐ 3,678（+229）| Swift | 信源：中

**它是什么**: 把闲置的 iPhone、iPad 或旧 Mac 变成 Mac 的第二块显示器。插上数据线或连到同一个 WiFi，设备就出现在系统的"显示器排列"里，是一块真实的扩展屏而不是投屏画面，还能当触摸板用（点按、拖拽、双指滚动）。

**解决什么问题**: 之前三条路各有门槛——Apple Sidecar 免费但要求两台设备同一 Apple ID，而且完全不支持 iPhone；Duet Display 改成了订阅制；Luna Display 要买一个硬件狗。OpenDisplay 补的正是这个缺口：免费、开源、不要账号、不要额外硬件，出差时用手上已有的设备临时加一块屏。

**谁在用、怎么用**（来自 Issues/HN/Reddit/X/评测）:
- 有线模式是当前口碑最好的用法，多篇第三方评测（Newsshooter、Softpedia、ProductiveToolz）的一致结论是"USB 下延迟低、即插即用，WiFi 配置体验糟糕，建议当有线方案用"。
- 协议文档化带来了实际的生态扩散：社区已基于 `PROTOCOL.md` 做出 Android / GrapheneOS 客户端和 iOS 12 客户端。
- 典型场景是笔记本外出办公临时加屏、旧 iPad 或旧 Mac 再利用，以及公司 Mac 与个人 iPad 不同 Apple ID 因而用不了 Sidecar 的人。

**社区怎么评价**:
- 正面: 有线连接稳定、画质到 Retina、把触摸板功能一并做了；开放协议吸引第三方客户端是同类项目里少见的。
- 负面: 连接稳定性是主矛盾。#133 报告 Intel Mac + Sequoia 下显示已连接但 iPad 黑屏（11 条评论），#160「Shows Connected but does not work」，#149 有中文用户反馈 WiFi 下连不上，#125 指出本地网络权限的状态判断有误——README 自己也承认两端 Local Network 权限缺失时不给任何提示。#271 是一条高质量缺陷：5K 屏上选「Best」画质会悄悄超过 H.264 的像素率上限，编码器逐帧拒绝，换「Balanced」才正常。#4 要求 Apple Pencil 压感，尚未落地。
- 健康度: 3,678 ⭐ / 14 subscribers（约 263:1），252 forks，142 open issues。贡献者高度集中——作者 peetzweg 212 commits、CI bot 52、第三名仅 3 commits。仓龄 3 个月（2026-06-10 建），最后 push 9 月 6 日。

**风险与争议**:
- **bus_factor**: 核心提交 99% 出自一人，142 个 open issue 已明显堆积。
- **stability**: 仍是 0.x，连接失败类 issue 占比高，Intel Mac、5K 屏等组合有已知缺陷。
- **dependency**: 依赖私有 API `CGVirtualDisplay` 建虚拟屏，macOS 大版本升级可能直接打断。
- **compliance**: v0.5 起许可从 MIT 改为 GPL-3.0（0.4.x 及更早仍是 MIT），商业二次开发需重新评估。
- **热度与讨论不对称**: 3,678 ⭐ 但 HN 主贴 3 分 0 评论、Reddit 的 r/macapps 与 r/apple 均无帖，传播主要来自媒体转载和聚合站，社区讨论足迹薄于星数。

**技术备注**: Swift，GPL-3.0。私有 `CGVirtualDisplay` 建虚拟屏 + ScreenCaptureKit 抓帧 + VideoToolbox 硬件 H.264 + 单条 TCP（USB 走系统自带 usbmuxd）。要求 macOS 14+、iOS/iPadOS 16+、接收端 Mac 12+；走 App Store / TestFlight，或用免费 Apple ID 在 Xcode 自建。

## 如何理解今天的热度信号

今天 9 项 RE 提供了一个很干净的对照组，可以用来练一套判断方法：

1. **先看 `pushed_at` 落在哪一次提交上，而不是看它是不是最近。** MiroFish 的最后 push 是 9 月 3 日，看起来很新，点开却是 `chore: update star history [skip ci]`；Agent-Reach 的最后 push 是 9 月 1 日，内容是改赞助商链接。而 localsend 同样是 9 月 14 日，落在十余个功能与修复 PR 上。同一个字段，含义完全不同。
2. **stars/subscribers 比值只是触发器，不是结论。** 今天全榜比值从 vaultwarden 的 213:1 一直铺到 oh-my-hermes 的 272:1，两者性质截然相反：前者是 2018 年建仓、日常有正确性修复的基建，后者是 3 个月仓龄、外部讨论为零的新仓。比值高只应该让你去做交叉验证，不应该直接得出判断。
3. **issue 的提交者是谁，比 issue 数量更能说明问题。** oh-my-hermes 有 269 条累计 issue 和 1,284 个 PR，数字很漂亮，但其中绝大多数由作者本人及其两个 AI 账号产出；opendisplay 只有 142 个 open issue，却包含 #133、#271 这类带具体机型、具体分辨率、具体失败表现的外部报告。后者才是"有人真在用"的证据。
